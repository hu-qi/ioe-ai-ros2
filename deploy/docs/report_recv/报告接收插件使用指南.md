# 报告接收插件（report_recv）使用指南

> 模块：ReportRecvPlugin v1.0.0
> 代码：`app_mgr_object/components/web/report_recv_plugin.py` + `report_repo.py` + `event_merge.py` + `reports_schema.sql`
> 接线：`app_mgr_object/components/web/web_server.py`（9 端点自动注册）
> 关联方案：doc/70（报告接收插件开发方案）、doc/38（整包 schema 1.0）、doc/45（增量 schema 1.1）
> 文档性质：**使用 / 对接 / 运维手册**（非开发方案）

---

## 1. 模块概述

报告接收插件是"教官操作端"数据汇聚的唯一入口，负责接收并存储边缘端（工位设备）上报的**操作报告**，供后续检索、复查、统计（P2 统计插件）与看板展示（P3）。

### 1.1 它解决什么问题

| 数据流 | 协议 | 端点 | 说明 |
|---|---|---|---|
| 整包报告 | doc/38 schema 1.0 | `POST /api/v1/reports` | 一轮操作结束时上报完整事件流/步骤/子步骤 |
| 实时增量 | doc/45 schema 1.1 | `POST /api/v1/events` | 操作过程中步骤变化时实时上报 |
| 订阅管理 | doc/45 §4 | `/api/v1/subscriptions*` | 平台订阅设备后，边缘端才开始增量上报 |
| 抓拍证据 | doc/45 §6 | `POST /api/v1/evidence` | 超时抓拍图（multipart） |

### 1.2 关键设计（使用前须知）

- **幂等去重**：整包以 `device_id + round.start_ms` 去重（重复上报返回成功但不重复入库）；增量以事件主键天然去重（重复上报 `delta_events=0`）。
- **软关联学员**：报告入库不依赖学员档案（P0 学员管理插件可未部署）；`student.id` 存在且命中 `students` 表 → `student_bound=1`，否则为 0，**不阻塞入库**。
- **增量先于整包**：增量事件先到时自动创建"存根报告"（`is_stub=1`）；整包后到会因幂等去重跳过（见 §5.3 FAQ，当前路由未接入补全逻辑）。
- **原始留存**：整包原始 JSON 落盘 `config/data/reports/{device_id}/{report_id}.json`。

### 1.3 涉及文件

| 文件 | 作用 |
|---|---|
| `components/web/report_recv_plugin.py` | 插件类 + 9 个 FastAPI 端点 |
| `components/web/report_repo.py` | SQLite 六表仓储（入库/检索/订阅/落盘） |
| `components/web/event_merge.py` | 增量事件合并器 |
| `components/web/reports_schema.sql` | 六表 DDL（reports/report_steps/report_substeps/report_events/report_progress/subscriptions） |

## 2. 启用与配置

### 2.1 启用条件

报告接收路由**随 Web 服务器自动注册**，不需要在 `plugin_load_order` 中单独添加插件。

只需满足：

1. `web_monitor` 插件在 `config/params.yaml` 的 `plugin_load_order` 中（当前默认已含，末尾 `web_monitor`）；
2. `config/web_monitor.yaml` 中 `enabled: true`（默认）；
3. Web 服务器启动成功（默认端口 **9183**，host 为 `network_interface` 对应网卡 IP，缺省 `0.0.0.0`）。

启动日志出现以下两行即表示就绪：

```
✅ 报告接收插件路由注册完成（9 端点）
ReportRecvPlugin 配置完成: db=.../config/app.db raw_json_dir=.../data/reports evidence_dir=.../data/evidence
```

> 若配置失败只会告警并跳过路由注册，不影响 Web 主服务（见日志 `报告接收插件配置失败，跳过路由注册`）。

### 2.2 默认存储路径（不配置时）

| 项目 | 默认值 | 说明 |
|---|---|---|
| 数据库 | `<包目录>/config/app.db` | SQLite，首次启动自动建六表 |
| 原始 JSON | `<包目录>/config/data/reports/{device_id}/{report_id}.json` | 整包原始 payload 留存 |
| evidence 抓拍图 | `<包目录>/config/data/evidence/{device_id}/{round_start_ms}/sub_{sub}_ts_{ts}.jpg` | multipart 上传的图片 |
| Web 端口 | 9183 | `web_monitor.yaml` 的 `port` |

### 2.3 定制路径（可选）

插件的 `config` 来自 Web 服务器配置中的 `report_recv` 段（`web_server.py` 中 `config=self.config.get('report_recv', {})`），支持：

```yaml
report_recv:
  db_path: "config/app.db"            # 覆盖数据库位置
  raw_json_dir: "config/data/reports" # 覆盖原始 JSON 目录
  evidence_dir: "config/data/evidence" # 覆盖 evidence 目录
```

> ⚠️ 当前 `web_monitor.yaml` 中未定义 `report_recv` 段，且 `web_monitor_plugin.py` 的 `_web_server_config` 尚未透传该段 —— 因此**默认即用代码内置路径，无需任何配置**。如需定制，需要同时在 `web_monitor_plugin.py` 的 `_web_server_config` 构造中加入 `'report_recv': self.plugin_config.get('report_recv', {})`，此处未做改动。默认路径已满足常规部署，建议先用默认值。

## 3. API 接口操作手册

> 基础地址：`http://<平台IP>:9183`（以下示例以 `http://127.0.0.1:9183` 表示，真机联调替换为平台实际 IP）。
> 统一响应格式：成功 `{"code": 0, "message": "ok", "data": {...}}`；失败为 4xx/5xx + `{"code": <http码>, "message": "...", "data": {}}`。

### 3.1 端点总览

| # | 方法 | 路径 | 功能 | 数据来源 |
|---|---|---|---|---|
| 1 | POST | `/api/v1/reports` | 接收整包报告 | doc/38 schema 1.0 |
| 2 | POST | `/api/v1/events` | 接收增量事件 | doc/45 schema 1.1 |
| 3 | GET | `/api/v1/reports` | 报告列表检索（分页+多条件） | — |
| 4 | GET | `/api/v1/reports/{report_id}` | 报告详情（steps/substeps/events） | — |
| 5 | POST | `/api/v1/subscriptions` | 订阅设备 | doc/45 §4.1 |
| 6 | GET | `/api/v1/subscriptions/{device_id}` | 查询订阅状态 | doc/45 §4.2 |
| 7 | DELETE | `/api/v1/subscriptions/{device_id}` | 退订设备 | doc/45 §4.3 |
| 8 | GET | `/api/v1/subscriptions` | 订阅设备列表 | doc/45 §4.4 |
| 9 | POST | `/api/v1/evidence` | 接收抓拍图（multipart） | doc/45 §6 |

### 3.2 接收整包报告 — `POST /api/v1/reports`

**必填**：`device_id`、`round.start_ms`（缺任一返回 422）。其余字段按 doc/38 schema 1.0（`student` 可为空对象 `{}`）。

请求示例：

```bash
curl -s -X POST http://127.0.0.1:9183/api/v1/reports \
  -H "Content-Type: application/json" \
  -d '{
    "schema_version": "1.0", "device_id": "dev01",
    "edge_node": "touch_ui_plugin", "ts_upload_ms": 1787569200000,
    "student": {"id": "S2024001", "name": "张明", "cls": "机修一班", "source": "manual"},
    "round": {
      "process_name": "组装自动机监测", "process_type": "assembly",
      "finish_reason": "completed",
      "start_ms": 1787569113000, "end_ms": 1787569200000,
      "duration_ms": 87000, "process_elapsed_ms": 87000,
      "events": [
        {"ts": 3200, "kind": 0, "step": 1, "sub": 1},
        {"ts": 11400, "kind": 1, "step": 1, "sub": 1}
      ],
      "steps": [{"idx": 1, "name": "装缓冲", "state": 2, "duration_ms": 8200,
                 "start_ms": 3200, "end_ms": 11400, "interval_ms": 0}],
      "substeps": [{"idx": 1, "name": "装缓冲", "state": 2, "duration_ms": 8200,
                    "count": 1, "total_duration_ms": 8200, "timeout": false,
                    "start_ms": 3200, "end_ms": 11400}],
      "unexecuted": [13, 14], "substep_counts": [1, 2, 2, 1, 2, 4, 2, 2]
    }
  }'
```

成功响应（`report_id = R{device_id}_{round.start_ms}`）：

```json
{ "code": 0, "message": "ok", "data": { "report_id": "Rdev01_1787569113000" } }
```

**幂等行为**：同一 `device_id + start_ms` 重复上报 → 同样返回 `code:0`，但**不会重复入库**（服务端日志 `整包去重命中`）。原始 JSON 会同步落盘到 `config/data/reports/{device_id}/{report_id}.json`。

### 3.3 接收增量事件 — `POST /api/v1/events`

**校验**：`schema_version` 必须为 `"1.1"`（否则 422）；必填 `device_id`、`round_start_ms`。`events` 为空数组时直接返回 `delta_events:0`。

请求示例：

```bash
curl -s -X POST http://127.0.0.1:9183/api/v1/events \
  -H "Content-Type: application/json" \
  -d '{
    "schema_version": "1.1", "type": "event_delta",
    "device_id": "dev02", "edge_node": "touch_ui_plugin",
    "ts_upload_ms": 1788407910000,
    "round_start_ms": 1788407000000, "process_elapsed_ms": 910000,
    "student": {"id": "S2024002", "name": "李华", "cls": "二班", "source": "manual"},
    "events": [
      {"ts": 12000, "kind": 0, "step": 1, "sub": 2},
      {"ts": 18500, "kind": 1, "step": 1, "sub": 2}
    ],
    "progress": {"done": 2, "total": 19, "current": "装扣机", "current_sub_index": 5}
  }'
```

成功响应（`delta_events` = 实际新增条数）：

```json
{ "code": 0, "message": "ok", "data": { "device_id": "dev02", "delta_events": 2 } }
```

**行为要点**：

- 增量事件写入 `report_events` 表（`source=delta`），主键 `(report_id, ts, kind, sub)` 天然去重，**重复上报 delta_events=0**；
- 更新 `report_progress` 实时进度快照（done/total/current/current_sub_index/process_elapsed_ms）；
- 若该轮次的整包尚未到达，自动创建**存根报告**（`is_stub=1`，见 §5.1 FAQ）；
- 入库后发布事件总线事件 `report.realtime_delta`（供后续 WebSocket 推送）。

### 3.4 报告列表检索 — `GET /api/v1/reports`

Query 参数（全部可选）：

返回主表 + 步骤 + 子步骤 + 事件流四部分；报告不存在返回 404。


### 3.6 订阅设备 — `POST /api/v1/subscriptions`

平台侧主动订阅某台设备；重复订阅 = 更新 note 且保持 active（返回 `resubscribed` 语义，响应含首次订阅时刻）。

```bash
curl -s -X POST http://127.0.0.1:9183/api/v1/subscriptions \
  -H "Content-Type: application/json" \
  -d '{"device_id": "dev01", "note": "1号工位"}'
```

```json
{ "code": 0, "message": "ok", "data": { "device_id": "dev01", "active": true, "subscribed_at_ms": 1788407900000 } }
```

> 支持**多设备同时订阅**：对每台设备逐次 POST 即可，互不影响。

### 3.7 查询订阅状态 — `GET /api/v1/subscriptions/{device_id}`

边缘端轮询此接口判断是否继续增量上报；未订阅返回 404。

```bash
curl -s http://127.0.0.1:9183/api/v1/subscriptions/dev01
```

```json
{ "code": 0, "message": "ok", "data": { "device_id": "dev01", "active": true, "subscribed_at_ms": 1788407900000 } }
```

### 3.8 退订设备 — `DELETE /api/v1/subscriptions/{device_id}`

置 `active=0`，停止该设备增量上报（记录仍保留，可重新订阅）。

```bash
curl -s -X DELETE http://127.0.0.1:9183/api/v1/subscriptions/dev01
```

```json
{ "code": 0, "message": "ok", "data": { "device_id": "dev01", "active": false, "was_active": true } }
```

### 3.9 订阅设备列表 — `GET /api/v1/subscriptions`

返回全部订阅记录（含 active=0 的历史设备），管理用途。

```bash
curl -s http://127.0.0.1:9183/api/v1/subscriptions
```

```json
{ "code": 0, "message": "ok", "data": { "devices": { "dev01": { "device_id": "dev01", "active": 1, ... } } } }
```

### 3.10 接收抓拍图 — `POST /api/v1/evidence`

multipart/form-data，字段：`file`（图片文件）、`sub`（子步骤序号 int）、`ts`（时间戳 int）、`device_id`。文件保存为 `{evidence_dir}/{device_id}/{round_start_ms}/sub_{sub}_ts_{ts}.jpg`（当前实现以 `ts` 近似 `round_start_ms` 组织目录）。

```bash
curl -s -X POST http://127.0.0.1:9183/api/v1/evidence \
  -F "file=@capture.jpg" -F "sub=3" -F "ts=1787569120000" -F "device_id=dev01"
```

```json
{ "code": 0, "message": "ok", "data": { "path": ".../evidence/dev01/1787569120000/sub_3_ts_1787569120000.jpg" } }
```

## 4. 边缘端对接联调

### 4.1 边缘端配置（touch_ui_plugin 侧）

真机联调前，在边缘端 `params.yaml` 配置平台地址（联调示例值）：

| 边缘端配置项 | 说明 | 示例值 |
|---|---|---|
| `report_enabled` | 开启整包上报 | `true` |
| `report_upload` | 上报方式 | `"http-post"` |
| `report_upload_url` | 平台整包接收端点 | `http://<平台IP>:9183/api/v1/reports` |
| `report_subscribe_api` | 平台订阅状态查询端点 | `http://<平台IP>:9183/api/v1/subscriptions/{device_id}` |
| `realtime_events_api` | 平台增量事件接收端点 | `http://<平台IP>:9183/api/v1/events` |
| `subscribe_poll_sec` | 订阅状态轮询间隔 | `5` |
| `realtime_upload_sec` | 增量事件攒批上报间隔 | `2` |

### 4.2 标准联调流程

一次完整的"订阅 → 实时增量 → 轮次结束整包"链路：

```
① 教官在平台订阅设备
   POST /api/v1/subscriptions {"device_id":"dev01"}
   └→ subscriptions.active = 1

② 边缘端轮询订阅状态（subscribe_poll_sec）
   GET /api/v1/subscriptions/dev01 → {"active": true}
   └→ 判定可上报，开始实时增量

③ 学员操作过程中，步骤变化 → 边缘端攒批上报
   POST /api/v1/events（schema 1.1，含 events + progress）
   └→ 追加 report_events + 刷新 report_progress（可能创建存根报告）

④ 一轮操作结束 → 边缘端上报整包
   POST /api/v1/reports（schema 1.0，含 events/steps/substeps/unexecuted）
   └→ 入库 reports + report_steps + report_substeps + report_events，原始 JSON 落盘

⑤ （可选）结束实时上报
   DELETE /api/v1/subscriptions/dev01 → active=0
```

### 4.3 联调前快速自测（不依赖真机）

用 §3.2/§3.3 的 curl 示例按 ①②③④ 顺序模拟一遍即可验证平台侧链路：

1. POST 订阅 dev01 → 期望 `active: true`；
2. POST 增量事件（dev01, round_start_ms 用整包同值）→ 期望 `delta_events: 2`；
3. GET 订阅状态确认 active；
4. POST 整包报告 → 期望 `report_id: Rdev01_<start_ms>`；
5. 重复 POST 同一整包 → 返回成功但**不重复入库**（验证幂等）；
6. GET `/api/v1/reports?device_id=dev01` 与 `/api/v1/reports/{report_id}` 核对入库结果；
7. DELETE 退订 → 期望 `active: false`。

### 4.4 多设备同时订阅验证

逐台 POST 订阅不同 `device_id`（如 dev01 + dev02），两台设备可并行上报增量，互不影响；`GET /api/v1/subscriptions` 应同时列出两台设备。

## 5. 数据验证与常见问题

### 5.1 数据库验证（六表）

库文件默认 `<包目录>/config/app.db`，可用 sqlite3 直接核对：

```bash
sqlite3 config/app.db ".tables"
# 期望: report_events  report_progress  report_steps  report_substeps  reports  subscriptions
```

| 验证点 | SQL 示例 | 期望 |
|---|---|---|
| 整包入库 | `SELECT report_id,device_id,student_name,finish_reason,is_stub,start_ms FROM reports;` | 每轮次一行，`is_stub=0` |
| 整包去重 | 对同 `device_id+start_ms` 重复 POST 后再查 | 行数不变 |
| 步骤明细 | `SELECT count(*) FROM report_steps WHERE report_id='Rdev01_...';` | 与整包 `steps` 条数一致 |
| 增量追加 | `SELECT source,count(*) FROM report_events GROUP BY source;` | batch/delta 两条来源共存 |
| 实时进度 | `SELECT done,total,current,current_sub_index,last_delta_ts FROM report_progress;` | 与最近增量 progress 一致 |
| 订阅状态 | `SELECT device_id,active FROM subscriptions;` | 订阅 active=1，退订后 0 |
| 原始 JSON | `ls config/data/reports/dev01/` | `Rdev01_<start_ms>.json` 存在 |

### 5.2 自动化回归验证（17 项）

仓库根已有端到端验证脚本（17 项断言，覆盖六表建表/整包/去重/增量/多设备订阅/存根/进度快照/落盘/evidence/统一计时）：

```bash
python3 test_verify_report_recv_126.py
```

期望输出 `17 项测试全部通过`（脚本使用 `/tmp` 临时库，不影响运行中的 `config/app.db`）。

### 5.3 常见问题（FAQ）

| 现象 | 原因与处理 |
|---|---|
| POST `/api/v1/reports` 返回 422 | 缺 `device_id` 或 `round.start_ms`（必填校验） |
| POST `/api/v1/events` 返回 422 | `schema_version` 不是 `"1.1"`，或缺 `device_id`/`round_start_ms` |
| 返回 `{"code":0}` 但库里没新数据 | **幂等命中**：该 `device_id+start_ms` 已存在（整包）或事件主键重复（增量 `delta_events=0`），属预期行为；换新 `start_ms` 验证 |
| 列表里出现 `is_stub=1` 的报告 | 增量先于整包到达时创建的存根；**注意**：当前实现中整包后到会命中幂等去重直接跳过（路由调用 `insert_full_report` 先去重），存根不会被自动补全（补全逻辑 `reconcile_full_report` 已实现但未接线），需关注后续版本或由统计/看板插件消费时处理 |
| GET 报告详情返回 404 | `report_id` 格式必须为 `R{device_id}_{round_start_ms}`，核对 `start_ms` |
| 订阅状态查询返回 404 | 该设备从未订阅，先 POST `/api/v1/subscriptions` |
| evidence 返回 500 | 图片写入失败（路径权限/磁盘），边缘端不重试，可接受丢帧（doc/45 §6）；检查日志确认 |
| Web 启动日志出现"报告接收插件配置失败，跳过路由注册" | 数据库/目录初始化异常；检查 `config/app.db` 路径可写性 |
| 时间字段怎么全是"很大的毫秒数" | 引擎单调毫秒时间轴（doc/45 §5/doc/58 统一计时），只有差值有意义；墙钟时间看 `ts_upload_ms` |
