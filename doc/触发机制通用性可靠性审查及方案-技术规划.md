# 触发机制通用性可靠性审查及方案-技术规划

> 状态：审查完成，规划中（2026-08-27 提交审核，**未修改代码**）
> 工程：app_mgr_object-0.2.0(标准版)
> 范围：策略配置机制（yaml / 前端预置·自定义）、触发队列老化去除、匹对稳定机制

## 一、需求
1. **策略配置机制**：通过 yaml 文件配置（smart_trigger.yaml）驱动触发业务；或前端选择预置策略/自定义策略；
2. **触发队列老化去除**：超时老化的匹对数据及时清除，避免老化队列影响后续业务；无任务/无始发仓时检查一次老化队列；
3. **匹对稳定机制**：目的仓空状态被始发匹对后应锁定资源状态；逐个匹配成功更新目的仓状态后再匹配下一个，避免多始发指向同一空仓。

## 二、测试现象与代码根因审查

### 2.1 现象：目的仓有货仍参与匹配候选；巷道放置语义
- **用户澄清规则**：放置恒从 1~n 升序**连续**放置；FIFO 与 FILO 均为「巷道最大 n 有货 → 配 n+1」；**中间空位（如 n-1 空，或 n 与 1 之间有洞）不可配**（AGV 进巷道过不去）；FIFO/FILO 差异在**出库（取货）顺序**，不在放置选择；
- **代码审查**：
  - `get_empty_bays_of_type(cargo_type)`（dest_bay_cache.py）按类型取空位，**未考虑巷道/连续占用**——目的仓有货不会入选（is_empty=False 过滤），但**巷道内中间空位会被误选**（任意空位语义）；
  - `select_slot`（pairing_policy.py）：fifo=最小空位索引、filo=最大空位索引——① filo 从尾放置**与用户规则不符**（放置恒从头）；② fifo 取最小空位**未校验前方（入口侧）连续占用**——如 1 满、2 空、3 满时误配 2（AGV 实际过不去）；
- **结论**：需修正为「**巷道连续占用下一个空位**」选择算法，与 FIFO/FILO 无关（策略用于出库预留）。

### 2.2 现象：多个始发候选指向同一空仓（目的仓锁定滞后）
- **代码链路**：候选生成（batch_scan_all/greedy_scan_type）→ 入队（enqueue_all，仅内存 `_queued_dst` 排除）→ 出队（try_dequeue → dispatch_task 仅 locker 内存锁）→ 任务完成释放（release_task 才 `dest_cache.update(dst, is_empty=False)`）；
- **缺陷①**：**出队后 `_queued_dst.discard`** 且 dest_cache.is_empty 仍 True → 下一轮扫描该目的仓**再次成为候选**（重复指向）；
- **缺陷②**：候选生成→入队间隙与排队期间目的仓 is_empty 未更新，多轮扫描可产生多个指向同一空仓的任务；
- **结论**：目的仓占用**滞后到任务完成才标记**——需「**匹配/入队即锁定**」机制（与 RCS 轮询协调）。

### 2.3 现象：始发仓已绑定未执行，人工移走货物应解绑并移出队列
- **代码现状**：AI 稳定空 → `_on_stable_empty` → `set_unbound` 解绑（bay_status_fusion_plugin 已实现 ✓）；
- **缺陷**：smart_trigger **未订阅解绑事件、未调用 remove_by_src**——队列中该始发仓的匹对任务残留（会继续派发无效任务）；
- **结论**：需「解绑 → 移出队列」事件联动（remove_by_src 接口已存在）。

### 2.4 现象：老化队列累积
- **代码现状**：task_queue.age_out（TTL 300s）已存在，smart_trigger 扫描循环每 2s 调用（✓）；remove_by_src/remove_by_dst 接口已有；
- **缺陷**：老化/移除时**未释放目的仓占用**（与 2.2 联动缺失）；无「空闲时主动检查老化」的显式机制（周期调用已覆盖，可加告警）；
- **结论**：老化机制已具备，需补「老化释放占用」与空闲检查增强。

### 2.5 策略配置机制
- **代码现状**：smart_trigger.yaml 已集中 cargo_priority/pair_overrides/work_schedule/operation_mode/scan_interval/aging_ttl/max_tasks；巷道策略在 status_poller.yaml pairing_policy（前端可编辑）；
- **缺口**：前端无「预置策略模板」一键配置；
- **结论**：触发参数已 yaml 驱动；建议增加 yaml 预置模板 + 前端下拉。

## 三、方案设计

### 3.1 巷道放置/匹配规则（匹对稳定-放置规则，最新需求修订）
- **匹配规则（巷道最大占用模型）**：巷道按 1~n 升序放置；**匹配依据 = 巷道内最大有占用的仓位 n** → 候选 = **n+1 的空仓位**；**中间空位不参与匹配**（“有货或中间有空位，匹配只需要根据巷道的最大有占用的仓位来匹对”——只看最大占用，空洞不阻塞匹配判定，AGV 按巷道升序放置）；FIFO/FILO 不影响放置选择（放置恒 1~n 升序），策略字段保留供出库调度预留；
```python
# dest_bay_cache.py select_by_strategy 核心修正（开关 lane_state_management 启用时）：
# 巷道最大占用索引 max_occ → 候选 = bays[max_occ+1]（紧邻最大占用的空位）
def _max_occupied_next_slot(self, lane) -> Optional[int]:
    max_occ = -1
    for i, b in enumerate(lane.bay_ids):          # 巷道升序扫描
        if b in self._bays and not self._bays[b].is_empty:
            max_occ = i                            # 记录最大占用索引
    nxt = max_occ + 1
    if nxt < len(lane.bay_ids):
        b = lane.bay_ids[nxt]
        if b in self._bays and self._bays[b].is_empty:
            return nxt                             # 最大占用后的空位（n+1）
    return None                                    # 巷道满/最大占用后无空位
# select_by_strategy：每巷道 _max_occupied_next_slot → 命中返回 lane.bay_ids[nxt]
# 开关关闭时回退旧行为（any 任意空位）
```
- 场景验证：巷道 [T2001,T2002,T2003,T2004]：全空 → max_occ=-1 → 候选 T2001（入口第一位）；T2001~T2003 有货 → max_occ=2 → 候选 T2004（n+1）；中间空洞（T2001 有货、T2002 空、T2003 有货）→ max_occ=2 → 候选 T2004（**跳过空洞 T2002**，按最大占用匹对）；T2001~T2004 全有货 → 无候选。

### 3.2 目的仓锁定/释放机制（匹对稳定-资源锁定，每次匹对更新才下一个）
- dest_cache 增加**保留状态**：`_reserved: Dict[str, str]`（bay_id → 来源 queued/dispatched/executing）；
- **每次匹对更新占用后再匹对下一个**：greedy_scan_type 逐个 src 配对——**每成功配对一个，立即 `dest_cache.mark_occupied(dst, source='matched')` 更新目的仓占用**（真实状态，非仅内存排除），之后才进行下一个 src 的匹对；下一个 src 的 select_by_strategy 基于**更新后的状态**选择（被占用/有货的仓位不再入选）；
- **入队即占用**：enqueue_all 对每候选 `dest_cache.mark_occupied(dst, source='queued')`（is_empty=False + reserved，幂等覆盖 matched）；
- **出队/派发**：reserved=dispatched（state_coordinator.dispatch_task）；
- **释放**（老化/remove_by_src/remove_by_dst/任务失败）：`dest_cache.release_occupied(dst)`（is_empty=True 回空）；
- **任务完成**：release_task 释放 reserved（RCS 轮询接管真实占用）；
- **RCS 轮询 update**：reserved 中的仓**不置回空**（轮询只更新非 reserved 仓的空/占用）；轮询后重算巷道最大占用（3.6）。

### 3.3 人工移走解绑 + 移出队列
- bay_status_fusion：稳定空解绑时 `_publish_event('bay.unbound', {'bay_id': bay_id})`（在 _on_stable_empty 增加）；
- smart_trigger：订阅 `bay.unbound` → `self._task_queue.remove_by_src(bay_id)` + 释放该 src 锁定（locker/coordinator）；
- 队列移除后目的仓释放（若该 src 的候选已占用目的仓）。

### 3.4 队列老化完善
- age_out 移除时：`release_occupied(dst)` + 释放 src 锁定；
- 空闲机制：扫描循环已周期 age_out（2s）；增强：**无候选且队列非空时**记录老化告警日志；「无任务/无始发仓时主动清理」由周期调用覆盖；
- aging_ttl 由 smart_trigger.yaml 配置（已有）。

### 3.5 策略 yaml 配置 + 预置模板
- **触发参数**：smart_trigger.yaml 保持驱动（scan_interval/aging_ttl/max_tasks/cargo_priority/pair_overrides/work_schedule/operation_mode）；
- **预置模板**：status_poller.yaml `pairing_policy.presets`：
```yaml
pairing_policy:
  presets:
    - id: all-fifo
      name: 全FIFO（按巷道连续升序放置）
      lanes: [...]      # 模板巷道（可省略 bays 按 lane 派生）
      type_rules: {...}
      default_strategy: fifo
    - id: mixed
      name: 混合（2F-3F 巷道 FIFO / 4F 巷道 FILO）
      lanes: [...]
      type_rules: {...}
```
- **前端**：策略弹窗加「预置模板」下拉（读取 pairing_policy.presets）→ 选择回填 lanes/type_rules → 保存（写 pairing_policy yaml 热加载）；自定义策略仍手填（现状）。

### 3.6 巷道状态实时管理机制（新增，开关启用）
- **目的**：对巷道仓位状态实时更新感知（RCS 轮询 10s + 匹对占用实时更新），匹配依据 = **巷道最大占用仓位**，处置合理（有货/中间空洞均按最大占用匹对）；
- **开关（yaml 配置）**：`pairing_policy.lane_state_management: true`（默认 false=旧行为 any 任意空位，向后兼容）；也可由 smart_trigger.yaml 全局开关覆盖；
- **实时感知链路**：
  1. RCS 轮询（status_poller `query_pod_berth_and_mat`）→ dest_cache.update 更新每仓 is_empty → **重算巷道最大占用索引**（max_occ）；
  2. 匹对占用（3.2 mark_occupied）→ 同步影响巷道状态（被占用仓视为有货）；
  3. select_by_strategy（开关启用时）→ 每巷道 `_max_occupied_next_slot`（最大占用 + 1 空位）取候选；
- **yaml 配置示例**：
```yaml
pairing_policy:
  lane_state_management: true    # 启用巷道状态实时管理（最大占用匹对）
  default_strategy: fifo
  lanes: [...]
```
- **关闭时**：保持现状（get_empty_bays_of_type 任意空位 / 或连续扫描），不影响既有部署。

## 八、运维可观测性增强-技术方案（2026-08-27 补充）

### 8.1 始发仓解绑 → 前端 toast 提示（§七.3）
- **现状**：bay.unbound 事件已发布（§3.3 实施），smart_trigger 已订阅移出队列；但 **event_bridge 未订阅 bay.unbound**、前端无提示；
- **技术方案**：
  1. event_bridge：business_events 列表加 `'bay.unbound'`（触发 business_update 刷新）＋ 专门 `_on_bay_unbound` 处理：`broadcast('bay_unbound', {bay_id})`（前端 toast 事件）；
  2. 前端 dashboard.js：`WS.on('bay_unbound', ...)` → `showToast('仓位 ' + bay_id + ' 已解绑（货物移走），已移出任务队列', 'warning')`；
- **效果**：人工移走始发仓货物 → 稳定空 → 解绑 + 移出队列 + 前端 toast（运维可观测）。

### 8.2 任务信息栏「已锁定目的仓」可视化（§七.2）
- **现状**：dest_cache 已维护 `_reserved`（queued/matched/dispatched），无对外统计；任务信息栏有 3 统计卡（今日完成/执行中/异常）；
- **技术方案**：
  1. dest_cache 新增 `get_reserved_count() -> int`（`len(self._reserved)`，含 queued+matched+dispatched）；
  2. business_collector.get_task_statistics 增加 `locked_dest` 字段（从 status_poller.dest_cache.get_reserved_count()）；
  3. 前端 renderTaskStats 增加第 4 统计卡「已锁定目的仓」（数字蓝/紫，指标名小号灰，与既有统计卡风格一致）；
- **效果**：运维可见当前保留占用（已匹对未完成）的目的仓数量，辅助判断巷道/队列状态。

### 8.3 中间空洞（§七.5，明确不需要）
- **决策**：目的仓巷道空洞为**正常状态**（工人移走目的仓货物到生产线），系统仅关心放置任务；目的仓 FIFO/FILO 均正常；
- **不做**：不检测空洞、不提示补洞、不影响匹配（最大占用模型已按最大占用匹对，空洞天然跳过）；
- **记录**：若未来需要出库调度（从目的仓取货），再评估空洞对出库的影响（§七.1 出库选择器预留）。

## 九、目的仓位状态颜色标识-技术方案（2026-08-27 补充，待实施）

### 9.1 需求
目的仓位按状态配色（匹对成功后可视化，符合当前 UI 规划规范）：
| 状态 | 含义 | 颜色 |
|------|------|------|
| 空（可用） | 无货、未被匹对 | **绿色** |
| 有货占用 | RCS 真实占用 | **灰色黑** |
| 已匹对锁定 | 始发已匹对（matched/queued/dispatched） | **橙色** |
| 解绑释放 | 因始发仓解绑移出队列而释放 | **蓝色** |

### 9.2 现状实勘
- 前端 renderDestGrid（dashboard.js L213）：仅 `is_empty ? empty(绿) : occupied(灰黑)` 两态；
- CSS（custom.css L175-176）：`.dest-cell.empty`=accent-green(0.7)、`.dest-cell.occupied`=#3a3a4a；
- dest_cache 已维护 `_reserved`（matched/queued/dispatched）但**未输出到前端**；无「解绑释放」状态标记；
- business_collector.get_dest_status（L88-92）每仓输出 is_empty/cargo_type/floor_no——无 reserved/状态字段。

### 9.3 技术方案
**9.3.1 dest_cache 状态扩展**
- 新增 `_unbind_released: Dict[bay_id, ts]`（因始发解绑移出而释放的标记）；
- `release_occupied(bay_id, set_empty=True, source='')`：source='unbind' 时记录 `_unbind_released`；其他来源（老化/失败）清除标记（正常回空=绿色）；
- `mark_occupied` 时清除 `_unbind_released`（重新匹对 → 橙色）；
- 新增 `get_bay_state(bay_id) -> str`：优先 reserved → unbind → occupied → empty。

**9.3.2 解绑释放标记链路**
- smart_trigger `_on_bay_unbound` → task_queue.remove_by_src → `release_occupied(dst, set_empty=True, source='unbind')`（解绑场景标记蓝色）；

**9.3.4 前端渲染（renderDestGrid）**

- 优先级 reserved > unbind > occupied > empty（后端已保证单值）。

## 十、任务统计数据接口-技术方案（2026-08-27 补充，待实施）

### 10.1 需求
任务信息栏「今日累积完成任务」统计需要有**数据接口**提供（前端可直接获取，不依赖业务汇总）。

### 10.2 现状审查
- **接口链路（已存在）**：前端 renderTaskStats ← `task_stats`（`/api/business/summary` 的 getTaskStatistics / WS `business_update` 推送）→ `today_completed`；前端 loadAllData 调 `getBusinessSummary`、WS 推送 `d.task_stats` 双路径；
- **实现**：`business_collector.get_task_statistics` 内 `engine.get_all_instances_from_db(limit=500)` 应用层遍历，过滤 `created_at/completed_at` 今日 + `status==completed` 计数；
- **缺陷**：
  1. **limit=500 上限**——任务历史 >500 条或今日完成 >500 时**漏统计**（计数不准）；
  2. **全量遍历**——每次统计拉 500 条 DB 记录做日期过滤，非精确 SQL；
  3. **无独立接口**——今日完成统计依赖 business summary，无法单独查询。

### 10.3 数据接口规划
**10.3.1 精确统计（后端）**
- persistence 新增按日期统计 SQL：
  - `count_by_date(status, date_field, day)`：`SELECT COUNT(*) FROM task_instances WHERE date(completed_at)=? AND status=?`（今日完成=completed；今日异常=failed）；
  - 无 limit 漏统计、性能 O(索引)；
- engine 暴露 `count_today_completed()` / `count_today_failed()`（透传 persistence）；
- business_collector.get_task_statistics 改用精确 SQL（替换 limit=500 遍历），字段不变（today_completed/failed）；
- 兜底：SQL 异常时回退现有遍历逻辑（容错）。

**10.3.2 独立接口（前端）**
- 新增 `GET /api/task/stats`：返回 `{today_completed, executing, failed, locked_dest, by_status, total}`（直接调 get_task_statistics）；
- api.js 新增 `getTaskStats()`；前端可选：loadAllData 单独拉 getTaskStats（替代依赖 business summary 的第 6 项），WS business_update 推送路径保留（实时）；
- 现有 /api/business/summary 的 task_stats 字段保留（兼容）。

|------|------|

### 10.5 测试验证
- 后端：count_by_date 精确计数（构造今日/昨日/多状态用例）；>500 条历史不漏统计；py_compile；
- 前端：getTaskStats 返回并渲染；node --check；
- 板端：今日完成任务数实时准确（大任务量下无误）；独立接口可查。

### 10.6 边界
- completed_at 为空（未完成任务）不计数（SQL date 过滤自然排除）；
- 时区：DB 时间戳为本地时区（created_at 默认 datetime('now','localtime')），今日按本地日界；
- SQL 异常回退遍历逻辑（数据不中断）；接口兼容 business summary 字段。
