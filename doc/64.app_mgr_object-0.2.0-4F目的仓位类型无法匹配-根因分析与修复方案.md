# 64. app_mgr_object-0.2.0 4F 目的仓位类型无法匹配-根因分析与修复方案

> 状态：**审查完成 / 方案待审核（本次未修改任何代码）**
> 工程：`app_mgr_object-0.2.0(标准版)`
> 日期：2026-09-01 ｜ 现象：T4003(类型3)/T4004(类型4)/T4005(类型5)/T4006(类型6) 一直显示空，无法配对；对应类型始发仓有货

---

## 1. 现象与相关配置

### 1.1 4F 巷道配置（status_poller.yaml）

```yaml
pairing_policy:
  lane_state_management: false
  lanes:
    - id: 4F-L1
      floor: 4
      strategy: fifo
      bays: [T4001, T4002, T4003, T4004, T4005, T4006]   # 类型 1/2/3/4/5/6 各一个
  type_rules:
    1: { lanes: [2F-L1, 4F-L1], strategy: fifo }   # 仅类型1 的规则包含 4F-L1
    2: { lanes: [2F-L2], strategy: fifo }
    3: { lanes: [2F-L3], strategy: fifo }
    4: { lanes: [3F-L1], strategy: fifo }
    5: { lanes: [3F-L2], strategy: fifo }
    6: { lanes: [3F-L3], strategy: fifo }
```

`dest_bay_configs`：T4001→类型1、T4002→类型2、…、T4006→类型6（4F-L1 为**混合类型巷道**）。

### 1.2 匹配链路

```text
batch_scan_all（按 cargo_priority 类型循环）→ greedy_scan_type(cargo_type)
  → get_empty_bays_of_type(cargo_type)                 # 空仓按类型过滤（dest_bay_cache.py:105）
  → select_by_strategy(cargo_type, src_bay, exclude)   # 巷道规则选位（dest_bay_cache.py:334）
      → _resolve_rule: bay_rules(L1) > type_rules(L2) > 类型匹配巷道(L3)（dest_bay_cache.py:220-249）
      → 巷道内取空位（fifo 取最小索引空位，未按类型过滤，dest_bay_cache.py:347-349）
```

---

## 2. 根因分析

### R-01（主因）：`type_rules` 白名单未把 4F-L1 纳入类型 2~6

- `_resolve_rule` 的 **L2（type_rules）命中即返回**（dest_bay_cache.py:238-247），**不会回退 L3**；
- 类型 2~6 的规则只指向 2F/3F 巷道（不含 4F-L1），因此：
  - 类型 3 只扫 2F-L3（T2005/T2006），类型 4~6 只扫 3F-L1/L2/L3；
  - **4F-L1 的 T4002~T4006 永远不会进入任何类型的候选巷道** → 始终 `is_empty=True`（前端一直显示空）；
- 4F-L1 仅在类型 1 的规则中出现，所以只有 T4001 有机会被匹配。

### R-02（潜在错配）：巷道内选空位未按 cargo_type 过滤

- `select_by_strategy` 未启用 `lane_state_management` 分支：`empty = [i for b in lane.bay_ids if b.is_empty and b not in exclude]`（dest_bay_cache.py:347-349）——**无类型过滤**；
- `_max_occupied_next_slot`（启用分支）同样不按类型（dest_bay_cache.py:313-332）；
- `greedy_scan_type` 对 `select_by_strategy` 的返回也不校验类型（batch_matcher.py:204-208）；
- 若直接把 4F-L1 加入类型 2~6 的 lanes（仅配置修复），fifo 会优先选 **T4001（类型1 空位）** 配给类型 2~6 的任务 → **跨类型错配**。因此必须同时做代码修复（见 §4）。

### R-03：排序顺序不是根因（回答“时间→区域→类型”能否解决）

- 目的仓能否被选中，取决于 `type_rules` 的**巷道候选集**（R-01）；`src` 排序只决定“哪个始发仓先被匹对”；
- 即使把匹配顺序改为“时间→区域→类型”，类型 3~6 仍只扫描 2F/3F 巷道，**4F 仓位依旧不在候选集**，问题不变；
- 因此：**仅改排序顺序不能解决 4F 匹配问题**；排序改动只影响“公平性/优先级”语义，且需明确“时间”方向（见 §5 可选优化）。

---

## 3. 问题二专项说明（匹配顺序：时间→区域→类型）

| 项 | 结论 |
|---|---|
| 能否解决 4F 匹配 | **不能**（根因在目的侧 type_rules，不在始发侧排序） |
| 时间方向 | 需明确：先绑定先服务（bind_time 升序）或新绑定优先（当前实现按区域升序、bind_time 新者优先为次键，batch_matcher.py:199） |
| 建议 | 若仅为公平性，可作为可选开关（`sort_order`），默认保持现状，不作为修复 4F 的手段 |

---

## 4. 解决思路与技术方案

### 4.1 方案 A（推荐）：配置修复 + 代码类型过滤（双修）

**① 配置修复（status_poller.yaml `type_rules`）**：为类型 2~6 追加 `4F-L1`（原巷道在前、4F 补位在后）：

```yaml
type_rules:
  1: { lanes: [2F-L1, 4F-L1], strategy: fifo }
  2: { lanes: [2F-L2, 4F-L1], strategy: fifo }
  3: { lanes: [2F-L3, 4F-L1], strategy: fifo }
  4: { lanes: [3F-L1, 4F-L1], strategy: fifo }
  5: { lanes: [3F-L2, 4F-L1], strategy: fifo }
  6: { lanes: [3F-L3, 4F-L1], strategy: fifo }
```

> 语义：2F/3F 对应巷道满后回退到 4F-L1 中**同类型**仓位（T4001~T4006 按类型对应）。

**② 代码修复（dest_bay_cache.py 巷道内选位按类型过滤）**：

```python
# select_by_strategy 未启用 lane_state_management 分支（dest_bay_cache.py:347-349）
empty = [i for i, b in enumerate(lane.bay_ids)
         if b in self._bays and self._bays[b].is_empty
         and self._bays[b].cargo_type == cargo_type      # ★ 按类型过滤
         and b not in exclude]

# _max_occupied_next_slot 启用分支：候选空位同样按类型过滤（dest_bay_cache.py:322-330）
for nxt in range(max_occ + 1, len(lane.bay_ids)):
    b = lane.bay_ids[nxt]
    if (b in self._bays and self._bays[b].is_empty
            and self._bays[b].cargo_type == cargo_type):  # ★ 按类型过滤
        return nxt
```

**③ 兜底校验（batch_matcher.py greedy_scan_type）**：select 结果类型不匹配时跳过（防混合巷道错配）：

```python
dst_bay = self._dest_cache.select_by_strategy(cargo_type, src_bay=src_bay, exclude=used_dst_set)
if not dst_bay or dst_bay in used_dst_set:
    continue
# ★ 防御：目的仓类型必须与货物类型一致
st = self._dest_cache.get_bay_status(dst_bay)
if not st or st.get('cargo_type') != cargo_type:
    continue
```

> 说明：`lane_state_management=true`（最大占用 n→n+1 连续模型）对 4F 混合巷道语义复杂（不同类型混放破坏“连续占用”假设）；建议现场在 4F 混巷场景保持 `lane_state_management=false`，启用场景按 ② 的类型过滤实现。

### 4.2 方案 B（备选，不改代码）：拆分 4F 为单类型巷道

- 把 4F-L1 拆为 6 条单类型巷道（每巷 1 仓），`type_rules` 各类型 lanes 指向对应巷道；
- 缺点：破坏 4F 巷道顺序语义、配置面大、每巷单仓易满；**不推荐**。

### 4.3 可选优化：匹配顺序开关（时间→区域→类型）

若需改变公平性，新增配置（默认关闭，保持现状）：

```yaml
# smart_trigger.yaml（可选）
sort_order: "time_region_type"   # 默认 by_type_region（现状）；time_region_type=时间(先绑定优先)→区域→类型
```

实现：`batch_scan_all` 生成全部候选后，按配置全局排序：
- `by_type_region`（现状）：`candidate.key(cargo_priority)`；
- `time_region_type`：`(bind_time, src 区域/编号, type_rank)`。

> 明确：该开关**不能解决 4F 匹配**（须配合方案 A）；仅改变“谁先被匹对”的公平性。

## 5. 测试与验收

1. **单元测试**：
   - 配置修复后：类型 3 有货且 2F-L3 满 → 4F-L1 中 T4003 被匹配；
   - 类型过滤：4F-L1 全空时类型 3 任务不得选中 T4001（类型1）；类型 1 任务不得选中 T4003；
   - 兜底校验：select 返回错误类型时跳过并继续下一巷道；
   - 排序开关：`time_region_type` 下候选按先绑定优先排序（仅公平性验证）；
2. **回归**：既有触发测试（test_trigger_yaml_config / ghost_lock）通过；
3. **板端**：类型 2~6 有货时 2F/3F 满仓后 4F 对应类型仓位正常变橙并派发；无跨类型错配；前端四色状态正确。

---

## 6. 兼容性与回滚

- 配置修复（type_rules 加 4F-L1）为现场参数调整，可随时改回；
- 代码修复（类型过滤 + 兜底校验）为防御性增强，不改变现有 2F/3F 单类型巷道行为；
- 排序开关默认关闭，行为与现状一致；
- 全部改动可独立回滚。

---

## 7. 结论

1. **根因**：`type_rules` 白名单未把 4F-L1 纳入类型 2~6（R-01），导致 T4002~T4006 永不进入候选巷道；同时巷道内选位无类型过滤（R-02），仅改配置会引发跨类型错配；
2. **排序顺序（时间→区域→类型）不能解决 4F 匹配**（R-03），只能作为公平性可选项；
3. **推荐方案**：配置为类型 2~6 追加 `4F-L1` + 巷道内选位按 `cargo_type` 过滤 + 匹配结果兜底校验；建议按 §4.1 实施并配套 §5 测试。
