## 1. P0-1：manual_intervention 语义冲突修复

### 1.1 根因回顾

`config/workflows/agv_transport_atomic.yaml` 中 `manual_intervention` 声明了 `final: true`，却又定义了 `user_retry / user_cancel / auto_resolved / auto_failed` 转移。而 `WorkflowInstance.run()` 的主循环条件是 `while not is_final_state(current_state)`，因此：

1. 进入 manual_intervention 后主循环立即退出，`_status` 被无条件置为 `COMPLETED`（instance.py:116）；
2. `WorkflowEngine._run_instance()` 的 finally 把实例从 `engine._instances` 弹出；
3. 实例弹出后，`task_monitor` 的自动闭环注入（`auto_resolved/auto_failed`）、`/task_control` 的 retry/cancel 均因“实例不存在”而失效；
4. manual_intervention 的 `on_enter`（log_manual_entry / publish_manual_event）因为循环已退出而从未执行，`manual_entered_at` 不落库，10 分钟告警升级失效；
5. 事件注入进队列后无人消费，全部滞留。

### 1.2 修复思路（方案 A，推荐）

把 manual_intervention 从“终态”改为**非终态的挂起态**：

- 实例进入后主循环继续运行，实例保留在引擎中，事件队列持续被消费；
- `on_enter` 正常执行（记录人工介入时间戳、发布人工介入事件）；
- `action: wait_for_completion` + `timeout: 0` 实现无限等待外部事件；
- `user_retry → calling_rcs`、`user_cancel → failed`、`auto_resolved → auto_recovery`、`auto_failed → failed` 全部可达；
- 人工处置期间 RCS 直接回执（`callback_completed/callback_exception`）也能闭环，避免事件滞留；
- 配套修正：
  - 终态状态码按终态类型区分（failed ≠ completed），失败任务正确发布 `task_failed` 并触发资源释放；
  - 恢复口径包含 `MANUAL` 状态（重启后人工任务继续被监控）；
  - 恢复校准支持 manual_intervention 行，并修正其查询参数 bug（当前误用 `task_id` 查询，应为 `rcs_task_no`）；
  - `monitoring/warn_pause` 增加 `user_cancel` 转移，使取消语义确定化。

> 方案 B（备选）：把 manual_intervention 保留为真终态，由 task_monitor 作为外部守护，直接通过持久化 + 引擎公开 API 完结/重跑，不再依赖事件注入。该方案改动更大，且会引入“引擎外改状态”的一致性问题，不推荐作为首选。

### 1.3 修复后的状态机

```
monitoring ──callback_exception(L2/L3)──▶ manual_intervention（挂起态，非终态）
compensating_query ──rcs_failed/超时──▶          │
run() 未知事件兜底 ──────────────────────────────┤
                                                 │ on_enter: log_manual_entry / publish_manual_event
                                                 │ action: wait_for_completion (timeout=0 无限等待)
                                                 ├──user_retry──────────▶ calling_rcs
                                                 ├──user_cancel─────────▶ failed
                                                 ├──auto_resolved───────▶ auto_recovery ──release──▶ completed
                                                 ├──auto_failed─────────▶ failed
                                                 ├──callback_completed──▶ auto_recovery
                                                 └──callback_exception──▶ failed
```

#### 步骤 3：引擎按实例终态分发回调

文件：`app_mgr_object/components/workflow/engine.py`

3a. 导入 `WorkflowInstanceStatus`：

```python

```

3b. `_run_instance()` 在 `run()` 正常返回后按实例终态分发（失败走 `on_instance_failed`，不再重复发 `on_instance_completed`）：

```python
    async def _run_instance(self, instance: WorkflowInstance):
        """在协程中执行实例（带并发控制）"""
        self._logger.info(f"[Engine] _run_instance 开始: {instance.id}")
        async with self._semaphore:
            self._logger.info(f"[Engine] _run_instance 获取信号量: {instance.id}")
            try:
                if self.on_instance_started:
                    self._logger.debug(f"[Engine] 调用 on_instance_started: {instance.id}")
                    self.on_instance_started(instance)
                self._logger.info(f"[Engine] 即将调用 instance.run(): {instance.id}")
                await instance.run()

                # run() 正常返回后，按实例终态分发回调：
                # - failed 终态走 on_instance_failed（发布 task_failed / 触发资源释放）
                # - 其余终态走 on_instance_completed
                if instance.status == WorkflowInstanceStatus.FAILED:
                    if self.on_instance_failed:
                        self.on_instance_failed(instance, None)

            except Exception as e:
                self._logger.error(f"[Engine] _run_instance 捕获异常: {e}")
                import traceback
                self._logger.error(traceback.format_exc())

                if self.on_instance_failed:
                    self.on_instance_failed(instance, e)
            finally:
                # 失败终态不重复发布 task_completed，避免下游重复处理
                if (self.on_instance_completed
                        and instance.status != WorkflowInstanceStatus.FAILED):
                    self.on_instance_completed(instance)
                self._instances.pop(instance.id, None)
```

> 行为影响：修复前 failed 终态只触发 `on_instance_completed`（发布 `workflow.task_completed`）；修复后 failed 触发 `on_instance_failed`（发布 `workflow.task_failed`），smart_trigger 的 `_on_task_failed` 会释放资源，语义正确。

#### 步骤 6：人工介入动作保护（时间戳仅首次写入）

```python
    async def _action_log_manual_entry(self, context: dict, instance) -> str:
        """记录进入 manual_intervention 的时间戳 + 触发原因（仅首次写入）"""
        import time
        if 'manual_entered_at' not in context:
            context['manual_entered_at'] = time.time()
        if 'manual_trigger_event' not in context:
            context['manual_trigger_event'] = context.get('_last_event', 'unknown')

        self.logger.warning(
            f"任务进入人工介入: {context.get('task_id')} "
            f"触发事件={context['manual_trigger_event']}, "
            f"时间戳={context['manual_entered_at']}"
        )

        # 记录异常日志
        try:
            self._engine._persistence.log_exception(
                context.get('task_id', ''),
                'manual_intervention',
                f"trigger={context['manual_trigger_event']}"
            )
        except Exception:
            pass

        return 'done'
```

> 该保护与 instance.py 的 `continue` 配合：未知事件导致挂起态重新进入时，不会重置 `manual_entered_at`，10 分钟告警升级计时保持连续。

### 1.5 P0-1 验收要点

- `manual_intervention` 不再是终态：进入后 `engine.get_instance(task_id)` 仍返回实例，`instance.status == running`；
- `/task_control retry` 可把任务从 manual_intervention 拉回 calling_rcs 重新下发；
- task_monitor 注入 `auto_resolved` 后任务经 auto_recovery（释放资源）到达 completed，DB 状态 SUCCESS；
- 注入 `auto_failed` / `user_cancel` 后任务到达 failed，DB 状态 FAILED，且发布 `workflow.task_failed` 触发资源释放；
- 重启进程后，MANUAL 状态任务被恢复并继续被轮询监控。

## 2. P0-2：wait_for_completion 事件透传修复

### 2.1 根因回顾

`workflow_engine_plugin._action_wait_for_completion()` 只识别 `callback_completed` 与 `callback_exception`，其余事件（含 `warn_l1`、`warn_info`、`user_cancel`、`user_retry`、`auto_resolved` 等）一律返回 `callback_exception`。这导致：

- `monitoring` 收到 L1 告警 `warn_l1` 时，实际转移事件是 `callback_exception` → 直接进 manual_intervention，`warn_pause` 分支不可达；
- 任何自定义事件都无法被 YAML 转移表消费。

### 2.2 修复思路

Action 是“事件消费者”，不应承担“事件解释器”的职责。改为**原样透传事件名**，状态转移完全交给 YAML `transitions` 表；Action 仅在事件消费异常时返回 `callback_exception`。

### 2.3 详细代码

文件：`app_mgr_object/plugins/workflow_engine_plugin.py`

```python
    async def _action_wait_for_completion(self, context: dict, instance) -> str:
        """挂起等待外部事件（RCS 回调 / 告警事件 / 人工操作事件）

        注意：本 Action 将事件名【原样透传】返回，由 YAML 状态转移表决定
        下一状态（callback_completed / callback_exception / warn_l1 /
        warn_info / user_retry / user_cancel / auto_resolved / auto_failed 等）。
        不要把未知事件统一映射为 callback_exception，否则 L1 告警暂停
        分支（warn_pause）与人工介入恢复永远不可达。
        """
        task_id = context.get('task_id', 'unknown')
        self.logger.info(f"[Action] 进入等待模式: {task_id}")

        try:
            # 等待 instance 的 event_queue 中的事件（由 event_bridge 注入）
            msg = await instance._event_queue.get()
            event = msg.get('event', '')
            data = msg.get('data', {})
            self.logger.info(f"[Action] 收到事件: {event}, task={task_id}")

            # 原样透传事件名，匹配交由 YAML transitions 处理
            return event

        except Exception as e:
            self.logger.error(f"[Action] 等待回调异常: {e}", exc_info=True)
            return 'callback_exception'
```

### 2.4 验收要点

- 对 monitoring 注入 `warn_l1`：任务进入 `warn_pause`，60s 无新事件后自动回 `monitoring`；
- 对 warn_pause 注入 `callback_completed`：进入 `releasing` 完成；
- 对 manual_intervention 注入 `user_retry`：进入 `calling_rcs`（与 P0-1 联动验收）。

## 3. P0-3：smart_trigger 周期扫描循环修复

### 3.1 根因回顾

`SmartTriggerPlugin._activate_impl()` 在 `AppMgrNode.__init__` 的主线程中执行：

```python
loop = asyncio.get_event_loop()
self._scan_task = loop.create_task(self._scan_loop())
```

此时主线程没有运行中的事件循环（真正的循环是 `node.asyncio_loop`，运行在独立线程），`get_event_loop()` 返回一个**从未 `run_forever` 的临时循环**，`_scan_loop()` 任务永远得不到调度。结果：周期扫描（每 2s 批量匹配）从不执行，系统只能依赖 `bay.bound` 等事件触发的单次扫描兜底。

### 3.2 修复思路

所有异步任务统一挂在 `node.asyncio_loop` 上：

- 创建：`asyncio.run_coroutine_threadsafe` 提交一个“创建任务”协程，在循环内 `asyncio.create_task` 并把句柄保存到 `self._scan_task`；
- 取消：`loop.call_soon_threadsafe` 在循环线程内取消任务（`Task.cancel()` 线程不安全）。

### 3.3 详细代码

文件：`app_mgr_object/plugins/smart_trigger_plugin.py`

3a. `_activate_impl()` 中替换原 `loop = asyncio.get_event_loop()` 部分：

```python
        # === 创建任务队列 ===
        self._task_queue = TaskQueue(
            resource_locker=self._trigger_engine._locker,
            robot_cache=status_poller.robot_cache,
            bay_cache=bay_fusion.cache,
            logger=self.logger,
        )
        self.logger.info(f"任务队列已创建 (max_size={self._max_queue_size})")
        # ===========================

        # 在节点主事件循环（node.asyncio_loop）上创建扫描任务，
        # 避免绑定到当前线程从未运行的临时事件循环导致扫描永不执行。
        loop = self.node.asyncio_loop

        async def _spawn_scan_task():
            self._scan_task = asyncio.create_task(self._scan_loop())
            return self._scan_task

        spawn_future = asyncio.run_coroutine_threadsafe(_spawn_scan_task(), loop)

        def _on_spawned(fut):
            try:
                fut.result()
                self.logger.info("智能触发器扫描任务已创建（绑定主事件循环）")
            except Exception as e:
                self.logger.error(f"创建扫描任务失败: {e}")

        spawn_future.add_done_callback(_on_spawned)

        # 事件订阅
        self.event_bus.subscribe('bay.bound', self._on_bay_bound)
        self.event_bus.subscribe('workflow.task_completed', self._on_task_completed)
        self.event_bus.subscribe('workflow.task_failed', self._on_task_failed)
        self.event_bus.subscribe('workflow.resources_released', self._on_resources_released)

        self._running = True
        self.logger.info(f"SmartTrigger v3 激活完成 (队列模式)")
        return True
```

3b. `_deactivate_impl()` 线程安全取消扫描任务：

```python
    def _deactivate_impl(self) -> bool:
        self._running = False
        loop = getattr(self.node, 'asyncio_loop', None)
        if self._scan_task and loop and not loop.is_closed():
            def _cancel():
                if not self._scan_task.done():
                    self._scan_task.cancel()
            loop.call_soon_threadsafe(_cancel)
            self._scan_task = None
        return True
```

3c. 顺带修复同类隐患：`workflow_engine_plugin.cancel_task()` 中 `asyncio.ensure_future` 在无运行循环的线程中会绑定错误循环：

```python
    def cancel_task(self, task_id: str):
        """Web 手动取消任务（在节点主事件循环中执行）"""
        if self._engine and getattr(self, '_loop', None):
            asyncio.run_coroutine_threadsafe(
                self._engine.cancel_instance(task_id), self._loop
            )
```

### 3.4 验收要点

- 启动后日志出现“智能触发器扫描任务已创建（绑定主事件循环）”；
- 每 2s 出现“扫描循环”相关日志 / `scan_count` 持续增长（此前无周期扫描日志）；
- 停机（Ctrl+C）无 `Task was destroyed but it is pending` 告警。

## 4. P1-1：同步阻塞 IO 移出 asyncio 循环

### 4.1 根因回顾

工作流 Action（`_action_invoke_gen_task`、`_action_compensate_query`）以及恢复校准 `_validate_and_recover` 直接在 asyncio 协程内调用 `requests` 同步 HTTP（RCS 接口，超时可达 10s）。事件循环被阻塞期间，所有工作流实例的调度、定时器与事件注入全部停摆。

### 4.2 修复思路

- 对协程内同步 IO，统一用 `asyncio.to_thread`（Python 3.9+；ROS2 Humble 为 3.10，可用）移入默认线程池；
- 轮询类插件（status_poller / task_status_monitor）运行在 ROS2 `MultiThreadedExecutor` 线程而非 asyncio 循环，阻塞影响有限，列为可选优化；
- 长期方向：将 `RCSHttpClient` 改为 aiohttp 异步实现，彻底去掉线程池往返。

### 4.3 详细代码

文件：`app_mgr_object/plugins/workflow_engine_plugin.py`

4a. `_action_invoke_gen_task()` 中的 RCS 调用改为线程池执行：

```python
        try:
            rcs = self._get_rcs_adapter()
            self.logger.info(f"[Action] 获取 RCS 适配器成功")

            # 同步 HTTP 调用放入线程池，避免阻塞 asyncio 事件循环
            resp = await asyncio.to_thread(rcs.gen_task, context)
            self.logger.info(f"[Action] RCS 响应: {resp}")

            if resp.get('code') == '0':
                rcs_task_no = resp.get('data', {}).get('taskNo', '')
                if rcs_task_no:
                    context['rcs_task_no'] = rcs_task_no

                self.logger.info(f"任务下发成功: {context['task_id']} → RCS taskNo={rcs_task_no}")
                return 'rcs_ack_ok'
            else:
                self.logger.error(f"任务下发失败: {resp.get('msg', '未知错误')}")
                # === 记录异常日志 ===
                try:
                    import json
                    self._engine._persistence.log_exception(
                        context.get('task_id', ''),
                        'gen_task_failed',
                        json.dumps({
                            'rcs_code': resp.get('code', ''),
                            'rcs_msg': resp.get('msg', ''),
                            'src_bay': context.get('src_bay', ''),
                            'dst_bay': context.get('dst_bay', ''),
                        })
                    )
                except Exception:
                    pass
                # ===========================
                return 'rcs_ack_fail'

        except Exception as e:
            self.logger.error(f"[Action] invoke_gen_task 异常: {e}", exc_info=True)
            return 'rcs_ack_fail'
```

4b. `_action_compensate_query()` 中的 RCS 查询改为线程池执行：

```python
        try:
            rcs = self._get_rcs_adapter()
            resp = await asyncio.to_thread(rcs.query_task_status, [rcs_task_no])

            if resp.get('code') != '0':
                return 'rcs_running'

            data_list = resp.get('data', [])
            if not data_list:
                return 'rcs_running'

            task_status = str(data_list[0].get('taskStatus', ''))

            if task_status == '9':
                self.logger.info(f"补偿查询确认完成: {context['task_id']}")
                return 'rcs_completed'
            elif task_status in ('7', '8'):
                self.logger.warning(f"补偿查询确认失败: {context['task_id']}")
                return 'rcs_failed'
            else:
                self.logger.info(f"补偿查询: 任务仍在执行: {context['task_id']}")
                return 'rcs_running'

        except Exception as e:
            self.logger.error(f"补偿查询异常: {e}")
            return 'rcs_running'
```

4c. `_validate_and_recover()` 中的校准查询同样改为线程池执行（见 1.4 步骤 5b）：

```python
                # 同步 HTTP 调用移入线程池，避免阻塞 asyncio 事件循环
                resp = await asyncio.to_thread(rcs.query_task_status, [rcs_task_no])
```

### 4.4 注意事项

- `asyncio.to_thread` 不提供超时取消线程的能力：`asyncio.wait_for` 超时后线程仍会在后台跑完。建议 RCS 客户端自身超时（当前 `rcs_timeout=10s`）保持收敛；
- `requests.Session` 线程安全：to_thread 并发后，同一 Session 可能被多线程同时使用。简单场景可用（连接池由 requests 管理），若要并发压测建议按线程建会话或迁移 aiohttp；
- 可选优化：`task_status_monitor._poll_once`、`status_poller` 的定时轮询若希望不占用 ROS 执行器线程，可包一层 `concurrent.futures.ThreadPoolExecutor` 提交；当前多线程执行器下非必须，先不纳入本批修复。

### 4.5 验收要点

- 工作流 action 执行期间（RCS 响应前），其他工作流实例仍可正常转移（用两个并发任务 + RCS 模拟器验证）；
- 单个 RCS 查询超时（模拟 10s 无响应）不会导致整体事件循环卡死；
- 补偿查询、恢复校准仍返回正确事件/状态。
