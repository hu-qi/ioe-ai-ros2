## 1. 根因分析

### 1.1 问题复现路径

```
系统重启
  │
  ▼
WorkflowEngine.recover_all()
  ├─ 从 SQLite 读回 TASK_1785570635_1 (state=monitoring)
  ├─ 创建实例, 立即 asyncio.create_task(_run_instance(...))
  │
  ▼
instance.run() → monitoring (state_def.action='wait_for_completion')
  │
  ├─ _execute_with_timeout: asyncio.wait_for(wait_for_completion, timeout=100s)
  │   └─ wait_for_completion 返回 'waiting' (挂起信号)
  │
  ├─ 100s 后 → asyncio.TimeoutError → 返回 'timeout'
  │
  ├─ YAML 转移: "timeout" → "compensating_query"
  │
  ▼
compensating_query (state_def.action='compensate_query')
  │
  ├─ compensate_query:
  │   ├─ POST /queryTaskStatus → taskStatus='2' (RUNNING)
  │   └─ 返回 'rcs_running'
  │
  ├─ YAML 转移: "rcs_running" → "monitoring"   ← ⚠ 问题点!
  │
  ▼
monitoring (再次进入, 100s timeout)
  │
  ├─ 100s 后超时 → compensating_query
  │   └─ 返回 'rcs_running' → monitoring (第 2 轮)
  │
  ├─ 100s 后超时 → compensating_query
  │   └─ 返回 'rcs_running' → monitoring (第 3 轮)
  │
  └─ ... 无限循环, 永不终结
```

### 1.2 两个根因

| 编号 | 根因 | 位置 | 严重度 |
|:---|:---|:---|:---|
| **R1** | `compensating_query.rcs_running → monitoring` 形成无限循环，无次数限制 | `agv_transport_atomic.yaml` L59 | 🔴 致命 |
| **R2** | `recover_all()` 未校验 RCS 任务实际状态，实例在 `monitoring` 直接恢复等待 | `engine.py:recover_all()` | 🔴 致命 |

### 1.3 R1 深入分析

当前 YAML 的 `compensating_query` 状态转移:

```yaml
compensating_query:
  transitions:
    - event: "rcs_completed"    # ← RCS 返回 9 → 正常结束
      target: "releasing"
    - event: "rcs_failed"       # ← RCS 返回 7/8 → 人工介入
      target: "manual_intervention"
    - event: "rcs_running"      # ← ⚠ RCS 返回 2 → 回到 monitoring!
      target: "monitoring"
    - event: "timeout"          # ← 查询本身超时
      target: "manual_intervention"
```

**问题**: 当 RCS 任务永远卡在 `RUNNING(2)` 状态（例如 AGV 故障但未上报、RCS 异常），`compensate_query` 持久返回 `'rcs_running'`，实例在 `monitoring → compensating_query → monitoring` 之间无限振荡。

**码级原因**: `_action_compensate_query()` 中，所有非 `9`/`7`/`8` 的状态码都返回 `'rcs_running'`，没有任何计数器或上限。

### 1.4 R2 深入分析

当前 `recover_all()` 实现:

```python
async def recover_all(self) -> int:
    rows = self._persistence.get_incomplete_instances()
    for row in rows:
        context = self._deserialize_context(row.get('context_blob'))
        instance = self._create_instance_obj(...)
        instance.current_state = row.get('current_state', ...)
        self._instances[instance.id] = instance
        asyncio.create_task(self._run_instance(instance))  # ← 直接启动!
```

**问题**:
1. 不检查 `rcs_task_no` 是否仍然有效
2. 不查询 RCS 该任务的当前实际状态
3. 如果 RCS 侧已完成但回调丢失 → 实例永远等待
4. 如果 RCS 侧已失败/取消 → 实例仍然等待 100s 再补偿查询

**场景**: 系统在任务 `TASK_xxx` 执行中崩溃，RCS 侧任务继续执行并完成（回调在系统离线期间丢失）。重启后实例以 `monitoring` 状态恢复，但 RCS 已无该任务，`queryTaskStatus` 可能返回空数据或终态 — 但当前代码不会在恢复时调用 `queryTaskStatus`。

## 3. 修复 1: 补偿循环计数器 — 打破无限循环

### 3.1 设计思路

在 `WorkflowInstance` 中增加 `compensate_cycle_count` 计数器。每次从 `compensating_query` 因 `rcs_running` 回到 `monitoring` 时自增。在 `compensate_query` Action 中检查计数器，达到上限后返回 `max_retry_reached`（而非 `rcs_running`），使状态机进入 `manual_intervention`。

```
状态流（修复后）:

monitoring (100s)
  │ timeout
  ▼
compensating_query
  ├─ compensate_cycle_count=0 → rcs_running → monitoring (第 1 轮)
  │   100s timeout
  ▼
compensating_query
  ├─ compensate_cycle_count=1 → rcs_running → monitoring (第 2 轮)
  │   100s timeout
  ▼
compensating_query
  ├─ compensate_cycle_count=2 → max_retry_reached → manual_intervention ✓
```

### 3.2 代码修改

#### 3.2.1 `components/workflow/instance.py` — 增加计数器

在 `__init__` 中增加（约第 84 行 `self._event_queue` 之后）:

```python
# ====== 新增: 补偿循环计数器 ======
# 每次从 compensating_query (rcs_running) 回到 monitoring 时自增
# 达到 MAX_COMPENSATE_CYCLES 后强制转入 manual_intervention
self.compensate_cycle_count: int = 0
self.MAX_COMPENSATE_CYCLES: int = 3
# ==================================

# 增量修改: 在 _transition_to 方法中，当目标状态是 monitoring 且当前状态
# 是 compensating_query 时，自动递增计数器
```

在 `_transition_to` 方法中增加检测逻辑（约第 133 行）:

```python
async def _transition_to(self, state_id: str):
    """执行状态转移"""
    old_state = self.current_state

    # ====== 新增: 补偿循环检测 ======
    if old_state == 'compensating_query' and state_id == 'monitoring':
        self.compensate_cycle_count += 1
        self._log_warning(
            f"补偿循环 #{self.compensate_cycle_count}: "
            f"{old_state} → {state_id} "
            f"(max={self.MAX_COMPENSATE_CYCLES})"
        )
        if self.compensate_cycle_count >= self.MAX_COMPENSATE_CYCLES:
            self._log_error(
                f"补偿循环已达上限 {self.MAX_COMPENSATE_CYCLES} 次, "
                f"强制转入 manual_intervention"
            )
            state_id = 'manual_intervention'  # 改写目标状态
    # ====================================

    # 执行 on_exit 动作
    old_def = self.definition.get_state(old_state)
    if old_def:
        for action_name in old_def.on_exit:
            await self._execute_action(action_name)

    self.current_state = state_id
    self._retry_count = 0
    self._log_debug(f"状态转移: {old_state} → {state_id}")

    # 持久化
    self._persistence.save(self)

    # 回调通知
    if self.on_state_changed:
        try:
            self.on_state_changed(state_id)
        except Exception:
            pass
```

## 4. 修复 2: 恢复前 RCS 状态校准 — 消除悬挂实例

### 4.1 设计思路

在 `_activate_impl()` 中调用 `recover_all()` 之前，增加一个 `_validate_recovered_instances()` 步骤：

1. 从 SQLite 读回所有未完成实例
2. 对每个处于 `monitoring` 或 `compensating_query` 状态的实例:
   a. 提取 `rcs_task_no`
   b. 通过 `rcs_adapter.query_task_status()` 查询 RCS 实际状态
   c. 根据 RCS 返回的状态码决定:
      - `9` (已完成) → 直接写入 `completed` 到 DB，不入引擎
      - `7`/`8` (失败/取消) → 写入 `failed` 到 DB，不入引擎
      - `2` (执行中) → 正常恢复进入 `monitoring`
      - 查询失败/任务不存在 → 写入 `manual_intervention` 到 DB

### 4.2 代码修改

#### 4.2.1 `plugins/workflow_engine_plugin.py` — `_activate_impl` 增加校准步骤

```python
def _activate_impl(self) -> bool:
    """激活：恢复实例 + 连接 EventBus + 订阅事件"""
    self._loop = self.node.asyncio_loop

    # ====== 新增: 恢复前 RCS 状态校准 ======
    asyncio.run_coroutine_threadsafe(
        self._validate_and_recover(), self._loop
    )
    # ======================================

    # 2. 连接 EventBus → Engine 事件桥
    self._event_bridge.connect(self._engine, self.event_bus, self._loop)
    self._event_bridge.subscribe_rcs_events()

    # 3. 订阅 trigger.task_created 事件
    self.event_bus.subscribe('trigger.task_created', self._on_trigger_task_created)

    self._running = True
    self.logger.info("WorkflowEngine 激活完成")
    return True
```

#### 4.2.2 `plugins/workflow_engine_plugin.py` — 新增 `_validate_and_recover` 方法

在 `_activate_impl` 方法之后添加:

```python
async def _validate_and_recover(self):
    """
    恢复前校验: 对每个历史实例查询 RCS 实际状态，消除悬挂任务

    逻辑:
      - RCS 返回 COMPLETED(9) → 直接完结, 不入引擎
      - RCS 返回 FAILED(7)/CANCELLED(8) → 标记失败, 不入引擎
      - RCS 返回 RUNNING(2) → 正常恢复进入引擎
      - RCS 无响应/任务不存在 → 标记人工介入
    """
    rows = self._engine._persistence.get_incomplete_instances()
    if not rows:
        self.logger.info("无历史未完成实例，跳过校准")
        await self._engine.recover_all()
        return

    self.logger.info(f"发现 {len(rows)} 个历史未完成实例，开始 RCS 状态校准...")

    # 收集所有具有 rcs_task_no 且在等待状态的实例
    instances_to_validate = []
    instances_no_rcs = []

    for row in rows:
        context = self._engine._deserialize_context(row.get('context_blob', None))
        current_state = row.get('current_state', '')
        rcs_task_no = context.get('rcs_task_no', '')

        if current_state in ('monitoring', 'compensating_query'):
            if rcs_task_no:
                instances_to_validate.append({
                    'row': row,
                    'context': context,
                    'rcs_task_no': rcs_task_no,
                })
            else:
                instances_no_rcs.append(row)
        else:
            # calling_rcs / releasing 等状态直接恢复
            instances_no_rcs.append(row)

    # 对可校验实例逐个查询 RCS
    recovered_count = 0
    resolved_count = 0

    for item in instances_to_validate:
        task_id = item['row']['task_id']
        rcs_task_no = item['rcs_task_no']

        try:
            rcs = self._get_rcs_adapter()
            if rcs is None:
                self.logger.warning(f"RCS 适配器未就绪，{task_id} 直接恢复")
                instances_no_rcs.append(item['row'])
                continue

            resp = rcs.query_task_status([task_id])

            if resp.get('code') != '0' or not resp.get('data'):
                self.logger.warning(
                    f"RCS queryTaskStatus 异常/无数据: {task_id}, "
                    f"标记为人工介入"
                )
                self._engine._persistence.update_state(task_id, 'manual_intervention')
                resolved_count += 1
                continue

            rcs_status = str(resp['data'][0].get('taskStatus', ''))

            if rcs_status == '9':
                # RCS 已完成 → 直接完结
                self.logger.info(f"[恢复校准] {task_id}: RCS 已完成(9), 直接完结")
                self._engine._persistence.update_state(task_id, 'completed')
                resolved_count += 1

            elif rcs_status in ('7', '8'):
                # RCS 已失败/取消 → 标记失败
                self.logger.warning(
                    f"[恢复校准] {task_id}: RCS 状态={rcs_status}, 标记失败"
                )
                self._engine._persistence.update_state(task_id, 'failed')
                resolved_count += 1

            elif rcs_status == '2':
                # RCS 仍在执行 → 正常恢复
                self.logger.info(
                    f"[恢复校准] {task_id}: RCS 仍在执行(2), 恢复正常监控"
                )
                instances_no_rcs.append(item['row'])

            else:
                # 未知状态 → 保守处理, 恢复监控
                self.logger.warning(
                    f"[恢复校准] {task_id}: RCS 返回未知状态 {rcs_status}, "
                    f"保守恢复监控"
                )
                instances_no_rcs.append(item['row'])

        except Exception as e:
            self.logger.error(f"[恢复校准] {task_id} 校验异常: {e}, 保守恢复")
            instances_no_rcs.append(item['row'])

    # 正常恢复剩余实例
    self.logger.info(
        f"RCS 校准完成: 恢复 {len(instances_no_rcs)} 个实例, "
        f"直接完结 {resolved_count} 个实例"
    )

    for row in instances_no_rcs:
        try:
            definition = self._engine._definitions.get(
                row.get('workflow_name', '')
            )
            if not definition:
                self.logger.warning(f"工作流定义不存在: {row.get('workflow_name')}")
                continue

            context = self._engine._deserialize_context(
                row.get('context_blob')
            )
            instance = self._engine._create_instance_obj(
                row['task_id'], definition, context
            )
            instance.current_state = row.get(
                'current_state', definition.initial_state
            )
            self._engine._instances[instance.id] = instance
            asyncio.create_task(self._engine._run_instance(instance))
            recovered_count += 1
            self._engine._log_info(
                f"恢复实例: {instance.id} 状态={instance.current_state}"
            )

        except Exception as e:
            self._engine._log_error(
                f"恢复实例失败 {row.get('task_id')}: {e}"
            )

    self.logger.info(
        f"恢复流程完成: 成功恢复 {recovered_count}, "
        f"校准完结 {resolved_count}"
    )
```

### 4.3 移除原 `recover_all()` 的直接调用

由于 `_validate_and_recover()` 已包含恢复逻辑，`_activate_impl()` 不再直接调用 `self._engine.recover_all()`，避免重复恢复。

> **注意**: `WorkflowEngine.recover_all()` 方法**保留不变**，作为 `_validate_and_recover()` 内部调用的基础设施。如果未来有不需要校准的场景，仍可直接使用。

## 5. 修复 3: 无匹配事件时的兜底处理

### 5.1 问题

当前 `instance.py` 的 `run()` 方法中，当 `_wait_for_event` 或 `_execute_with_timeout` 返回的事件在 `state_def.transitions` 中无匹配时：

```python
event = await self._execute_with_timeout(state_def)  # 或 _wait_for_event
next_state = state_def.transitions.get(event)
if next_state:
    await self._transition_to(next_state)
else:
    self._log_warning(f"无匹配转移: state={self.current_state} event={event}")
    await self._transition_to('manual_intervention')  # ← 已有此兜底但需增强
```

此处的兜底逻辑已经存在，但 `manual_intervention` 在 YAML 中被定义为 `final: true`，这意味着 `is_final_state('manual_intervention')` 返回 `True`，循环会退出。

**验证**: 当前代码已有此处理，但需要确保 `manual_intervention` 的 `final: true` 标记正确（当前 YAML 中已存在）。

### 5.2 增强: 在兜底时额外记录上下文

```python
# 在 instance.py run() 方法中，无匹配转移处增强日志
else:
    self._log_warning(
        f"无匹配转移: state={self.current_state} event={event} "
        f"available_events={list(state_def.transitions.keys())}"
    )
    # 持久化当前心跳时间，便于运维诊断
    self.context['_last_unknown_event'] = event
    self.context['_last_state_before_fallback'] = self.current_state
    await self._transition_to('manual_intervention')
```

### 7.2 常见问题

| 问题 | 原因 | 解决 |
|:---|:---|:---|
| 恢复后实例仍悬挂 | RCS 不可达 → 校准失败 → 保守恢复 | 这是预期行为：保守策略避免误杀正常任务 |
| 补偿计数器提前触发 | 第 N 轮 rcs_running 触发上限 | 调整 `MAX_COMPENSATE_CYCLES` 值（instance.py） |
| 恢复后看到重复的 `completed` 事件 | RCS 已完成但之前回调也到达了 | 无影响，去重由 EventBus 订阅方处理 |
| `_validate_and_recover` 超时 | RCS 响应慢 | 增加 `rcs_adapter` 的 `rcs_timeout` 配置 |
