# AI智能教学分析平台（教官操作端）——商业应用差距分析与补齐路线（Agent 执行版）

> 编制日期：2026-09-12（v2，估算体系由"人天"改为"Agent 任务"，由 Agent 组织实现）
> 分析基线：当前工程（P1~P7 路线图全部交付，142 项存量测试零回退，Vue3 SPA 已上线 `/ui`）
> 对标对象：商业级教学分析 / 培训管理 SaaS 产品的通用能力标准（账号与安全、部署交付、数据治理、可运维性、可扩展性、商业化功能）
> 执行模式：**由编码 Agent（AtomCode）担任工程总协调**——负责任务拆解、并行分发、代码评审、集成回归；人只保留架构决策与批次验收。
> 文档用途：作为商用化立项排期与投入决策的输入材料。

## 二、差距清单（按商用阻塞程度分级，估算单位：Agent 任务）

### 估算口径说明

- **AT（Agent Task）**：一个可独立交付、自带测试、可交给子 Agent 在隔离上下文中完成的工程任务。单个 AT 的 Agent 执行墙钟约 **0.5~2 小时**（含自测与文档）；
- **墙钟**：按任务批次并行执行后的自然时间（日），取决于并行度与共享文件串行点，**与人数无关**；
- **人的参与**：仅两类——**决策**（拍板技术方案，分钟级～小时级）与**验收**（每批次结束评审 Agent 的交付报告 + 抽验，小时级）。

### 级别说明
- **P0（商用阻塞）**：不解决无法向真实客户交付 / 存在数据安全风险；
- **P1（商用必备）**：试点客户可用，但规模化推广前必须补齐；
- **P2（竞争力增强）**：影响售前竞争力与续费，可按客户节奏排期。

### P0-1 账号认证与角色权限（最大差距）

|---|---|---|
| 登录认证 | 账号密码 / SSO，会话管理，登录审计 | 无（免登录直进） |
| 角色权限 | 教官 / 管理员 / 观察者分级，页面与 API 双层鉴权 | 无 |
| 数据权限 | 教官只看本班级/本工种数据 | 无，全员可见全部数据 |

## 三、Agent 组织与执行模型（本路线的实现方式）

### 3.1 角色分工

| 角色 | 承担者 | 职责 |
|---|---|---|
| 总协调 Agent | AtomCode（主会话） | 差距→任务拆解、AT 分发与依赖编排、子 Agent 产出 diff 评审、共享文件合并、批次集成回归、交付报告 |
| 实现 Agent | 子 Agent（worker，隔离上下文） | 单个 AT 的编码 + 自测；**只能写入声明过的非重叠文件范围**（scope），防止互相覆盖 |
| 专项 Agent | 子 Agent（reviewer/tester 探查角色） | 安全审查、压测脚本执行、验收前独立复核 |
| 人 | 产品/技术负责人 | ① 决策点拍板（§五）；② 批次验收（看交付报告 + 抽验关键路径）；③ 现场类操作（真实端侧联调、证书申购等 Agent 无法触达项） |

### 3.2 执行循环（每个批次）

```
人拍板决策点（0.5h）
  → 总协调 Agent 拆解为 AT 清单 + scope 分配（自动）
  → 并行分发 worker 子 Agent（每 AT 一个，scope 不重叠）
  → 逐个 AT diff 评审（总协调，发现问题打回重做）
  → 共享文件合并（web_server.py / schema.sql 等串行点由总协调统一改）
  → 全量回归（142+新增 全绿才收口）
  → 输出批次交付报告 → 人验收（1~2h）
```

### 3.3 并行度与串行点约束

- **并行度上限 3~4**：受共享文件冲突约束——`web_server.py`、`reports_schema.sql`、`base.html` 是高频公共文件，涉及它们的 AT 由总协调串行处理或收口合并，其余 AT 全并行；
- **质量闸门**：每个 AT 交付必须附带新增测试；批次收口跑全量回归，不绿不合入（沿用仓库现有 pytest 惯例）；
- **上下文隔离**：每 AT 独立子 Agent 会话，携带精确文件清单与验收标准，避免长上下文漂移。

### 3.4 Agent 模式的边界（需要人/现场配合的项）

| 边界 | 处理 |
|---|---|
| 真实端侧联调（边缘设备在客户现场） | Agent 准备 mock 联调环境（既有 test/report_recv 30 项 + :8183 mock），真机联调由人执行、Agent 出联调脚本 |
| HTTPS 证书申购/域名/防火墙 | 现场操作，Agent 出操作手册 |
| 商务决策（license 模式、定价） | 人的决策点 |
| 压测的真实硬件边界 | Agent 生成压测方案与本机压测，客户硬件标定由人执行 |

## 四、补齐路线图（按 Agent 墙钟排期）

```
第 1 批（商用最小闭环）                       墙钟 ≈ 2~3 个工作日
  Day1   AT-101→(102|103|104 并行)→105→106   【前置：决策1 认证方案】
  Day1~2 AT-201~205 全并行 + AT-302~305 并行  【前置：决策3 license 是否做】
  Day2~3 AT-301 初始化向导（依赖 101/302）+ 批次回归 + 验收
第 2 批（试点客户打磨）                       墙钟 ≈ 2 个工作日
  Day4   AT-501~505 全并行 + AT-401/402 并行
  Day5   AT-403（依赖第 1 批鉴权骨架）+ AT-404 压测 + 批次回归 + 验收
  （观察期后另发 AT-506 旧版下线）
第 3 批（规模化推广前，择需）                 墙钟 ≈ 2~3 个工作日/次
  └─ P2 各 AT 按客户画像随选随发，无固定排期
```

**里程碑验收口径**：第 1 批完成 = 具备单客户商用交付条件；第 2 批完成 = 具备 3~5 家试点并行运维条件。

## 五、决策点与风险（开工前置）

| # | 决策/风险 | 建议 | 阻塞 |
|---|---|---|---|
| 1 | 认证方案：自建 JWT vs 对接客户 SSO/LDAP | 首版自建 JWT（内网场景），预留 OIDC 扩展位 | 阻塞 AT-101 |
| 2 | 数据库演进：SQLite vs PostgreSQL | ≤10 万报告 SQLite 足够；压测（AT-404）结论驱动 | 阻塞 AT-405 |
| 3 | license 控制是否需要 | 订阅制则 P0；买断可延后 | 阻塞 AT-304 |
| 4 | 证据清理误删风险 | dry-run 先行 + keep_forever 链路先验证 | AT-203 内置 |
| 5 | 多客户隔离深度（字段 vs 库） | 首版字段隔离；>10 客户或有合规要求切库隔离 | 阻塞 AT-403 |
| 6 | **Agent 协作风险：共享文件合并冲突** | 总协调串行收口 + 每批次全量回归兜底 | 执行期持续 |
| 7 | **Agent 能力边界：鉴权/加密属安全敏感改动** | 安全类 AT 强制独立 reviewer Agent 复核后再合入 | AT-101/201 执行期 |

## 七、结论

1. **业务功能层面已无商业差距**：合同定义的全部能力均已交付且测试兜底，这部分不必再投入；
2. **差距本质是"从交付物到产品"的鸿沟**：认证权限、数据安全合规、交付运维三项 P0 是商用硬门槛，Agent 组织下**约 3 个工作日墙钟可清零**；
3. **架构底座适配 Agent 并行改造**：插件化体系、YAML 规则驱动、全量 pytest 回归、模块边界清晰——天然适合按 AT 拆解、隔离 scope 并行实现；
4. **建议启动方式**：人拍板 §五决策 1/3 → 总协调 Agent（AtomCode）即下发第 1 批 16 个 AT，最短次日可进入批次验收；本报告作为商用化立项评审会输入材料。
