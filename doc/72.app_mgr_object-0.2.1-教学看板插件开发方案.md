## 1. 背景与目标

### 1.1 背景

需求说明.docx §3.4 明确"教学看板"为教官操作端的"驾驶舱"：一屏掌握教学全局，快速定位需要关注的重点。

教学看板是整个平台的**最终输出层**，汇聚 P0 学员档案、P1 报告数据、P2 统计诊断的结果，为教官提供可执行的教学决策支持。

P1 期已实现增量事件实时入库 + `report_progress` 表；P2 期已实现统计计算 + 4 类诊断规则。本插件负责**将这些数据汇聚到一屏看板，并支持实时刷新与下钻**。

### 1.2 目标

开发 `teaching_dashboard_plugin`，实现：

1. 今日概览看板（考试人数、平均得分、通过率、待辅导学员数）；
2. 高频错误点 TOP5（遗漏率/超时率/顺序错误率最高的 5 个步骤，支持下钻）；
3. 需关注的学员列表（退步预警、波动较大、薄弱环节突出的学员，可点击进入学员详情页）；
4. 实时进度展示（订阅中设备的当前操作进度，30s 刷新）；
5. 教学改进验证（对比调整前后的班级平均分、完成率变化）。

### 1.3 范围与边界

| 维度 | 本期 P3 | 不做 |
|---|---|---|
| 数据来源 | 直连 `reports` / `report_progress` / `diagnosis_results` 表读聚合 | 不通过 P2 统计插件 API 间接拿数据（同库直读） |
| 实时推送 | 复用现有 WebSocket 机制，订阅 `report.realtime_delta` 事件推送到前端 | 不自建 WebSocket 服务 |
| 前端渲染 | 复用现有 `base.html` 主题与图表组件（Chart.js）渲染看板 | 不做移动端适配（本期仅 PC/触屏） |
| 改进验证 | 按时间窗对比班级平均分/完成率变化 | 不做 A/B 测试框架（本期简单对比） |

> **关键决策**：本插件**直连 reports 系列表 + diagnosis_results 表读聚合**，不通过 P2 的 `report_analysis_plugin` API 间接调用。理由同 P2：同库跨插件读是既有惯例，统计是高频读操作，走 API 性能差。P2 统计插件负责**计算并写入 diagnosis_results 表**，P3 看板插件负责**读 diagnosis_results 表展示**，职责清晰分离。

```

    ├── reports / report_steps / report_substeps / report_events 表

    └── event_bus: report.received / report.realtime_delta

P2 report_analysis_plugin
    ├── analysis_cache 表（统计缓存）
    └── diagnosis_results 表（诊断结果）

    ├── dashboard_repo：直连上述表读聚合
    ├── WebSocket 推送：订阅 report.realtime_delta，推送到前端看板
    └── REST API /api/v1/dashboard/** 返回 JSON 看板数据
         ↓

```

### 2.3 与 P2 统计分析插件的协作

| 协作点 | 方式 |
|---|---|
| 诊断结果来源 | 本插件直连 `diagnosis_results` 表读，不调 P2 API |
| 统计数据来源 | 本插件直连 `analysis_cache` 表读缓存结果，若缓存失效则直连 `reports` 表实时计算 |
| 职责分离 | P2 负责"计算并写入"，P3 负责"读并展示"，避免看板插件承担计算逻辑 |

> **跨插件读库的合法性**：既有 `smart_trigger_plugin` 跨插件读 `task_cache` 数据做触发判断，本插件跨插件读 `diagnosis_results` / `analysis_cache` 表做看板展示，符合既有底座"同库跨插件读"的惯例。

## 3. 看板模块定义（对齐 .docx §3.4）

### 3.1 今日概览

**模块内容**（.docx §3.4）：

| 指标 | 计算口径 | 数据来源 |
|---|---|---|
| 今日考试人数 | `COUNT(DISTINCT student_id) WHERE DATE(ts_upload_ms) = today` | reports 表 |
| 今日平均得分 | `AVG(total_score) WHERE DATE(ts_upload_ms) = today` | reports 表 |
| 今日通过率 | `COUNT(total_score >= pass_threshold) / COUNT(*)` | reports 表 |
| 待辅导学员数 | `COUNT(DISTINCT student_id) WHERE diagnosis_type = 'student_regression'` | diagnosis_results 表 |

**API**：`GET /api/v1/dashboard/today_summary`

**响应 data**：

```json
{
  "exam_count": 28,
  "avg_score": 82.5,
  "pass_rate": 0.85,
  "pending_tutor_count": 3,
  "date": "2026-09-06"
}
```

### 3.2 高频错误点 TOP5

**模块内容**（.docx §3.4）：遗漏率/超时率/顺序错误率最高的 5 个步骤。

**计算口径**：

1. 对每个 step idx，计算综合错误得分：
   - 遗漏率 = `COUNT(report WHERE step.idx IN unexecuted) / COUNT(report)`
   - 超时率 = `COUNT(report WHERE substep.timeout=true AND substep.idx IN step) / COUNT(report)`
   - 顺序错误率 = （P2 算法，基于 INTERRUPT 事件）
2. 综合得分 = `遗漏率 × 0.4 + 超时率 × 0.4 + 顺序错误率 × 0.2`（权重可配置）；
3. 按综合得分降序，取 TOP5。

**API**：`GET /api/v1/dashboard/top_error_points?limit=5`

**响应 data**：

```json
{
  "points": [
    {
      "rank": 1, "step_idx": 5, "step_name": "装击针",
      "omission_rate": 0.35, "timeout_rate": 0.28,
      "sequence_error_rate": 0.15, "composite_score": 0.298
    }
  ]
}
```

**下钻能力**：点击某个错误点 → 调用 `GET /api/v1/analysis/step_duration?step_idx={idx}` 查看该步骤的全班用时分布与异常学员明细。

### 3.3 需关注的学员

**模块内容**（.docx §3.4）：退步预警、波动较大、薄弱环节突出的学员列表。

**数据来源**：`diagnosis_results` 表，筛选 `diagnosis_type = 'student_regression'` 的学员。

**补充逻辑**：

- "波动较大"：该学员最近 N 次报告 `total_score` 标准差 > 阈值（可配置，默认 15 分）；
- "薄弱环节突出"：该学员薄弱步骤 TOP3 综合得分 > 全班平均值的 1.5 倍。

**API**：`GET /api/v1/dashboard/attention_students`

**响应 data**：

```json
{
  "students": [
    {
      "student_id": "S2024003", "student_name": "王强", "cls": "机修二班",
      "reason": "student_regression", "detail": "最近3次平均分 65.2 < 前5次×0.85 (76.5×0.85=65.0)",
      "last_score": 62.0, "avg_score_recent": 65.2
    }
  ]
}
```

**闭环能力**：点击学员姓名 → 跳转 P0 学员详情页 `/students?id={student_id}`，形成"看板→诊断→个别辅导"闭环。

### 3.4 实时进度展示

**模块内容**：订阅中设备的当前操作进度，30s 刷新。

**数据来源**：`report_progress` 表（P1 期增量事件入库时写入）。

**API**：`GET /api/v1/dashboard/realtime_progress`

**响应 data**：

```json
{
  "devices": [
    {
      "device_id": "dev01", "student_name": "张明",
      "done": 12, "total": 19, "current": "装击针",
      "current_sub_index": 13, "process_elapsed_ms": 91000,
      "is_stub": true, "updated_at": 1788407910000
    }
  ]
}
```

**实时推送**：

1. P1 期 `report_recv_plugin` 收到增量事件后发布 `event_bus` 事件 `report.realtime_delta`；
2. 本插件订阅该事件，通过现有 `ConnectionManager.broadcast_json()` 推送到前端 WebSocket；
3. 前端 `dashboard.js` 收到推送后更新实时进度卡片。

### 3.5 教学改进验证

**模块内容**（.docx §5.4）：对比调整前后的班级平均分、完成率变化。

**计算口径**：

1. 教官选择两个时间窗：调整前（如 2026-08-01 ~ 2026-08-31）、调整后（如 2026-09-01 ~ 2026-09-30）；
2. 分别计算两个时间窗的班级平均分、完成率；
3. 展示变化趋势（上升/下降/持平）。

**API**：`GET /api/v1/dashboard/improvement_validation?cls=&before_start=&before_end=&after_start=&after_end=`

**响应 data**：

```json
{
  "before": {"avg_score": 75.2, "completion_rate": 0.78, "report_count": 45},
  "after": {"avg_score": 82.5, "completion_rate": 0.85, "report_count": 52},
  "delta": {"avg_score": 7.3, "completion_rate": 0.07},
  "trend": "improved"
}
```

## 6. 关键实现细节

### 6.1 实时进度推送链路

```
P1 report_recv_plugin
    ↓ event_bus.publish('report.realtime_delta', {device_id, round_start_ms, progress, events})
P3 teaching_dashboard_plugin
    ↓ _on_realtime_delta(data) 订阅事件
    ↓ ConnectionManager.broadcast_json({type: 'realtime_progress', data: ...})
前端 dashboard.js
    ↓ WebSocket onmessage
    ↓ 更新实时进度卡片 DOM
```

**复用既有机制**：web_server.py 已有 `ConnectionManager` 与 WebSocket 广播能力（参考现有 `/ws` 端点，doc/42）。本插件只需订阅 `event_bus` 事件并转发到 `ConnectionManager`，推送由 web 层统一处理。

### 6.2 看板数据刷新策略

| 模块 | 刷新方式 | 频率 |
|---|---|---|
| 今日概览 | 前端轮询 `GET /today_summary` | 30s |
| 高频错误点 TOP5 | 前端轮询 `GET /top_error_points` | 60s（变化较慢） |
| 需关注的学员 | 前端轮询 `GET /attention_students` | 60s |
| 实时进度 | WebSocket 推送（增量事件触发） | 实时（doc/45 `realtime_upload_sec` 默认 2s） |
| 教学改进验证 | 教官手动触发 | 按需 |

### 6.3 下钻链路

```
高频错误点 TOP5 → 点击某步骤
    ↓
GET /api/v1/analysis/step_duration?step_idx={idx}（P2 统计插件）
    ↓
展示该步骤的全班用时分布 + 异常学员明细
    ↓
点击某异常学员
    ↓
跳转 P0 学员详情页 /students?id={student_id}
```

### 6.4 闭环能力

需求说明.docx §5.2-5.3 强调"诊断→改进→验证"闭环，本看板插件提供完整的闭环入口：

| 闭环环节 | 看板入口 |
|---|---|
| 诊断 | 今日概览（待辅导数）+ 高频错误点 TOP5 + 需关注学员 |
| 改进 | 教官根据诊断建议调整教学方案（线下行为，系统不记录） |
| 验证 | 教学改进验证模块，对比调整前后数据 |
| 个别辅导 | 需关注学员 → 点击进入学员详情页 → 查看薄弱步骤 TOP3 |

## 7. 校验与异常处理

### 7.1 输入校验

| 字段 | 校验规则 | 失败码 |
|---|---|---|
| cls | 非空时长度 1-32 | 422 |
| before_start/before_end/after_start/after_end | 正整数，start <= end | 422 |
| limit | 正整数，上限 20 | 422 |

### 7.2 异常处理

| 场景 | 处理 |
|---|---|
| 今日无考试数据 | 返回 `exam_count: 0, avg_score: 0, pass_rate: 0, pending_tutor_count: 0`，不报错 |
| 高频错误点不足 5 个 | 返回实际数量，不补齐 |
| 需关注学员为空 | 返回 `students: []`，不报错 |
| 实时进度无订阅设备 | 返回 `devices: []`，不报错 |
| 教学改进验证时间窗无数据 | 返回 `before: null, after: null, trend: "no_data"` |
| WebSocket 断连 | 前端自动重连（复用现有 WS 重连机制，doc/42） |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 大量历史报告导致统计查询慢 | 看板加载超时 | 复用 P2 `analysis_cache` 表缓存；今日概览限定 `DATE(ts_upload_ms) = today` 索引命中 |
| WebSocket 连接不稳定 | 实时进度推送丢失 | 前端自动重连 + 30s 轮询兜底（WS 推送为增量优化，轮询保证最终一致） |
| 教学改进验证时间窗选择不当 | 对比结果无意义 | UI 提示建议时间窗长度 ≥ 7 天；展示 report_count 辅助判断样本量 |
| 看板页面模块过多导致加载慢 | 用户体验差 | 各模块独立异步加载，首屏优先加载今日概览 |
| 诊断结果与实际教学不符 | 教官不信任看板 | 诊断阈值可配置（P2）；看板展示 metric_value 让教官自行判断 |
