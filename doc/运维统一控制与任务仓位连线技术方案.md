- 日期：2026-08-26
- 状态：规划（待审核后实施）
- 关联：device_ops_center-v0.0.1（OPS 基座：节点运维统一入口，doc/58 定位"只监督生产部署后状态、不轮询业务 API、无业务端点"）

## 一、现状分析（web 组件 + web_monitor_plugin）

### 1.1 组件结构（plugins/web_monitor_plugin.py 门面）
- `web_monitor_plugin.py`：插件生命周期管理 + 组件组装（v2.1.0）
  - `status_monitor`（StatusMonitor）：**自己跑 `ros2 node list` + `systemctl status` + HTTP 回调** 探测节点/通道/服务（components/web/status_monitor.py）
  - `control_executor`（ControlExecutor）：**自己管理 dev_scripts（SIGINT 杀脚本）与 deployment_services（systemctl）**，start/stop/restart 直接执行（components/web/control_executor.py）
  - `alarm_manager`、`web_server`（FastAPI :9183）、`business_collector`（业务快照聚合）、`config_manager`（热加载）、`task_controller`、`event_bridge`（WS 推送）
- Web 页面：index.html（仪表盘：仓位热力 + AGV + 任务）、monitor.html（节点/通道状态）、control.html（节点/服务控制）、calibration.html（标定）

### 1.2 现存问题（用户痛点）
1. **节点/服务控制各自一套**：app_mgr control.html 直接 systemctl/脚本控制，OPS（device_ops_center）node_governor 也控制同一批节点——两套控制会冲突：**app_mgr 手动 stop 的节点会被 OPS watchdog 自愈拉起**，用户停在 app_mgr 页面操作却无法预期结果。
2. **状态数据源不统一**：app_mgr 自己 `ros2 node list` + `systemctl status` 探测，OPS watchdog prober 也探活同一批节点——两套结果可能不一致（OPS 有 pause/resume 语义，app_mgr 无）。
3. **app_mgr web 掺杂运维**：control.html/monitor.html 运维 UI 与业务混在一起，且运维逻辑与 OPS 重复。

### 1.3 OPS 侧已有能力（统一入口已具备，无需新增 OPS 功能）
- `POST /api/nodes/{name}/restart`：restart + `watchdog.recovery.reset(name)`
- `POST /api/nodes/{name}/stop`：stop + **`watchdog.recovery.pause(name)`（防自愈拉起）**
- `POST /api/nodes/{name}/start`：start + `watchdog.recovery.resume/reset(name)`
- `GET /api/nodes/{name}/service`：`ctl.status()`（systemd is-active 或进程探测）
- `GET /api/nodes`：注册节点列表（managed_nodes.yaml：rtsp_node / app_mgr，含 restart 配置）
- `GET /api/status`：system（设备）+ rtsp（推理）+ nodes（watchdog 探活）+ governor
- `GET /api/watchdog/status`：watchdog 开关 + auto_recovery + 各节点探活状态
- 架构定位：OPS 是**唯一运维控制执行者**，app_mgr 只做**业务 + 遥控展示**。

## 二、需求 1：统一节点服务控制（以 OPS 为执行者，app_mgr 为遥控 UI）

### 2.1 思路
- **app_mgr 不再直接执行 systemctl/脚本**（ControlExecutor 的 dev_scripts/deployment_services 路径停用，代码保留兼容）；
- 新增 **OpsControlProxy** 组件（app_mgr 内 HTTP 客户端），所有节点/服务控制按钮 → OpsControlProxy → `http://127.0.0.1:1818/api/nodes/{name}/restart|stop|start`；
- OPS 内部已统一处理看门狗冲突：stop 时 pause（防拉起）、restart 时 reset、start 时 resume——**冲突由 OPS 单点解决**；
- 用户常登录 app_mgr（业务为主），在 app_mgr UI 即可完成节点重启，结果实时回显。

### 2.2 配置（app_mgr params.yaml 新增）
```yaml
ops_integration:
  enabled: true
  base_url: "http://127.0.0.1:1818"        # OPS web 端口
  timeout_s: 10
  node_map:                                  # app_mgr 显示名 → OPS managed node 名
    rtsp_inference: "rtsp_node"
    app_mgr: "app_mgr"
``'

### 2.3 OpsControlProxy 接口（components/web/ops_proxy.py）
```python
class OpsControlProxy:
    def list_nodes(self) -> dict          # GET /api/nodes（含 watchdog 状态）
    def node_status(self, name) -> dict   # GET /api/nodes/{name}/service
    def restart(self, name) -> dict       # POST /api/nodes/{name}/restart
    def stop(self, name) -> dict          # POST /api/nodes/{name}/stop（OPS 自动 pause 看门狗）
    def start(self, name) -> dict         # POST /api/nodes/{name}/start（OPS 自动 resume）
    def ops_status(self) -> dict          # GET /api/status（系统/rtsp/nodes 统一状态）
``'
- 统一返回 `{success, error, detail}`；OPS 不可达 → `{success: False, error: "OPS 不可达: ..."}`，前端 toast 提示（禁原生 alert）。

### 2.4 UI 改造（control.html / control.js）
- 服务管理卡片改标题为「节点运维（经 OPS 统一控制）」：
  - 表格列出 OPS `/api/nodes` 注册节点（显示名 + OPS 名 + watchdog 状态）；
  - 每行「启动 / 停止 / 重启」按钮（停止带二次确认，文案提示"停止后 OPS 看门狗暂停自愈，需手动启动恢复"）；
  - 操作结果回显 OPS 返回（success/error + probe 结果）。
- 移除/隐藏「开发模式脚本控制」入口（保留代码不删，UI 不暴露）。

## 三、需求 2：统一状态数据源

### 3.1 思路
- **节点/服务/系统状态以 OPS 为权威**（watchdog prober 探活 + managed_nodes registry + RestartCtl.status）；
- app_mgr status_monitor 的 `get_ros2_nodes_status` / `get_services_status` **不再自己跑 `ros2 node list` / `systemctl`**，改为经 OpsControlProxy 拉 OPS：
  - 节点状态 ← `GET /api/nodes`（watchdog_status）+ `GET /api/watchdog/status`（nodes 探活）；
  - 服务状态 ← `GET /api/nodes/{name}/service`（逐节点，或批量 `/api/status` 的 nodes 段）；
  - 系统信息（CPU/内存/网络）← `GET /api/status` 的 system 段（OPS device.collect()）。
- **保留 app_mgr 自产业务状态**：仓位（bay_cache）、目的仓（dest_cache）、AGV、任务队列、活跃实例、告警——这些是业务数据，仍由 app_mgr 业务插件产生（需求 3 边界）。

### 3.2 缓存策略
- 复用现有 StatusMonitor `_cache` + RLock：OPS 数据每 5s 拉取一次（对齐现有 monitor_interval），拉取失败用旧缓存 + 标记 `ops_reachable: false`（前端显示 OPS 离线提示，参考 OPS 自身 doc/78 离线降级）。

### 3.3 UI（monitor.html / monitor.js）
- 节点/服务表格数据源切换为 OPS 统一状态；新增「数据源: OPS」角标；OPS 离线时表格置灰 + 提示。

## 四、需求 3：app_mgr web 以业务为主

### 4.1 职责边界（数据/接口来源分工）
| 类别 | 数据/动作 | 来源 |
|---|---|---|
| 业务 | 仓位绑定/目的仓/AGV/任务队列/活跃实例/工作流/告警/配对覆盖/时段 | app_mgr 自身业务插件（smart_trigger/workflow/bay_cache/...） |
| 视觉 | rtsp 参数、标定 ROI、视频帧、模型切换 | OPS 代理 rtsp 节点（OPS /api/params、/api/calibration、/ws/calibration 已有） |
| 运维 | 节点/服务 start-stop-restart、节点探活、系统状态、日志清理、补丁升级、网络 | OPS（本方案需求 1/2 接入） |
| 决策 | 任务配对（src→dst）、AGV 分配、下发 RCS | app_mgr（trigger/workflow/rcs_client） |

### 4.2 实施要点
- app_mgr web 保留并强化业务页（index 仪表盘、任务、仓位、标定）；control.html 运维部分全部改走 OpsControlProxy；monitor.html 状态改走 OPS；
- app_mgr 内不再新增任何 systemctl/脚本控制路径；ControlExecutor 保留为兼容层但 UI 停用；
- 未来新节点注册只需改 OPS managed_nodes.yaml，app_mgr 自动展示（经 /api/nodes）。

## 五、需求 4：任务配对仓位连线（v5：三色线条 + 全曲线路由 + 浮动匹配面板）

### 5.1 数据流（已打通，v4 修复字段丢失）
- app_mgr `business_update` WebSocket 推送（event_bridge → /ws），dashboard.js 订阅 `WS.on('business_update')`：
  - `task_queue.queue`：**触发前**候选任务，每项含 `src_bay` / `dst_bay`（TaskCandidate）→ **浅蓝虚线**（pending；候选即触发，积压时才可见）；
  - `active_instances.instances`：**触发后**执行中任务，含 `src_bay` / `dst_bay` / `status` / `current_state` / `robot_id` → **灵动科技深蓝实线**（active）；
  - `recent_failures`（v5 新增）：**任务异常**（workflow.task_failed 事件缓存，60s 窗口）→ **灵动红色实线**（error）；
  - 任务完成/正常结束 → 实例消失 → **连线淡出移除**。
- 仓位定位：仓位卡 `data-bay-id` + `BAY_GROUP_MAP`（起始 A/B/C/D 区 24 仓）/ `DEST_FLOOR_MAP`（目的 2F/3F/4F 区 18 仓）。

### 5.2 视觉规范（v5 三色）
| 状态 | 线型 | 颜色 | 效果 |
|---|---|---|---|
| pending 候选匹配 | 虚线 | 浅蓝 #93c5fd（1.5px，opacity .9） | 静态虚线 + 淡光晕 |
| active 任务中 | 实线 | 灵动科技深蓝 #2563eb（2px） | 双层亮蓝 glow（#60a5fa）+ dashoffset 流光动画 |
| error 任务异常 | 实线 | 灵动红 #ef4444（2px） | 红色 glow（#f87171）+ 流光动画 |
| 移除 | — | — | opacity 0 过渡 0.6s 后 remove |

### 5.3 全曲线路由（v5，无直线段）
- 端点：src 卡片右边缘中点 → dst 卡片左边缘中点（不穿卡）；
- **单段三次贝塞尔**：`M sx,sy C mx,sy mx,dy dx,dy`（`mx = (sx+dx)/2 + laneDx`，laneDx 为轨道偏移）——起点水平引出、背景带内平滑转折、终点水平引入，**全程曲线、无 L 直线段、无折角**；
- 轨道分配：按 src.cy 排序分配 laneIdx → 垂直段（曲线最深处）水平错开，不交叉。

### 5.4 异常数据链路（v5）
- 根因：failed 实例 run() 结束即 `_instances.pop`（engine.py L300），不留在 active_instances；
- 方案：event_bridge 订阅 `workflow.task_failed`（payload 含 src_bay/dst_bay）→ `_recent_failures`（deque maxlen=10，带 failed_at）→ business_collector 汇总进 `recent_failures` → 前端 60s 内显示红色线，超时移除。

### 5.5 浮动匹配信息面板（v6：半透明 + 默认折叠 + 可拖动）
- **结构**（index.html 静态骨架 + JS 填充）：标题栏（`pair-panel-header`：图标 + 标题 + 数量汇总 badges + 折叠箭头） + 内容区（`pair-panel-body`：候选/进行中/异常三组色点列表）；
- **透明度（v6 提升）**：面板背景 `rgba(15,25,40,.5)` + blur(4px)，标题栏 `rgba(15,25,40,.68)`——更透、少遮挡仓位，标题保持可读；
- **默认折叠（v6）**：`.pair-panel.collapsed .pair-panel-body{display:none}`——默认只显示标题栏 + 数量汇总（候选 n / 进行 n / 异常 n，异常红色强调），点击标题栏展开/收起（chevron 旋转），避免遮挡仓位区域；
- **可拖动（v6）**：标题栏 mousedown 拖动面板（原生 mousedown/mousemove，更新 left/top 并 clamp 在 card-body 内，cursor grab/grabbing）；面板 `pointer-events:auto`（标题可点击拖动、body 可滚动）；
- 内容随 business_update 实时更新（renderPairPanel 只填 body + badges，不重置折叠状态）；
- 实现：dashboard.js `renderPairPanel(d)` + `bindPairPanel()`（折叠 toggle + 拖动，一次性绑定）。

### 5.6 边界
- 同一 src/dst 多条（理论上 1:1 贪婪保证）→ active 覆盖 pending；同 key error 优先；
- resize/重渲染 → refresh 重算；连线 pointer-events:none（不拦截）；面板仅标题栏可交互（点击/拖动），body 纯展示可滚动；
- 拖动位置不持久化（刷新复位右上角，后续可 localStorage）；
- 不改变 renderBayGrid/renderDestGrid 业务渲染逻辑（纯视觉叠加 + data-bay-id 属性）。

## 九、风险与假设

- **假设**：OPS :1818 与 app_mgr 同机部署（板端一致，127.0.0.1 可达）；OPS 节点名与 app_mgr 显示名映射固定；
- **风险**：OPS 重启瞬间 app_mgr 控制失败 → 前端提示重试（幂等：restart 可重复执行，stop 后再 start 语义由 OPS 保证）；
- **兼容**：原 /api/control/* 与 ControlExecutor 保留（灰度期可用），UI 默认走 OPS；后续版本可移除；
- **看门狗冲突**：彻底消除——app_mgr 不再直接操作进程/服务，全部经 OPS 单点（stop 必 pause、start 必 resume），OPS 侧逻辑已实现（api_routes.py nodes_stop/start）。
