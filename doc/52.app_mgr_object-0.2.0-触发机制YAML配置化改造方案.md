## 1. 目标与范围

### 1.1 目标

将智能触发器（SmartTrigger）的触发机制通过 **YAML 配置** 驱动，达到：

1. **现场可调**：始发仓条件、目的仓条件、AGV 状态均衡、限流节奏、工作时间窗口等触发要素，尽量通过修改 `smart_trigger.yaml` / `status_poller.yaml` 改变触发行为，不发布代码；
2. **热更新闭环**：配置变更（改 YAML 或前端保存）→ 校验 → 持久化 → 运行时生效 → 可观测；
3. **边界明确**：区分“参数调整”（YAML 可完全覆盖）与“逻辑重构”（需代码介入），并为逻辑重构预留可配置的策略选择器，最大化 YAML 覆盖面。

- 触发插件：`smart_trigger_plugin`、`status_poller_plugin`、`bay_status_fusion_plugin`；
- 触发组件：`components/trigger/*`、`components/task_cache/*`；
- 配置链路：`base/param_manager.py` → `config/plugin_configs/*.yaml` → Web 配置接口。

## 5. 通用化设计（目标架构）

### 5.1 设计原则

1. **单一事实来源**：`smart_trigger.yaml`（触发机制）与 `status_poller.yaml`（资源/状态）保持权威；启动加载与运行热更新走**同一套 schema/校验/注入器**，消除“Web 生效、重启回退”的不对称；
2. **参数 vs 逻辑分层**：
   - 参数层（数值/开关/映射）：全部 YAML；
   - 策略层（排序、AGV 选择、状态映射、重试）：以“**策略注册表 + YAML 选择器**”方式配置化——算法内核保留代码，但“用哪个算法、参数多少”由 YAML 决定；
3. **生效语义三档**：每个配置项声明 `startup`（仅启动生效）/ `hot`（运行热更新）/ `restart`（需重启），Web 保存时按档位提示；
4. **事件驱动解耦**：配置变更统一走 `plugin_configs.updated` 事件 → 各插件注册自己的 applier，不再强依赖 `web_monitor` 手写 handler。

### 5.2 目标组件图

```mermaid
graph LR
  A[config/plugin_configs/*.yaml] --> B[ParamManager 启动加载]
  B --> C[ConfigLoader<br/>schema 校验 + 默认值合并 + 版本号]
  C --> D[启动注入器<br/>TriggerEngine / DestBayCache / RobotCache / TaskQueue]
  D --> E[运行期 HotReloadRegistry<br/>segment -> {validate, apply}]
  F[Web /api/config/*] --> G[ParamManager.update_plugin_config_nested]
  G --> H[YAML 原子持久化 + 内存更新]
  H --> I[EventBus: plugin_configs.updated]
  I --> E
  E --> J[smart_trigger / status_poller / bay_status_fusion applier]
  J --> D
```

## 6. 开发步骤（审核通过后实施）

### 阶段 0：配置 Schema 与默认值收敛（前置，无行为变化）

- 梳理全部触发相关配置项，形成字段注册表（键名、类型、默认值、档位、校验规则）；
- 将 `trigger_engine.py:79-80` 等代码默认值与 YAML 显式收敛（消除 R-08）；
- 产出《触发机制配置字段字典》附录（§11）。

### 阶段 1：启动注入修复（R-01，最高优先）

1. `TriggerEngine.__init__` 增加 `config: dict = None` 参数，直接以插件 YAML 配置初始化 `cargo_priority / pair_overrides / pairing_policy / max_tasks_per_scan`（替换 `_get_config` 空缓存路径）；
2. `smart_trigger_plugin._activate_impl` 把 `self.config` 传入 `TriggerEngine`；
3. `status_poller_plugin._configure_impl` 将 `self.config.get('pairing_policy')` 注入 `DestBayCache`；
4. 保留 `set_*` 热更新接口不变。

### 阶段 2：热加载注册表（R-02 / R-03）

1. 新增 `HotReloadRegistry`（或扩展 `ConfigManager`）：
   - `register(plugin_name, section, validate, apply)`；
   - `apply(plugin_name, section, value)` 统一入口；
2. `smart_trigger_plugin` 订阅 `plugin_configs.updated`，对 `smart_trigger` 段调用 applier；
3. 将现有 `max_total_tasks / aging_ttl / scan_interval / max_queue_size / dispatch_per_round` 改为 hot 档，applier 更新插件属性 + 引擎/队列对象；
4. `status_poller_plugin` 订阅后支持轮询间隔热重建定时器、状态映射热更新；
5. Web 层 `config_manager.apply_config` 收敛为“持久化 + 发布事件”，业务 applier 从各插件订阅执行（保留现有 handler 作为兼容层）。

### 阶段 3：策略可配置化（R-05）

1. AGV 选择策略：`RobotCache.get_available_robot(strategy=...)` 或独立 `RobotSelector`（round_robin 现状 / least_busy / specified）；
2. 扫描顺序：`batch_matcher` 排序键按 `src_scan_order.mode` 切换；
3. 状态映射：`status_poller` 读取 `agv_status_mapping`；
4. 派发轮次：`dispatch_per_round` 替换 `smart_trigger_plugin.py:264` 硬编码；

# components/trigger/hot_reload.py（新增，示意）
class HotReloadRegistry:
    def __init__(self, logger=None):
        self._handlers: dict[tuple[str, str], dict] = {}   # (plugin, section) -> {validate, apply}

    def register(self, plugin_name: str, section: str, validate, apply):
        self._handlers[(plugin_name, section)] = {'validate': validate, 'apply': apply}

    def apply(self, plugin_name: str, config: dict) -> dict:
        result = {'applied': [], 'rejected': []}
        for (p, section), h in self._handlers.items():
            if p != plugin_name or section not in config:
                continue
            value = config[section]
            err = h['validate'](value)
            if err:
                result['rejected'].append((section, err))
                continue
            h['apply'](value)
            result['applied'].append(section)
        return result

### 7.3 AGV 选择策略（阶段 3）

```python
# components/task_cache/robot_cache.py（目标改动）
def get_available_robot(self, strategy: str = 'round_robin',
                        available_statuses: tuple = ('AVAILABLE',)) -> Optional[int]:
    with self._lock:
        available = [rid for rid, e in self._robots.items()
                     if e.status in available_statuses]
        if not available:
            return None
        if strategy == 'specified':
            ids = getattr(self, '_specified_ids', None)
            pick = [r for r in available if r in ids]
            if pick:
                return pick[0]
        if strategy == 'least_busy':
            # 按最近释放/空闲最早者（示例：可扩展为任务数/电量加权）
            return min(available, key=lambda r: self._robots[r].update_time)
        # round_robin（现状）
        idx = self._next_index % len(available)
        self._next_index = (idx + 1) % len(available)
        return available[idx]
```

## 13. 结论

1. 0.2.0 已具备“YAML 驱动触发”的骨架（目的仓巷道/策略、优先级、配对覆盖、限流、工作时间均已入 YAML），**约 70% 配置项可直接修改 YAML 生效**；
2. 核心缺口为 **R-01 启动注入**（改 YAML 重启不生效、`pairing_policy` 启动丢失）与 **R-02 热加载覆盖面**（节奏类参数需重启），修复后即可达到目标文档所述的“现场改 YAML 即可”体验；
3. 通用化方向：**schema 注册表 + 启动注入 + 事件驱动热加载 + 策略选择器**，预计改动集中在 trigger 组件与三个插件，前端配置页与校验为增强项；
4. 本次仅输出审查与方案文档，**未修改任何代码**，待审核通过后按 §6 阶段 0-5 实施。
