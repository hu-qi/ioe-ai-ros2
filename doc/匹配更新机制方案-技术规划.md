# 匹配更新机制方案-技术规划

> 状态：规划（2026-08-27 提交审核，**未修改代码**）
> 工程：app_mgr_object-0.2.0(标准版)

## 一、需求
1. **匹配优先级顺序**：从初始仓位区域开始 A→B→C→D；始发仓位编号 1001→1002→…→1006；仓位有货则按此优先级顺序匹对；
2. **候选控流**：每次最多保留 4 个候选匹对（避免过早匹对导致队列过长；仅 2 台 AGV，节奏控流合理）；
3. **目的仓位匹配**：
   - 按始发仓位对应的区域巷道（始发→目的巷道映射）匹配；
   - 巷道 1-2-3 升序、仓位小编号到大编号顺序匹对（FIFO/FILO）；
   - 最大巷道 n 有货 → 配 n+1；n-1 或 n 和 1 之间空洞不能匹配（AGV 过不去）；
   - 逐个匹配成功更新目的仓状态后才匹配下一个始发仓；
   - 队列超时老化及时清除。

## 三、技术方案
### 3.1 匹配优先级（src 按区域+编号升序）
- batch_matcher.greedy_scan_type：src 排序改为 **bay_id 升序**（`x[0]` 主键；bind_time 保留为候选字段，不作为排序主键）；
- bay_id 格式（A1001~D1006）字典序天然满足：区域 A<B<C<D、编号 1001<1002<…<1006；
- 仅剩余仓位（未显式配对）按此序；显式 pair_overrides 仍最高优先（不受影响）；
- 效果：有货始发仓按「A区1001→A区1002→…→D区1006」固定顺序匹对（确定性、可预期）。

### 3.2 候选控流（每次最多 4 个）
- smart_trigger.yaml `max_tasks_per_scan: 4`（配置驱动；batch_scan_all 已按 max_tasks 截断）；

### 3.3 目的匹配规则（确认既有实现，无需改动）
- 巷道升序/仓位升序：resolve_rule 返回 lane_ids 顺序 + 巷道 bays 顺序（入口→深处）；

### 8.1 需求澄清修正：候选上限 = 全局任务数上限（2026-08-27）
- **澄清**：「候选上限 4」指**全局任务数上限**——队列中 + 运行中 ≤ 4（含执行中任务，最多 4 个任务队列），非「每次扫描生成 ≤4」；
- **原缺陷**：max_tasks_per_scan=4 仅限制每次扫描生成量，队列可累积至 max_queue_size=50——测试出现大量候选；
- **修复**：
  1. smart_trigger 新增 `_task_capacity()`：`max(0, max_total_tasks - 队列长度 - 运行中)`（运行中 = workflow_engine.get_active_count()）；
  2. `_scan_loop` 与 `_scan_and_dispatch_once` 匹对前检查：capacity ≤ 0 → 本次不匹对；`max_tasks = min(max_tasks_per_scan, capacity)`；
  3. yaml 新增 `max_total_tasks: 4`（全局上限，配置驱动）；max_tasks_per_scan 保留（批次上限）；
- **测试**：capacity 逻辑（空→4 / 队列2+运行1→1 / 队列2+运行2→0 / 超限→0）+ 动态 max_tasks 不超 cap（100 随机用例）——全部通过；py_compile OK；
- **效果**：系统同时最多 4 个任务（队列 + 执行中），队列不再无限累积；任务完成后释放容量继续匹对。

### 8.5 候选队列超限（12 个）修复-三层防护（2026-08-27 审核通过已实施）
- **现象**：测试仍出现 12 个候选队列（目标：含执行中最多 4 个匹对队列）；
- **根因（审查）**：
  1. **两处扫描并发无锁**：`_scan_loop`（主循环 2s）与 `_scan_and_dispatch_once`（bay.bound 事件异步触发）可同时匹对+入队——各自读到相同 capacity → 各生成 ≤4 → 队列累积超限；
  2. **queued 计数恒 0（关键 bug）**：`_task_capacity` 用 `len(self._task_queue)`——**TaskQueue 无 `__len__`（是 `size()`）** → 抛 TypeError 被 except 吞掉 → queued=0 → capacity 恒偏大 → 队列不断累积（12 候选主因）；
  3. 运行中计数滞后：dispatch 后 workflow 任务实例创建有延迟，running 偏小；
- **修复（三层防护）**：
  1. `_task_capacity` 改用 `self._task_queue.size()`（修复 queued 计数）；
  2. **asyncio.Lock 单飞**：smart_trigger 新增 `_scan_lock`，`_scan_loop` 与 `_scan_and_dispatch_once` 的「capacity→匹对→入队」段互斥（消除并发超发）；锁内重算 capacity + `candidates[:capacity]` 截断；
  3. **enqueue_all(max_total)**：task_queue 入队时强制 `len(_queue) >= max_total` 则释放超限候选占用并跳过——队列长度严格 ≤ max_total（最终兜底）；
- **测试**：enqueue_all(max_total=2) 传入 4 候选 → 队列 2 + 超限释放；TaskQueue.size() 计数正确；不传 max_total 兼容；py_compile 全通过；
- **效果**：队列 + 运行中严格 ≤ max_total_tasks（4）；并发/滞后不再超发。
