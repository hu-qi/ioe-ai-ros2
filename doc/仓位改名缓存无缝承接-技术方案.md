## 一、需求

仓位编号变更（改名，如 A1001→A1000）成功后，要求**缓存数据无缝承接**：

1. **BayCache 条目承接**：旧键的 cargo_type / ai_detected / bind_status / debounce_count / in_task / last_seen / bind_time / revision / source 全部迁移到新键（不是新建空条目）；
2. **滤波组件承接**：AreaStatusFilter（防抖队列 status_queue / current_stable_state / update_count / last_update_time）随改名迁移，防抖计数与稳定状态不丢；
3. **前端编号联动**：仓位编号显示即时切换为新名，且无旧名残留（方案 A prune 为 2s 兜底，本次迁移在改名帧内完成，无残留窗口）；
4. 真实"新增/删除"仓位行为保持现状（新增=注册新键、删除=prune 清理），不得误迁移。

现状缺口：改名后 rtsp 名称变、前端名称变（方案 A 已防"多仓位"），但缓存/滤波器状态不承接——新名作为全新空条目（source=init、bind=0、防抖队列空），有货仓位改名会丢失防抖进度与绑定状态。

## 二、现状实勘（2026-08-27 已验证）

- **改名链路**：前端 bayEditModal（dashboard.js L664-743）old=bayId→newName；OPS 代理 set `polygon_ch{i}_names` 数组（替换 + 长度校验 + 读回校验，doc/仓位名称类型编排 §11）→ rtsp 热更新（AreaAssembler clear+rebuild）→ 下一帧 topic 以新名发布（`area.name`）；成功后前端同步 app_mgr yaml `bay_configs`（`m[new]=m[old]; delete m[old]`）。
- **topic 结构**（板端 `ros2 topic echo /dev01_object_status` 证实）：`channels[channel_id].areas[]` 顺序稳定 = rtsp polygon 数组顺序（改名只替换数组元素值，**顺序不变**）；0.3s 全量周期发布（`status_publish_interval=0.3`）；每 area 含 bay_id/has_cargo/cargo_type。
- **app_mgr 侧**：`_on_bay_status` → `_process_single_bay` → `cache.update_ai_result`（`_ensure_entry` 只增不删）；方案 A 已加 `prune_stale(2s)` + `_filters` 清理。**app_mgr 对"改名"无感知**（不知 old→new 映射），旧键靠 prune 消失、新键全新。
- **前端联动**：数据源 `getBayStatus`→renderBayGrid；WS `business_update`（event_bridge `_schedule_business_refresh`）与 loadAllData 周期刷新已存在——**前端无需改动**，后端迁移后键即新名。
- **dest 目的仓**：DestBayCache.update 不动态加键；改名入口 destArrangeModal→setConfigDest→yaml→reload_config（加新键留旧键，同样无承接）——见附录。

## 三、方案设计

### 3.1 改名感知：topic 位置签名对比（零 API、零前端改动）

利用 topic 通道结构（channel_id + areas 顺序稳定）做**位置签名映射**：

- 插件维护 `self._pos_map: Dict[(channel_id, area_index), bay_id]`（上一帧快照）；
- 每帧（signal_ok 通道）重建当前 `cur_map`，与 `_prev_pos_map` 对比：
  - 位置 p 旧名 old → 新名 new，且满足**全部**条件才判定改名 old→new：
    1. `old` 已不在本帧任何位置（旧名完全消失）；
    2. `new` 在本帧唯一（无第二个位置同名）；
    3. `old` 在 BayCache 中、`new` 不在 BayCache（防覆盖真实仓位）；
  - 任一条件不满足 → 不迁移（保持现状逻辑）。

### 3.2 BayCache 迁移：新增 `rename_bay(old, new) -> bool`

`bay_cache.py` 新增方法（持 `self._lock`）：

- `entry = self._bays.pop(old)`；`entry.bay_id = new`；`self._bays[new] = entry`（**对象整体转移，全部状态字段保留**）；
- 日志 info（含迁移前后 cargo_type/bind_status 摘要）；
- old 不存在返回 False。

### 3.3 滤波组件迁移：`_filters[new] = _filters.pop(old)`

AreaStatusFilter 对象无 bay_id 绑定字段，直接转移实例（防抖队列/稳定状态/update_count 全部保留）。

### 3.4 融合插件接入（`bay_status_fusion_plugin.py`）

- 新增 `_collect_pos_map(msg)`：构建 (channel_id, area_index)→bay_id（仅 signal_ok 通道）；
- 新增 `_detect_and_apply_renames(cur_map)`：执行 3.1 检测 + 3.2/3.3 迁移；单帧迁移数上限 6（超限 warn 跳过，防整通道异常批量误判）；
- `_on_bay_status`（与 fallback 分支）帧处理顺序：**处理仓位（update_ai_result）→ 改名检测迁移 → prune_stale**（迁移先于 prune，保证旧键迁移而非被删；新键本帧已刷新 last_seen 不会被误剪）；
- 首帧（`_prev_pos_map` 为空）只建映射不检测；
- 配置 `rename_detection: true`（默认开，yaml 注释）。

### 3.5 前端联动（零改动确认）

迁移后 BayCache 键即新名 → `getBayStatus`/WS business_update → renderBayGrid 显示新名+承接状态；旧键已迁移（非 prune 删除），无 A1001 残留窗口。前端改名成功后已有 `loadAllData()`，后端迁移在下一帧（≤0.3s）完成，随后刷新即见新名。

## 五、边界与失败模式

1. **通道顺序调换**：cur_names 仍含旧名 → 条件①不满足 → 不迁移（名称未变，无影响）；
2. **两仓名互换位置**：A/B 都仍在缓存 → 条件③（new 不在缓存）不满足 → 不迁移；
3. **真实新增仓位**：new 不在缓存、但旧名未消失（数量+1）→ 条件①不满足 → 不迁移，正常 `_ensure_entry` 注册；
4. **真实删除仓位**：旧名消失、位置无新名 → 不迁移，prune 清理；
5. **新名与现有仓位冲突**：条件③挡住，防覆盖；
6. **批量改名（多仓同帧）**：循环逐个迁移，每个按当前缓存判断；单帧 > 6 个 warn 跳过（防整通道异常批量误判）；
7. **信号跳过通道**：该通道不参与 cur_map；恢复后对比迁移（旧名 last_seen 仍新）；
8. **rtsp 未启动**：无帧 → 无检测；首帧仅建映射；
9. 迁移不改变 last_seen（沿用旧键值，新键本帧已被 update 刷新）。

## 九、实施后问题与修复（2026-08-27，板端回归发现）

### 9.1 问题现象
1. **排序错位**：改名（A1001→A1000）后，新编号 A1000 排到 A 区最后（应按编号排序）；
2. **数据未更新**：改名后前端仓位数据（绑定/任务/货物状态）未承接，显示旧值或空状态。

### 9.2 根因分析
**问题1（排序）**：
- renderBayGrid 按 bays 数组原始顺序分组、无排序；bays 顺序 = BayCache `_bays` 的 dict 插入顺序；
- `rename_bay` 执行 pop+重插 → 新键到 dict 末尾 → A1000 排 A 区最后。

**问题2（数据未更新，两个层面）**：
- **层面A（后端竞态，主因）**：前端改名流程 `Promise.all([doName, doType])` 并行；`setConfigBay`（yaml 热加载）→ `reload_config` **立即执行**，此时 rtsp 新帧（0.3s）未到 → A1000 不在缓存 → **抢先创建空条目** → 下一帧 topic 改名检测条件③（new 不在缓存）不满足 → **迁移被跳过** → 旧键状态丢失。
- **层面B（前端刷新时机）**：改名成功后 loadAllData() 仅一次；若早于后端迁移则读到旧数据；前端无周期业务刷新、改名不触发 business_update → 之后不再更新。

### 9.3 修复（已实施）
1. **前端排序**：renderBayGrid / renderDestGrid 分组后组内按编号数字部分升序（`baySortByNum`：parseInt 数字后缀，同数字字典序兜底）；
2. **后端 reload_config 改名配对迁移**：新旧键集对比，removed/added 数量相等且 ≤6 时，按「前缀相同 + 编辑距离≤2 + 双向唯一」配对执行 `rename_bay`（状态承接），再应用新配置 cargo_type；无法配对的 removed 留给 prune、added 正常创建；与 topic 检测两种时序均兼容（reload 先迁移后 topic 不重复；topic 先迁移后 reload removed 为空）；
3. **前端改名后延迟刷新**：改名成功回调 `setTimeout(loadAllData, 1000)`——留足 rtsp 热更新 + 后端迁移窗口。

### 9.4 测试（本地 6 项全过）
1. reload 改名配对迁移（状态保留 + cargo_type 新定义）；2. 前缀不同不配对；3. 数量不等不配对；4. topic 先迁移后 reload 不重复；5. 编辑距离/双向唯一配对（A1001↔A1000、T2001↔T2002）；6. T 前缀配对。py_compile + node --check 通过。

### 9.5 板端回归清单
1. 改名 A1001→A1000：A 区按编号排序（A1000 最前）；≤1s 前端显示承接状态（绑定/任务/AI 状态）；
2. 改名后无需手动刷新即可见新名+数据；
3. 真实新增/删除仓位行为不变；顺序调换不误迁移。
