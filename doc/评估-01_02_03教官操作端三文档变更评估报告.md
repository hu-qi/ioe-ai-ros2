### 3.3 需与产品方确认的三个问题

1. **架构路径**：02 方案定义的是独立新平台（SQLAlchemy ORM、独立建表、Vue3 前端），而现有平台是 app_mgr_object 插件体系（原生 SQL repo、已有前端）。
   - 路径 A（推荐）：**在现有平台上补齐能力** —— 4 接口/诊断/统计已就绪，只补评分引擎、YAML 规则化、证据转换等增量；
   - 路径 B：按 02 方案另起新工程 —— 成本高，且需要重新对接联调。
   - **此决策是 P1 开发的前提。**
2. **评分权重公式**：02 §4.1 示例 `total_score += score * rule.time_weight` 中，子步骤得分已含用时系数，汇总时再乘 `time_weight` 属双重计权，且 `accuracy_weight/sequence_weight` 定义了却未使用。建议按 03 §2.5 语义确认汇总公式（03 同样存在 `total += score * default["time_weight"]` 写法，疑为文档笔误）。
3. **规则数据源**：02 §5.3 说"引擎优先 YAML，DB 表作界面编辑持久化"，03 §2.3.3 说"可完全由 YAML 驱动，数据库不存规则"——两文档不一致，需定案（简化方案：完全 YAML 驱动）。

## 四、建议行动

1. **先确认架构路径**（路径 A / B），此为后续所有开发的前提；
2. 确认评分公式与规则数据源两个疑点（可先按 03 文档语义实现：得分直接累加、完全 YAML 驱动）；
3. 按优先级推进：P1 评分引擎（+ scoring_rules YAML）→ P2 诊断规则 YAML 化与工序分组 → P3 证据转换 → P4 第 5 维与证据关联 → P5 教学闭环 → P6 看板工序维度；
4. P7 前端重构建议单独立项评估，现有前端可支撑当前功能验收；
5. 每步开发带测试验收（沿用 test/ 下按层拆分的测试组织方式）。

## 五、总体结论

- **对接层**：01/02/03 三份文档与 dev01 v3 完全对齐，平台侧 4 接口已就绪，**无新增对接变更**；
- **业务层**：三份文档新增的是平台业务能力（评分引擎、YAML 配置驱动、工序维度、证据处理、教学闭环），现有平台完成度约 60%，剩余为增量开发而非重构；
- **关键决策点**：架构路径（A 补齐 vs B 新建）+ 评分公式 + 规则数据源，三项确认后即可开工 P1。
