# app_mgr_object-0.1.4 P0 修复开发指南

> 文档版本：v1.0
> 编写日期：2026-08-07
> 适用基线：`app_mgr_object-0.1.4(基础版)`（与《39.app_mgr_object-0.1.4-工程架构与开发参考文档.md》配套）
> 修复范围：
>   - P0-1 统一资源释放入口（StateCoordinator）+ 释放标记防二次释放
>   - P0-2 执行终态 on_exit 与全局 on_error，保证资源释放与异常处理
>   - P0-3 统一 RCS 查询键（taskCode / taskNo）
>   - 附：`rcs.alarm_escalated` 消费方（人工介入超时升级告警呈现）

---

## 0. 修复原则

1. **向后兼容**：所有改动对旧事件（不带 `resources_released` 字段）保持幂等，不破坏 0.1.4 现有运行实例；
2. **幂等优先**：资源释放、终态动作、异常处理均"只执行一次"，以任务级标记 + 内存集合双重保障；
3. **入口唯一**：资源释放统一收敛到 `StateCoordinator`，工作流 Action 与事件订阅方均通过它释放；
4. **引擎兜底**：YAML 定义了动作则以动作为主发布方，引擎回调降级为"未发布时的兜底"，避免重复事件。

---

## 1. P0-1 统一资源释放入口（StateCoordinator）

### 1.1 现状与问题

当前存在 **两条释放路径 + 一次重复释放**：

```text
路径 A（工作流内部）：
  monitoring --callback_completed--> releasing
    → Action: release_resources → StateCoordinator.release_task()   ← 第 1 次释放
    → 引擎回调 on_instance_completed → EventBus: workflow.task_completed
      → smart_trigger._on_task_completed → _release_via_coordinator() ← 第 2 次释放（重复）

路径 B（失败路径）：
  任意状态 --失败--> failed(final)
    → 终态 on_exit 不执行（P0-2 修复）
    → 引擎回调 on_instance_failed → EventBus: workflow.task_failed
      → smart_trigger._on_task_failed → _release_via_coordinator()   ← 依赖外部事件，smart_trigger 缺失即泄漏
```

重复释放目前"恰好无害"（`set_idle` / `mark_in_task` / `locker.release` 均幂等），但存在隐患：

- 释放日志/统计失真（无法区分谁释放的、释放了几次）；
- `DestBayCache.update(is_empty=False)` 被重复调用，语义混乱；
- 未来若加入"释放后才允许复用仓位"类逻辑，双释放会引入竞态；
- 失败路径完全依赖 smart_trigger 存在，若其未加载或事件丢失则资源永久泄漏。

### 1.2 设计思路

```text
唯一入口：StateCoordinator.release_task(context, force=False)
  ├─ 幂等：_released_task_ids 集合（按 task_id 记录），已释放则直接返回 False
  ├─ 释放标记：事件与 context 均携带 resources_released: true
  ├─ 兼容：task_id 缺失时降级为"非幂等释放"（保持旧行为，不影响运行）
  └─ dispatch_task 时清除该 task_id 的记录（同任务重试可再次锁定）

事件字段约定（向后兼容）：
  workflow.task_completed / workflow.task_failed / workflow.resources_released
    新增可选字段 resources_released: bool（缺失视为 False，订阅方以 coordinator 幂等为最终保障）
```

### 1.3 实现步骤

1. 改造 `StateCoordinator`：新增 `_released_task_ids` 与幂等释放逻辑；
2. 改造 `workflow_engine_plugin._action_release_resources`：接收 `release_task` 返回值，向 context 与事件写入释放标记；
3. 改造 `components/workflow/event_bridge.py` 的完成/失败回调：事件携带 `resources_released`；
4. 改造 `smart_trigger_plugin` 三个释放回调：已带标记则跳过，未带标记走 coordinator（内部幂等）；
5. 保留旧分散释放逻辑作为"coordinator 缺失"的降级路径（行为不变）。

#### 1.4.1 `app_mgr_object/components/task_cache/state_coordinator.py`

```python
class StateCoordinator:
    def __init__(self, robot_cache, bay_cache, dest_cache, locker,
                 logger: logging.Logger = None):
        self._robot_cache = robot_cache
        self._bay_cache = bay_cache
        self._dest_cache = dest_cache
        self._locker = locker
        self._logger = logger or logging.getLogger(__name__)
        self._lock = threading.RLock()
        # P0-1 新增：已释放任务集合（幂等释放）
        self._released_task_ids = set()

    def dispatch_task(self, robot_id: int, src_bay: str, dst_bay: str,
                      task_id: str = '') -> bool:
        with self._lock:
            if not self._locker.lock(robot_id, src_bay, dst_bay):
                self._log_debug(f"dispatch 资源冲突: robot={robot_id} src={src_bay} dst={dst_bay}")
                return False
            # P0-1：任务重新下发时清除历史释放记录（支持同 task_id 重试）
            if task_id:
                self._released_task_ids.discard(task_id)
            if src_bay:
                self._bay_cache.mark_in_task(src_bay, True, source='dispatch')
            if robot_id:
                self._robot_cache.set_busy(robot_id, task_id or src_bay,
                                           source='dispatch')
            self._log_info(f"dispatch: robot={robot_id} {src_bay}→{dst_bay} task={task_id}")
            return True

    def release_task(self, task_context: dict, force: bool = False) -> bool:
        """统一资源释放入口（幂等）。

        Args:
            task_context: 任务上下文，需含 robot_id / src_bay / dst_bay / task_id
            force: 为 True 时即使已释放也再次执行（用于人工强制清理）

        Returns:
            True  — 本次实际执行了释放
            False — 已释放过（幂等跳过）或未做任何释放
        """
        with self._lock:
            task_id = task_context.get('task_id') or task_context.get('task_code')
            if not task_id:
                # 无 task_id 无法幂等：保持旧行为直接释放
                self._log_warning("release_task: 缺少 task_id，按非幂等方式释放")
                return self._release_task_impl(task_context)

            if task_id in self._released_task_ids and not force:
                self._log_debug(f"任务 {task_id} 已释放，跳过重复释放")
                return False

            ok = self._release_task_impl(task_context)
            if ok:
                self._released_task_ids.add(task_id)
            return ok

    def _release_task_impl(self, task_context: dict) -> bool:
        robot_id = task_context.get('robot_id')
        src_bay = task_context.get('src_bay')
        dst_bay = task_context.get('dst_bay')

        self._locker.release(robot_id=robot_id, src_bay=src_bay, dst_bay=dst_bay)
        if src_bay:
            self._bay_cache.mark_in_task(src_bay, False, source='release')
        if robot_id:
            self._robot_cache.set_idle(robot_id, source='release')
        if dst_bay:
            self._dest_cache.update(dst_bay, is_empty=False, source='task_complete')

        self._log_info(
            f"release: task={task_context.get('task_id')} "
            f"robot={robot_id} {src_bay}→{dst_bay}"
        )
        return True

    def get_released_task_ids(self) -> set:
        with self._lock:
            return set(self._released_task_ids)

    def reset_release_state(self):
        """人工清理/测试用：清空全部释放记录（不释放资源）"""
        with self._lock:
            self._released_task_ids.clear()
```

```python
async def _action_release_resources(self, context: dict, instance) -> str:
    self.logger.info(f"释放资源: {context.get('task_id')}")
    released = False
    try:
        coordinator = getattr(self.node, 'state_coordinator', None)
        if coordinator is not None:
            # P0-1：统一入口（幂等，返回是否实际释放）
            released = coordinator.release_task(context)
        else:
            # 兼容降级：原分散释放逻辑（smart_trigger 未激活时兜底）
            src_bay = context.get('src_bay')
            dst_bay = context.get('dst_bay')
            robot_id = context.get('robot_id')
            status_poller = getattr(self.node, 'status_poller', None)
            if status_poller and robot_id:
                status_poller.robot_cache.set_idle(robot_id)
            if src_bay:
                bay_fusion = getattr(self.node, 'bay_status_fusion', None)
                if bay_fusion and bay_fusion.cache:
                    bay_fusion.cache.set_unbound(src_bay)
                    bay_fusion.cache.mark_in_task(src_bay, False)
            if dst_bay and status_poller and status_poller.dest_cache:
                smart_trigger = getattr(self.node, 'smart_trigger', None)
                if smart_trigger and getattr(smart_trigger, '_trigger_engine', None):
                    smart_trigger._trigger_engine.release_dst_bay(dst_bay)
                status_poller.dest_cache.update(
                    dst_bay, is_empty=False, source='task_complete'
                )
            released = True

        # P0-1：释放标记写入 context 与事件（下游订阅方据此跳过二次释放）
        context['resources_released'] = True
        self._publish_event('workflow.resources_released', {
            'task_id': context.get('task_id'),
            'src_bay': context.get('src_bay'),
            'dst_bay': context.get('dst_bay'),
            'robot_id': context.get('robot_id'),
            'resources_released': True,
            'released': released,
        })
        return 'done'
    except Exception as e:
        self.logger.error(f"释放资源异常: {e}")
        return 'done'
```

#### 1.4.4 `app_mgr_object/plugins/smart_trigger_plugin.py` —— 订阅方跳过已释放任务

```python
def _release_via_coordinator(self, data: dict):
    # P0-1：事件已带释放标记 → 工作流内部已释放，直接跳过
    if data.get('resources_released'):
        self.logger.debug(f"任务 {data.get('task_id')} 已由工作流释放，跳过")
        return
    if self._state_coordinator is not None:
        # 幂等兜底：即使旧事件无标记，coordinator 也保证只释放一次
        self._state_coordinator.release_task(data)
    else:
        self._trigger_engine.release_task_resources(data)

def _on_task_completed(self, data: dict):
    task_id = data.get('task_id', '')
    self.logger.info(f"任务完成: {task_id}, 释放并分发下一任务")
    self._release_via_coordinator(data)
    self._dispatch_from_queue()

def _on_task_failed(self, data: dict):
    task_id = data.get('task_id', '')
    self.logger.warning(f"任务失败: {task_id}, 释放并分发下一任务")
    self._release_via_coordinator(data)
    self._dispatch_from_queue()

def _on_resources_released(self, data: dict):
    self._release_via_coordinator(data)
    self._dispatch_from_queue()
```

## 2. P0-2 执行终态 on_exit 与全局 on_error

### 2.1 现状与问题

`WorkflowInstance.run()` 的执行循环为：

```python
while not self.definition.is_final_state(self.current_state):
    ...
    next_state = state_def.transitions.get(event)
    if next_state:
        await self._transition_to(next_state)
    ...
```

`_transition_to()` 只执行**旧状态**的 `on_exit`。因此：

- 进入 `completed` / `failed` 终态后循环立即退出，**终态自身的 on_exit 永远不会执行**；
- `agv_transport_atomic.yaml` 中 `completed.on_exit: [publish_completed_event]`、`failed.on_exit: [release_resources, publish_failed_event]` 均为死配置；
- 目前"任务完成事件"由引擎回调兜底发布，但"失败释放"完全依赖 `smart_trigger` 订阅 `task_failed` 事件——事件链断则资源泄漏；
- YAML 的全局 `on_error` 从未被引擎消费：Action 抛异常时仅日志记录，无确定性处置。

### 2.2 语义与设计

明确两个语义（写入工作流规范注释）：

```text
on_exit（终态）: 实例进入终态时执行一次，用于终态收尾动作
                 （completed → 发布完成事件；failed → 释放资源 + 发布失败事件）
on_error（全局）: 实例 run() 或引擎执行抛出未捕获异常时执行一次
                  （log_error + release_resources + publish_failed_event）
```

关键设计：

```text
1. 幂等标记（实例级）：
     _terminal_exit_executed —— 终态 on_exit 只执行一次
     _on_error_executed      —— 全局 on_error 只执行一次
     terminal_event_published—— 终态事件已由 Action 发布（引擎回调降级为兜底）

2. 执行时机：
     run() 主循环退出（到达终态）→ _execute_terminal_exit()
     run() except Exception      → _execute_on_error()
     引擎 _run_instance except   → 兜底 _execute_on_error()（实例已执行则跳过）

3. 事件去重：
     publish_completed_event / publish_failed_event 置 terminal_event_published=True
     引擎回调仅在 terminal_event_published=False 时发布，避免双发

4. 与 P0-1 协同：
     failed 终态 on_exit 内的 release_resources 走 StateCoordinator（幂等）
     task_failed 事件携带 resources_released=True，smart_trigger 自动跳过
```

### 2.3 实现步骤

1. `WorkflowInstance`：新增幂等标记与两个公开方法 `run_terminal_exit()` / `run_on_error()`；
2. `WorkflowInstance.run()`：循环退出后执行终态 on_exit；异常分支执行全局 on_error；
3. `WorkflowEngine._run_instance`：终态回调前检查 `terminal_event_published`；异常分支兜底执行 on_error；
4. `workflow_engine_plugin`：`publish_completed_event` / `publish_failed_event` 置标记；
5. 调整 `agv_transport_atomic.yaml`：保持现有 on_exit/on_error 内容即可（语义被激活），并补充注释；
6. 引擎回调改为兜底发布后，正常路径只发一次事件。

```python
self._on_error_executed = False        # 全局 on_error 已执行
```

新增公开方法：

```python
async def run_terminal_exit(self) -> bool:
    """执行终态 on_exit（进入终态时执行，仅一次）。返回是否实际执行。"""
    if self._terminal_exit_executed:
        return False
    self._terminal_exit_executed = True
    state_def = self.definition.get_state(self.current_state)
    if not state_def:
        return False
    for action_name in state_def.on_exit:
        await self._execute_action(action_name)
    return True

async def run_on_error(self, error: Exception = None) -> bool:
    """执行全局 on_error（幂等，仅一次）。返回是否实际执行。"""
    if self._on_error_executed:
        return False
    self._on_error_executed = True
    if error is not None:
        self._log_error(f"执行全局 on_error: {error}")
    for action_name in self.definition.on_error:
        await self._execute_action(action_name)
    return True

@property
def terminal_event_published(self) -> bool:
    """终态事件是否已由 Action 发布（引擎回调据此去重）"""
    return self._terminal_event_published

@property
def resources_released(self) -> bool:
    """资源是否已释放（读取 context 标记，供事件桥携带）"""
    return bool(self.context.get('resources_released', False))
```

#### 2.4.2 `WorkflowInstance.run()` 改造

```python
async def run(self):
    """执行工作流，直到到达终态"""
    self._logger.info(f"[Instance] run() 开始执行: {self.id}")
    self._log_info(f"工作流启动: {self.id} 起始状态={self.current_state}")
    self._persistence.save(self)

    try:
        while not self.definition.is_final_state(self.current_state):
            state_def = self.definition.get_state(self.current_state)
            if not state_def:
                self._log_error(f"无效状态: {self.current_state}")
                await self._transition_to('failed')
                break

            # 1. 执行 on_enter 动作
            for action_name in state_def.on_enter:
                await self._execute_action(action_name)

            # 2. 执行主动作（带超时控制）
            if state_def.action:
                event = await self._execute_with_timeout(state_def)
            else:
                # 无主动作，等待外部事件
                event = await self._wait_for_event(state_def.timeout)

            # 保存最后事件用于诊断
            self.context['_last_event'] = event

            # 3. 状态转移
            next_state = state_def.transitions.get(event)
            if next_state:
                await self._transition_to(next_state)
            else:
                self._log_warning(
                    f"无匹配转移: state={self.current_state} event={event} "
                    f"available_events={list(state_def.transitions.keys())}"
                )
                self.context['_last_unknown_event'] = event
                self.context['_last_state_before_fallback'] = self.current_state

                if self.current_state == 'manual_intervention':
                    continue
                await self._transition_to('manual_intervention')

        # ===== P0-2：到达终态后执行终态 on_exit（仅一次）=====
        await self.run_terminal_exit()
        # ===================================================

        # 终态：按终态类型设置实例状态（failed 与 completed 区分）
        if self.current_state == 'failed':
            self._status = WorkflowInstanceStatus.FAILED
            self._log_warning(f"工作流失败: {self.id} 终态={self.current_state}")
        else:
            self._status = WorkflowInstanceStatus.COMPLETED
            self._log_info(f"工作流完成: {self.id} 终态={self.current_state}")

    except asyncio.CancelledError:
        self._status = WorkflowInstanceStatus.CANCELLED
        self._log_warning(f"工作流取消: {self.id}")

    except Exception as e:
        self._status = WorkflowInstanceStatus.FAILED
        self._log_error(f"工作流异常: {self.id} {e}", exc_info=True)
        # ===== P0-2：全局 on_error（幂等；含 log_error/release/publish_failed）=====
        try:
            await self.run_on_error(e)
        except Exception as oe:
            self._log_error(f"全局 on_error 执行异常: {oe}")
        # ========================================================================

    finally:
        self._persistence.save(self)
```

#### 2.4.3 `WorkflowEngine._run_instance` 改造（兜底 + 事件去重）

```python
async def _run_instance(self, instance: WorkflowInstance):
    """在协程中执行实例（带并发控制）"""
    self._logger.info(f"[Engine] _run_instance 开始: {instance.id}")
    async with self._semaphore:
        self._logger.info(f"[Engine] _run_instance 获取信号量: {instance.id}")
        try:
            if self.on_instance_started:
                self.on_instance_started(instance)

            await instance.run()

            # ===== P0-2：终态事件去重 —— Action 已发布则引擎不再发布 =====
            if instance.status == WorkflowInstanceStatus.FAILED:
                if self.on_instance_failed and not instance.terminal_event_published:
                    self.on_instance_failed(instance, None)
            if (self.on_instance_completed
                    and instance.status != WorkflowInstanceStatus.FAILED
                    and not instance.terminal_event_published):
                self.on_instance_completed(instance)
            # ===========================================================

        except Exception as e:
            self._logger.error(f"[Engine] _run_instance 捕获异常: {e}")
            import traceback
            self._logger.error(traceback.format_exc())

            # ===== P0-2：引擎级兜底执行全局 on_error（实例已执行则跳过）=====
            try:
                await instance.run_on_error(e)
            except Exception as oe:
                self._logger.error(f"[Engine] on_error 兜底执行异常: {oe}")
            # =============================================================

            if self.on_instance_failed and not instance.terminal_event_published:
```

### 2.5 边界与兼容说明

1. **老实例恢复**：重启后从 SQLite 恢复的实例走 `recover_all` / `_validate_and_recover`，恢复时 `current_state` 直接回填；若其状态已是终态（completed/failed），`run()` 循环不进入、`run_terminal_exit()` 会补执行终态 on_exit（幂等，安全）；
2. **manual_intervention 挂起态**：非终态，`run_terminal_exit` 不会触发；`user_cancel → failed` 时终态 on_exit 正常执行释放；
3. **CancelledError**：保持取消语义，不执行 on_error（取消不是异常）；
4. **重复事件防护**：即使 YAML 中同时配置了 on_exit 发布与引擎回调，`terminal_event_published` 保证只发一次；
5. 若某些工作流 YAML 未配置终态 on_exit，引擎回调照常兜底，行为与 0.1.4 完全一致。

## 3. P0-3 统一 RCS 查询键（taskCode / taskNo）

### 3.1 现状与问题

`queryTaskStatus` 在代码中存在**两种入参写法**，且响应匹配逻辑不一致：

| 调用点 | 入参 | 响应匹配 | 一致性 |
|---|---|---|---|
| `task_monitor_plugin` 批量轮询 | `task_id`（业务任务号 taskCode）| `item.taskCode == task_id` | 与 payload 约定一致 |
| `workflow_engine_plugin._action_compensate_query` | `rcs_task_no`（RCS 流水号）| 取 `data[0]` 首项 | 键不一致 |
| `workflow_engine_plugin._validate_and_recover` | `rcs_task_no` | 取 `data[0]` 首项 | 键不一致 |

问题：

- 若 RCS `queryTaskStatus` 实际按业务任务号（taskCode）检索（与 `agvCallback` 回传的 `taskCode` 一致），则补偿查询/恢复校准会查不到数据 → 误判为"无响应"→ 任务被错误置为 `manual_intervention`；
- 若 RCS 按 taskNo 检索，则轮询路径（taskCode）失效；
- 无论哪种实现，`data[0]` 的取法在批量场景下都不可靠。

结论：**以 taskCode（业务任务号，即我们的 `task_id`）为统一主键**（与 `RCSPayloadBuilder` 中 `taskCode = task_id`、`agvCallback` 回传 `taskCode` 的约定一致），同时提供 taskNo 兼容回退，并对响应做容错匹配。

### 3.2 设计思路

```text
统一入口：RCSAdapterPlugin.query_task_status_unified(task_id, rcs_task_no='')
  ├─ 优先用 task_id（taskCode）查询
  ├─ 无数据/异常 → 用 rcs_task_no（taskNo）回退查询
  └─ 返回原始 RCS 响应

统一匹配：RCSAdapterPlugin.extract_task_status(resp, task_id, rcs_task_no='')
  ├─ taskCode ∈ {task_id, rcs_task_no} 才视为命中
  ├─ 单条 data 且无 taskCode 时兼容取首项（防 RCS 字段差异）
  └─ 未命中返回 ''，调用方按"仍执行中/未知"保守处理

Context 双键保存（建议）：
  context['task_id']    = 业务任务号（统一主键，已有）
  context['rcs_task_no']= RCS 流水号（回填保留，用于展示与回退）
```

### 3.3 实现步骤

1. `rcs_adapter_plugin` 新增 `query_task_status_unified()` 与 `extract_task_status()`；
2. `workflow_engine_plugin._action_compensate_query` 改用统一方法；
3. `workflow_engine_plugin._validate_and_recover` 改用统一方法（`task_id` 取自 `row['task_id']`）；
4. `task_monitor` 保持 taskCode 主键批量查询不变，仅将"按首项匹配"改为走 `extract_task_status`（可选，防御字段差异）；
5. `WorkflowEventBridge._on_rcs_agv_callback`：实例查找增加 taskNo 回退（`task_code` 匹配不到时按 `context.rcs_task_no` 反查）；
6. 记录到文档：任何新增 RCS 查询一律使用统一方法。

#### 3.4.1 `app_mgr_object/plugins/rcs_adapter_plugin.py` —— 统一查询与匹配

```python
def query_task_status_unified(self, task_id: str, rcs_task_no: str = '') -> dict:
    """统一查询任务状态：优先 taskCode（业务任务号），taskNo 兼容回退。

    与 RCSPayloadBuilder 的 taskCode=task_id、agvCallback 回传 taskCode 的约定保持一致。

    Args:
        task_id:     业务任务号（context['task_id']，如 TASK_xxx）
        rcs_task_no: RCS 任务流水号（context['rcs_task_no']，可为空）

    Returns:
        RCS 原始响应（code/data/msg）；两次查询均失败时返回最后一次响应。
    """
    keys = []
    if task_id:
        keys.append(task_id)
    if rcs_task_no and rcs_task_no not in keys:
        keys.append(rcs_task_no)
    if not keys:
        return {'code': '-1', 'msg': '缺少查询键', 'data': []}

    last_resp = {'code': '-1', 'msg': '查询失败', 'data': []}
    for key in keys:
        try:
            resp = self._client.query_task_status([key])
            last_resp = resp
            if resp.get('code') == '0' and resp.get('data'):
                self.logger.debug(
                    f"query_task_status_unified: 键 {key} 命中 "
                    f"({len(resp['data'])} 条)"
                )
                return resp
            self.logger.debug(
                f"query_task_status_unified: 键 {key} 无数据 "
                f"(code={resp.get('code')})"
            )
        except Exception as e:
            self.logger.warning(f"query_task_status_unified: 键 {key} 查询异常: {e}")
    return last_resp

def extract_task_status(self, resp: dict, task_id: str,
                        rcs_task_no: str = '') -> str:
    """从 RCS 响应中容错提取任务状态码。

    Returns:
        数字状态码字符串（'0'~'9'），未命中返回 ''。
    """
    data_list = resp.get('data') or []
    if not isinstance(data_list, list):
        return ''
    valid_keys = {task_id, rcs_task_no}
    for item in data_list:
        code = str(item.get('taskCode', ''))
        if code in valid_keys:
            return str(item.get('taskStatus', ''))
    # 兼容：响应未回带 taskCode 且仅一条数据时，取首项
    if len(data_list) == 1:
        return str(data_list[0].get('taskStatus', ''))
    return ''
```

```python
    if instance.compensate_cycle_count >= instance.MAX_COMPENSATE_CYCLES:

            self._engine._persistence.log_exception(

                json.dumps({
                    'cycles': instance.compensate_cycle_count,
                    'rcs_task_no': context.get('rcs_task_no', ''),
                    'current_state': instance.current_state,
                })
            )
        except Exception:
            pass
        return 'max_retry_reached'

    task_id = context.get('task_id', '')
    rcs_task_no = context.get('rcs_task_no', '')
    if not task_id and not rcs_task_no:
        self.logger.warning(f"无任务号，无法补偿查询: {context.get('task_id')}")
        return 'rcs_running'

        resp = await asyncio.to_thread(
            rcs.query_task_status_unified, task_id, rcs_task_no

            return 'rcs_running'

        if not task_status:
            self.logger.warning(f"补偿查询: 未匹配到任务 {task_id} 的状态")
            return 'rcs_running'

        if task_status == '9':
            self.logger.info(f"补偿查询确认完成: {task_id}")
            return 'rcs_completed'
        elif task_status in ('7', '8'):
            self.logger.warning(f"补偿查询确认失败: {task_id}")
            return 'rcs_failed'
        else:
            self.logger.info(f"补偿查询: 任务仍在执行: {task_id}")
            return 'rcs_running'
    except Exception as e:
        self.logger.error(f"补偿查询异常: {e}")
```

### 5.1 实施顺序（按依赖关系）


### 5.3 手工回归清单

1. **正常搬运闭环**：AI 绑定 → 触发 → 下发 → 回调完成 → 资源释放日志仅一次 → `get_locked_count()` 为 0；
2. **失败闭环**：模拟 RCS 返回 7/8 → 终态 on_exit 释放资源 + 发布 task_failed（smart_trigger 收到事件不二次释放）；
3. **超时补偿**：关闭 RCS 回调，等待 monitoring 100s 超时 → compensating_query 用 taskCode 查询 → rcs_running 回 monitoring；
4. **断电恢复**：任务执行中 kill 进程重启 → 恢复校准按统一键查询，已完成任务不误置 manual；
5. **人工介入超时**：任务进入 manual_intervention 并停留超过 `manual_timeout` → 30s 内出现 WARNING 告警（页面可见），重复轮询不刷屏；
6. **配置热加载**：`manual_timeout` 改动经 Web 配置保存后重启生效（顶层参数持久化路径不变）。

### 5.4 风险与回滚

- 改动面集中在 `workflow/instance.py`、`workflow/engine.py`、`state_coordinator.py`、两个 event_bridge、workflow_engine_plugin、smart_trigger_plugin，均为同一任务链路的内部模块；
- 回滚策略：四步各自独立提交（git commit 分离），若某步回归可单独 revert；SQLite 无 schema 变更，无需数据迁移；
- 兼容性：旧事件无 `resources_released` 字段、旧 YAML 无终态 on_exit，均不影响新逻辑（幂等兜底），可灰度发布。
