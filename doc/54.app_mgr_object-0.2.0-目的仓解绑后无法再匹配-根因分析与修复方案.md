# 54. app_mgr_object-0.2.0 目的仓解绑后无法再匹配-根因分析与修复方案

> 状态：**审查完成 / 方案待审核（本次未修改任何业务代码）**
> 工程：`app_mgr_object-0.2.0(标准版)`
> 日期：2026-08-31 ｜ 方式：静态源码审查 + 最小复现脚本验证（无 ROS2 桩模式）

---

## 1. 问题描述

**现象**：某一目的仓 T 因与初始仓 S 匹配成功而进入队列（占用）；随后初始仓 S 的货物被移走（解绑），S 的候选被移出队列；之后**相同货物类型的另一初始仓 S2 再次有货时，无法再匹配该目的仓 T**。

**现场怀疑**：目的仓 T 被移出队列后状态未及时更新（前端显示蓝色 `unbind`），导致无法再次被匹配。

**审查结论**：
- 目的仓 T 的**真实状态已被正确更新**：`is_empty=True`、保留占用已释放（前端蓝色只是“解绑释放”标记，本身**不阻断匹配**）；
- **真正根因**：`TaskQueue.remove_by_src()` 移除候选时**只清理了 `_queued_src`，遗漏清理 `_queued_dst`**，导致 T 残留在队列排除集合中；下一轮扫描把 T 当作“已入队目的仓”排除，因此无法再匹配；
- 蓝色 `unbind` 是表象（让现场误判为“状态未更新”），**残留的 `_queued_dst` 才是拦截匹配的根因**。

## 2. 业务流程梳理（触发链路）

### 2.1 主线流程

```text
AI 检测有货(/dev01_object_status)
  └─ bay_status_fusion_plugin：防抖 → 稳定有货 → RCS 绑定 → 发布 bay.bound
        └─ smart_trigger_plugin：bay.bound → 立即扫描(_scan_and_dispatch_once)
              └─ TriggerEngine.batch_scan_all：
                   ① is_in_working_window（work_schedule）
                   ② _task_capacity（max_total_tasks - 队列 - 运行中）
                   ③ TaskBatchMatcher.greedy_scan_type：
                      src（已绑定且 in_task=False）→ dst（空 + 排除集合）→ 配对
                   ④ 匹对即占用：dest_cache.mark_occupied(dst, 'matched')（橙）
              └─ TaskQueue.enqueue_all：入队即占用 mark_occupied(dst, 'queued')（橙）
                    _queued_src/_queued_dst 记录排除集合
              └─ _dispatch_from_queue → try_dequeue：
                    StateCoordinator.dispatch_task → 锁定 AGV/始发/目的仓（'dispatched'，橙）
                    → 发布 trigger.task_created → workflow_engine 执行
              └─ 完成/失败/资源释放事件 → release → 目的仓释放（灰/绿）
```

### 2.2 队列移除的三条路径（本问题关键对比）

| 路径 | 触发源 | 代码 | 清理 `_queued_src` | 清理 `_queued_dst` | 目的仓状态处理 |
|---|---|---|---|---|---|
| `remove_by_src` | `bay.unbound`（始发仓解绑，人工移走货物） | task_queue.py:187-195 | ✅ L191 | ❌ **缺失** | `release_occupied(set_empty=True, source='unbind')` → 回空 + 蓝色标记 |
| `remove_by_dst` | 目的仓人工移除 | task_queue.py:197-201 | 不适用 | ✅ L200 | `release_occupied()` → 回空（无蓝色） |
| `_age_out_locked` | 老化 TTL 超时 | task_queue.py:161-173 | ✅ L170 | ✅ L171 | `release_occupied()` → 回空（无蓝色） |

> **只有 `remove_by_src` 遗漏了 `_queued_dst` 清理**——这就是“解绑场景专属异常”的直接原因。

### 2.3 目的仓状态机（含前端颜色）

```text
empty（绿）──匹配成功──▶ matched（橙）──入队──▶ queued（橙）──派发──▶ dispatched（橙）
   ▲                        │                │                 │
   │                        │                │                 ├─ 完成（货物到位）：释放保留，
   │                        │                │                 │   RCS 轮询接管 → occupied（灰黑）
   │                        │                │                 └─ 失败/取消：回 empty（绿）
   │                        │                ▼
   │                        │        移除（老化/remove_by_dst）→ empty（绿）
   │                        ▼
   │                 解绑移出（remove_by_src）
   │                        ▼
   │                 unbind（蓝，is_empty=True，可再次匹配）
   └────再次匹配──mark_occupied 清除蓝色──▶ matched（橙）
```

## 3. 代码逻辑审查

### 3.1 正常路径（审查通过）

1. **匹对即占用**：`greedy_scan_type` 每成功配对一个候选立即 `mark_occupied(dst, source='matched')`（batch_matcher.py:196-214），下一个 src 基于更新后状态选择，避免多 src 指向同一空仓；
2. **入队即占用**：`enqueue_all` 对候选 `mark_occupied(dst, source='queued')`（task_queue.py:88-92），并同步维护 `_queued_src/_queued_dst`（L88-89）；
3. **扫描排除**：`_scan_loop` / `_scan_and_dispatch_once` 取 `get_queued_sets()` 作为 `exclude_dst` 传入 `batch_scan_all`（smart_trigger_plugin.py:260-264、503-506），`greedy_scan_type` 对空目的仓按 exclude 过滤（batch_matcher.py:164-165）；
4. **释放回空**：`release_occupied(set_empty=True)` 置 `is_empty=True` 并清除保留占用（dest_bay_cache.py:267-285）；
5. **老化/remove_by_dst**：均正确同步清理 `_queued_dst`（task_queue.py:170-171、200）。

### 3.2 异常路径（根因所在）

`remove_by_src`（task_queue.py:187-195）：

```python
def remove_by_src(self, src_bay: str):
    with self._lock:
        removed = [c for c in self._queue if c.src_bay == src_bay]
        self._queue = [c for c in self._queue if c.src_bay != src_bay]
        self._queued_src.discard(src_bay)            # ✅ 只清理了 src
        if self._dest_cache is not None:
            for c in removed:
                self._dest_cache.release_occupied(c.dst_bay, set_empty=True, source='unbind')
        # ❌ 缺失：for c in removed: self._queued_dst.discard(c.dst_bay)
```

**后果链**：
1. 候选 S→T 从队列移除，T 真实状态回空（`is_empty=True`）且标记蓝色 `unbind`；
2. 但 `_queued_dst` 仍含 T（`get_queued_sets()` 返回残留集合，task_queue.py:204-206）；
3. 下一轮扫描 `exclude_dst` 含 T → `empty_dst = [d for d in ... if d not in exclude_dst]` 过滤掉 T（batch_matcher.py:164-165）→ **T 无法再匹配**；
4. 前端显示蓝色（`get_bay_state` 优先级 reserved > unbind > occupied > empty，dest_bay_cache.py:297-310），现场误以为“状态未更新”，实际是排除集合残留。

### 3.3 顺带审查发现（次要项，供后续评估）

| 编号 | 项 | 位置 | 说明 | 风险 |
|---|---|---|---|---|
| N-1 | `try_dequeue` 不校验始发仓绑定状态 | task_queue.py:93-143 | 若 `bay.unbound` 事件因启动时序丢失，队列中该 src 候选仍可能被派发 | 低 |
| N-2 | `remove_by_src` 未释放 locker 锁 | task_queue.py:187-195 | 队列中候选未加锁（加锁在派发时），正常流程无影响；仅作防御性补齐 | 低 |
| N-3 | `_unbind_released` 蓝色无 TTL | dest_bay_cache.py:280 | 设计如此（doc/触发机制 §九.6：可见性优先），但需前端/接口明确“蓝色=可再匹配”语义 | 低 |
| N-4 | 启动窗口事件丢失 | smart_trigger_plugin.py:163-174 | `bay.unbound` 在 smart_trigger 激活前发布会丢失；激活前无队列，影响有限 | 低 |

## 4. 根因确认（最小复现）

无 ROS2 桩模式复现（S01→T2001 入队 → `remove_by_src('S01')` → S02 同类型再匹对）：

| 步骤 | 结果 | 结论 |
|---|---|---|
| 初始匹对 | `[('S01','T2001')]` | 正常 |
| enqueue 后 `queued_dst` | `['T2001']` | 正常 |
| `remove_by_src` 后 `queued_dst` | `['T2001']` | **BUG：残留** |
| 目的仓状态 | `get_bay_state='unbind'`（蓝），`is_empty=True` | 真实状态已回空（现场怀疑不成立） |
| S02 重新匹对（带残留 exclude） | `[]` | **无法匹配 T2001** |
| S02 重新匹对（清除残留 exclude） | 可再次选中 T2001 | 根因确认：排除集合残留 |

> 复现脚本基于 `test/test_trigger_ghost_lock.py` 同款桩（`_FakeBayCache`/`DestBayCache`/`RobotCache`/`TriggerEngine`/`TaskQueue`），仅用于诊断，未写入工程。

## 5. 修复方案（开发步骤，供审核）

### 阶段 1：核心修复（必做，一行级改动）

`task_queue.py` `remove_by_src` 补清理 `_queued_dst`：

```python
def remove_by_src(self, src_bay: str):
    with self._lock:
        removed = [c for c in self._queue if c.src_bay == src_bay]
        self._queue = [c for c in self._queue if c.src_bay != src_bay]
        self._queued_src.discard(src_bay)
        for c in removed:
            self._queued_dst.discard(c.dst_bay)      # ★ 修复：清除残留排除项
        # 释放该 src 相关候选的目的仓占用（解绑场景标记蓝色，doc/触发机制 §九）
        if self._dest_cache is not None:
            for c in removed:
                self._dest_cache.release_occupied(
                    c.dst_bay, set_empty=True, source='unbind')
```

### 阶段 2：回归测试（必做）

在 `test/test_trigger_yaml_config.py`（或新建专项用例）新增：

1. `remove_by_src` 后 `get_queued_sets()[1]` 不再含被移除候选的目的仓；
2. 同类型新始发仓可再次匹配该目的仓（构造 S01→T2001 入队 → 移除 → S02 同类型再匹对 → 命中 T2001）；
3. 目的仓状态流转断言：queued（橙）→ remove_by_src 后 unbind（蓝、is_empty=True）→ 重新匹配后 matched（橙、蓝色清除）；
4. 既有幽灵锁定/老化/remove_by_dst 用例保持通过（防回归）。

### 阶段 3：防御增强（建议，可选）

1. `try_dequeue` 出队前校验 src 仓 `bind_status == 1`（防启动窗口事件丢失导致派发失效候选，N-1）；
2. `remove_by_src` 内防御性 `self._locker.release(src_bay=src_bay)`（N-2，幂等）；
3. 前端/接口明确“蓝色=解绑释放、可再匹配”语义（N-3）：`get_bay_state='unbind'` 时 `is_empty` 必为 True，建议业务采集器输出 `rematchable` 字段或在界面提示。

### 阶段 4：板端回归

- 人工移走初始仓货物 → 解绑 → 队列移除 → 目的仓变蓝 → 同类型新货上料 → 立即重新匹对成功（蓝变橙）；
- 老化/人工移除目的仓/任务失败/任务完成四类释放路径无回归；
- Web 状态展示（四色）正确。

## 6. 影响面与结论

1. **根因**：`TaskQueue.remove_by_src()` 漏清理 `_queued_dst`（task_queue.py:187-195），导致被解绑候选的目的仓残留在扫描排除集合中，无法再匹配；
2. **现场怀疑修正**：目的仓真实状态（`is_empty`）更新及时，前端蓝色 `unbind` 是正常“解绑释放”标记，并非“状态未更新”；真正拦截在排除集合；
3. **修复代价**：核心修复仅 1-2 行（阶段 1）+ 单测（阶段 2），风险低、无接口变更；
4. **建议**：审核通过后按阶段 1→2→3→4 实施；阶段 3 为健壮性增强，可独立排期。
