# 前端页面加载慢分析与优化技术规划（10+ 秒）

- 日期：2026-08-26
- 状态：规划（待审核后实施）
- 工程：app_mgr_object-0.2.0(标准版)

---

## 一、问题

app_mgr 任意页面加载/切换需要 **10+ 秒**才全部显示内容。

## 二、根因分析（代码实勘）

### 根因 1（主因）：/api/status 慢探测拖垮页面初始化
- `status_monitor.get_system_status()`（L748）用 `ThreadPoolExecutor(3)` 并行探测节点/通道/服务，然后 **`future.result()` 等最慢的探测完成**（L761-763 无 timeout）；
- 慢探测来源：`systemctl status` **timeout=10s**（L326）、callback HTTP **(3,5)s**（L593）、rclpy `get_node_names` 重试 3 次；
- 任一探测挂起 → /api/status 10s+。

### 根因 2：前端 Promise.all 串行等待最慢
- **index 仪表盘** `loadAllData()` = `Promise.all(7 个 API)`（bay/dest/agv/taskInstances/taskQueue/alarms/**status**）→ **最慢的 /api/status 决定整体渲染**（页面全部内容延迟 10s+）；
- monitor 页 `loadMonitorData + loadNodesStatus + loadChannelsStatus + loadHealthScore` 多个请求（`loadHealthScore` 又是 Promise.all 3 fetch：ops/nodes + ops/channels + local status）；
- control 页大量初始化 API + 大 inline JS。

### 根因 3：OPS 代理往返叠加（P2/P3/P4 新增链路）
- 每页面初始化多个 /api/ops/* fetch（nodes/channels/status）→ OpsControlProxy 转发 OPS（HTTP 往返）；OPS 不可达有 5s 离线窗口，但可达且慢时**无响应缓存**，每次请求都等 OPS。

### 根因 4：前端体积
- control.html **2782 行 inline JS**（大量历史注释/死代码残留）解析执行慢；
- **chart.umd.js（~200KB）base.html 全站加载**，仅 monitor 页用到。

## 三、优化技术规划

### P5-1 后端 /api/status 探测优化（核心）
1. `ThreadPoolExecutor` 各 `future.result(timeout=2.5)`——超时用旧缓存/默认值，单探测不拖垮整体；
2. 探测超时收紧：`systemctl status` 10→3s；callback HTTP (3,5)→(2,3)；`get_node_names` 重试 3→1 次；
3. `get_system_status` 结果 **TTL 缓存 3s**（页面+轮询复用，减少探测频率；web_monitor_plugin 已有 2s 缓存保留）。

### P5-2 前端非阻塞渲染（体验）
4. **index loadAllData 拆分**：业务快接口（bay/dest/agv/task）独立 Promise 先渲染（首屏秒开），`/api/status` 与告警**异步填充**（不阻塞仓位/任务/连线渲染）；
5. **monitor loadHealthScore 拆分**：ops/nodes、ops/channels、local status 各自独立渲染 KPI（不 Promise.all 等最慢）；OPS 不可达快速降级（已有 offline 标记）；
6. **页面骨架先行**：卡片先渲染「加载中」，各 API 完成后逐块填充（渐进加载）。

### P5-3 OPS 代理缓存（P2/P3 链）
7. **OpsControlProxy 响应 TTL 缓存**：list_nodes / channels_status / ops_status 缓存 5s（本地 dict + ts），页面/轮询复用，减少 OPS HTTP 往返；离线窗口 5s 保持。

### P5-4 资源与体积
8. **chart.umd.js 移到 monitor 页 extra_js**（base.html 移除，仅 monitor 用）——全站省 ~200KB 解析；
9. **control.html inline JS 精简**：清理历史注释块（restartInferNodes/服务管理/模式切换等已死代码注释，预计减 1000+ 行）→ 解析执行加快；
10. 各页 extra_js 保持本地（无 CDN 依赖）。

## 五、验证清单

1. 页面加载耗时：index/monitor/control/calibration 首屏 <3s（业务先渲染），状态 <5s 填充；
2. /api/status 耗时：<3s（单探测超时 2.5s 兜底）；多次刷新命中 TTL 缓存；
3. monitor 页：OPS 不可达时 nodes/channels/健康度各自降级显示（不互相阻塞）；
4. OPS 代理：5s 缓存生效（OPS 停后 5s 内页面用缓存快速失败）；
5. chart 仅 monitor 加载（index/control 无 chart 请求）；
6. 回归：业务（仓位/任务/AGV/连线/面板）、控制页运维、监控页状态、标定页。

## 六、假设

- 慢源主要为 /api/status 探测（systemctl/callback），优化后页面加载显著改善；
- 前端非阻塞拆分不改变数据展示内容（仅渲染顺序）；
- OPS 代理缓存一致性：状态类数据 5s 内可接受（监控页 10s 轮询场景）。
