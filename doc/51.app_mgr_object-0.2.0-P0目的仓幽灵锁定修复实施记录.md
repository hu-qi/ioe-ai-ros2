> 依据：doc/50.app_mgr_object-0.2.0-触发机制全链路分析报告.md §7 R-01（P0）
> 影响文件：4 个（3 源码 + 1 回归测试）

## 一、问题描述（R-01 摘要）

批量匹对流程中，`greedy_scan_type` 每成功生成一个候选就立即 `dest_cache.mark_occupied(dst, 'matched')` 锁定目的仓；但候选随后在**两个截断点**被丢弃时，目的仓占用未被释放：

1. `batch_matcher.py batch_scan_all` 按 `max_tasks` 截断：`all_candidates.extend(type_candidates[:remaining])` —— 超出 `remaining` 的候选被丢弃，其 `matched` 占用残留；
2. `smart_trigger_plugin.py _scan_loop` / `_scan_and_dispatch_once` 锁内重算容量后二次截断：`candidates = candidates[:capacity]` —— 被丢弃候选同样残留占用。

残留后的目的仓处于 `is_empty=False + reserved='matched'`，RCS 轮询尊重 reserved 不会置回空，也不再有任何释放路径 → **“幽灵锁定”**：巷道可用仓逐渐被假占用占满，触发吞吐持续下降，只能重启或人工干预恢复。

**触发条件**：某货物类型可配对数量 > 扫描剩余名额即必然发生（当前 `max_tasks_per_scan=4`，单类型绑定仓最多可达 6 个）。

## 三、技术方案（三层防线，保持既有匹对稳定语义）

### 3.1 第一层：候选生成即限流（源头控制）

`greedy_scan_type` 新增 `max_tasks` 参数（默认 `None`=不限）：

- 显式配对覆盖循环、策略配对循环的每次迭代前检查 `_reached_max()`，达到上限立即停止继续配对；
- 未被生成的候选**根本不会执行 `mark_occupied`**，从源头消除“生成后丢弃”的占用残留。

### 3.2 第二层：批量扫描防御性截断释放（兜底）

`batch_scan_all` 把 `remaining` 传给 `greedy_scan_type(max_tasks=remaining)`，并保留防御逻辑：

- 若某类型返回的候选仍超过 `remaining`（显式配对超限等异常路径），对超出的候选逐个 `_release_candidates()`（调用 `dest_cache.release_occupied(dst)`）后再截断；
- 函数末尾增加终态防御：返回值严格不超过 `max_tasks`，超出部分先释放再截断。

新增 `TaskBatchMatcher._release_candidates(candidates)`：遍历候选释放目的仓占用，异常仅告警不影响主流程。

### 3.3 第三层：智能触发器二次截断释放（容量缩水路径）

`TriggerEngine` 新增公开接口：

- `release_candidate(candidate)`：释放单个候选占用的目的仓（`release_occupied(c.dst_bay)`，带异常防护）；
- `release_candidates(candidates)`：批量释放。

`smart_trigger_plugin.py` 两处截断点（`_scan_loop` 与 `_scan_and_dispatch_once`）改为：

```python
capacity = self._task_capacity()
if len(candidates) > capacity:
    # 截断丢弃的候选须释放目的仓占用（防幽灵锁定）
    self._trigger_engine.release_candidates(candidates[capacity:])
    candidates = candidates[:capacity]
```

### 3.4 设计取舍

- **保留 `matched` 占用时机**：`mark_occupied('matched')` 仍发生在匹对时（“每次匹对更新占用后才匹对下一个”的既有语义不变），仅保证**最终未入选的候选一定释放**；
- **不改变入队占用/释放**：`enqueue_all` 入队占用 `queued`、重复/满拒绝释放、`age_out`/`remove_by_src` 释放等既有机制不动；
- **可选演进（本版本不做）**：完全解耦“候选生成”与“占用锁定”，仅入队时 `mark_occupied`——可进一步消除窗口，但会改变“匹对即锁定”语义，建议在后续版本评估。

## 六、影响面与回归注意事项

1. **正常扫描链路**：候选 → 入队 → 派发不受影响（保留候选在入队时由 `enqueue_all` 覆盖为 `queued`）；
2. **容量缩水路径**：运行中任务数增加导致 capacity 变小时，被截断候选的目的仓立即回空，下一轮可再次匹对（行为更优）；
3. **显式配对覆盖**：仍按原语义优先入选，且受 `max_tasks` 约束；
4. **巷道策略/最大占用模型**：不涉及选择算法改动，`lane_state_management` 行为不变；
5. **兼容性**：`greedy_scan_type` 新增参数带默认值，既有调用（仅 `batch_scan_all`）无需改动；
6. **建议板端回归**：多类型批量扫描（单类型候选 > 剩余名额）连续 30 分钟，观察目的仓四色状态无异常橙色残留、`locked_dest` 计数稳定、触发吞吐不再下降。

---

## 七、遗留与后续建议

- **可选演进**：将 `mark_occupied` 从“匹对时”推迟到“入队时”，候选阶段仅内存排除（`used_dst_set` / 排除集），彻底消除“匹配期占用窗口”，需评估与 RCS 轮询置空竞态的平衡；
- **监控增强**：可在 `dest_cache` 增加“`matched` 占用超时释放”（如 10s 未入队自动回空）作为纵深防御，防未来新增截断点再次引入同类问题；
- 建议将本用例纳入 CI（`pytest test/`），随触发链路改动持续回归。
