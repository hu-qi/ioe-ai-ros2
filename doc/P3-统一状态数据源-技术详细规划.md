## 三、方案设计

### 3.1 数据源优先级（OPS 优先 + 本地降级）

```
monitor.js loadNodesStatus()
  → GET /api/ops/nodes
  → success && !offline  → 渲染 OPS 源（看门狗状态）+ 角标「OPS」
  → 失败 / offline / 空列表 → GET /api/status 降级
      → nodes.monitored_nodes（自探测 status/alias/pid）+ 角标「本地降级」
```

- 降级判定：/api/ops/nodes 返回 `success=false` 或 `offline=true` 或 `nodes` 为空；
- 角标：card-header 右侧 badge（「OPS 权威源」蓝 / 「本地降级」橙），随时可辨数据来源；
- 10s 轮询（复用现有 setInterval）+ WS status_periodic 触发刷新。

## 八、v2 修订：通道状态可靠性修复（板端反馈"rtsp 离线仍在线"）

### 8.1 用户问题
1. 状态监控页通道无数据；通道数据/状态从哪获取最可靠？
2. **重大问题：rtsp 节点停止离线，OPS 视频通道仍显示在线**；
3. 分析系统健康趋势计分逻辑，节点来源 OPS 状态。

### 8.2 根因分析（代码实勘）
- **通道状态来源链**：OPS 订阅 rtsp 节点 `/system_monitor/status`（JSON 含 channels[].signal_status + bay_summary）→ `node.rtsp_status`（main.py L131-133）→ `/api/status` rtsp 段；
- **根因 A（OPS）**：`/api/status` rtsp 段 `json.loads(node.rtsp_status)` **无时效检查**——rtsp 离线停止发布后旧 JSON 永存 → 通道"在线"；而 watchdog prober `_probe_topic` 有 ts 新鲜度（age<=timeout_s）——同数据两处口径不一致；
- **根因 B（rtsp 节点）**：`channel_status.signal_ok` 推理回调置 true（yolov8_inference_plugin L405-406）**永不重置**——源断流后 signal_status 仍 true；
- **结论**：通道状态不可信来源 = /system_monitor/status 的 signal_status；
- **最可靠通道状态源 = OPS roi_frames 帧新鲜度**（`/api/calibration/status` frame_age_ms 每通道）：OPS 自持订阅 /debug/rtsp_dev01_X，rtsp 离线 → 帧停 → age 增 → 通道 offline——实时、无需 rtsp 在线。

### 8.3 app_mgr 通道现状
- monitor.js 通道表用 /api/status channels → status_monitor → device_manager（AI 消息维护 signal_stable）——rtsp 离线无 AI 消息陈旧；device_manager 未就绪返回空 → 通道无数据；
- 与节点表（已 OPS）数据源不一致。

### 8.4 健康度计分（status_monitor._calculate_health_score）
- 节点 40%（monitored_nodes alive）+ 通道 40%（health_rate/signal_status）+ 服务 20%（is_running）；
- v2 改造：节点用 OPS watchdog running/总数、通道用 OPS 帧龄在线率、服务保留本地；OPS 不可用回退本地 health_score。

### 8.5 修复方案
- **OPS**：
  - `/api/status` rtsp 段加时效（`age > 10s` → `{rtsp_online:false, stale:true, channels:[]}`）；
  - 新增 `/api/rtsp/channels`：roi_frames 帧龄（age<=5s → online）+ channel_count + rtsp_status ts → `{rtsp_online, channels:[{ch, online, frame_age_ms}], online_count, total}`——rtsp 离线 → 所有通道 offline；
- **app_mgr**：
  - monitor.js `loadChannelsStatus()`：OPS 优先（/api/ops/channels 代理）+ 降级本地 device_manager；
  - ops_proxy.py `channels_status()`；web_server /api/ops/channels；
  - 健康度：OPS 节点/通道 + 本地服务；KPI 通道双源。

## 十三、通道口径统一修复（2026-08-26，板端"app_mgr CH3 离线但 OPS 正常"）

### 13.1 现象
rtsp 节点停止再重启后：app_mgr 监控页 CH3 离线（帧龄 111386ms），其余通道在线；OPS 显示所有通道正常。

### 13.2 根因（两口径不一致）
- **OPS 总览页**（/api/status rtsp 段）用 rtsp 节点 `/system_monitor/status` 的 `channels[].signal` = **视频流连接状态**（channel_monitor `update_from_streams` 的 `is_connected` + signal_status_timeout 5s 超时）——rtsp 重启后 CH3 **源连接恢复**（is_connected=true）→ signal=true → OPS 显示正常；
- **app_mgr 监控页**（/api/rtsp/channels）用 **roi_frames 帧龄**（/debug 帧实际到达）——CH3 **帧停 111s**（源连接但无实际帧流/推理未出帧）→ 离线；
- **本质**：signal（视频流连接）≠ 帧流（实际推理输出）；连接恢复 ≠ 帧流恢复。

### 13.3 修复（OPS /api/status 帧龄修正）
- OPS `/api/status` rtsp 段：解析 rtsp JSON 后用 roi_frames `frame_age_ms` **修正 channels[].signal**（帧龄 <=5000ms → signal true，否则 false）+ 附加 frame_age_ms；
- OPS 总览页 renderChannels 用 c.signal → 自动显示真实帧状态（与 app_mgr 口径一致）；
- app_mgr 无需改动（已用 /api/rtsp/channels 帧龄）。

### 13.4 CH3 帧停根因排查方向（rtsp 节点侧，板端执行）
- 视频流连接恢复（is_connected true）但无帧 = **解码/推理链路未恢复出帧**；
- 检查 rtsp 节点日志：decoder error / reconnect（10 次重连失败）/ 推理线程状态；
- 检查 CH3 共享内存是否有新帧（simple_memory get_latest_buffer）；
- 检查 video.yaml CH3 rtsp 源实际数据流（连接挂起无数据）。

### 13.5 验证
- OPS /api/status：rtsp 段 channels[].signal 与帧龄一致（CH3 帧停 → signal false）；
- OPS 总览页 CH3 显示离线（与 app_mgr 一致）；app_mgr 不变；
- 板端：排查并恢复 CH3 帧流后，两处均显示在线。
