## 四、业务能力差距详细分析（按开发优先级）

### P1 单轮评分引擎（最高优先级，三大新增能力之一）

**目标形态**（01 §八 / 02 §4.1 / 03 §2.5）：
- 子步骤得分 = 基础分(max_score) × 用时系数(min(1, std/actual)) × 正确性系数(完成1.0/中断0.5/未执行0) × 顺序系数(正确1.0/错误0.7)；超时再乘 timeout_penalty(默认0.5)；
- 整轮扣分：未执行每个 -2、重复操作每次 -1、轮次超时总分 ×0.9；
- 等级：≥90 优秀 / 75-89 良好 / 60-74 合格 / <60 不合格；
- 触发时机：整包到达后立即评分（01 §9.3），结果写 `reports.total_score/grade_level` 与 `report_substeps.score`，随后刷新学员累计、班级诊断、看板缓存；
- 配置化：评分规则存 YAML（`config/scoring_rules.yaml`），按工序分组，教官界面可调。

**现有基础**：
- `reports.total_score` 列已存在（doc/38 §7 预留），整包解析已透传 `round.total_score`（端侧算的分，如上报则先存）；
- `report_substeps` 有 duration_ms/count/timeout，缺 std_duration_ms/over_std/omitted/score/sequence_error；
- `report_analysis_plugin` 已有 SOP 标准加载机制（`sop_model_paths` 按 process_type 从外部文件读标准用时）——**这是 std_duration_ms 的现成数据源**；
- 整包到达钩子现成：`receive_full_report` → `insert_full_report` → `_publish_event("report.received")`，评分引擎订阅该事件即可，无需改接收链路。

**需要开发**：
1. `config/scoring_rules.yaml`（含 default/processes/global_penalties/grade_levels 四段）+ 规则加载器（对齐现有 `_load_sop_standards` 风格）；
2. 评分引擎模块 `scoring_engine.py`（纯函数化，输入报告+子步骤+规则，输出逐项得分与总分等级）；
3. `report_substeps` 加列迁移（std_duration_ms/over_std/omitted/score/sequence_error/segments）+ `reports` 加 grade_level；
4. 评分触发：订阅 `report.received` 事件异步评分（或 BackgroundTasks）；
5. 单元测试（用 doc 中的示例数据：910s 拆解轮、substep_counts=[3,2,6,2,1,2,2,1]）。

**必须先澄清的设计疑点（评分公式）**：
- 02 §4.1 示例：`total_score += score * rule.time_weight` —— 子步骤得分已含用时系数（time_factor），汇总再乘 time_weight 是**双重计权**；且 `accuracy_weight/sequence_weight` 定义了却未在公式中使用；
- 03 §2.5 同样写了 `total += score * default["time_weight"]`；
- **两文档一致地自相矛盾**，疑为从"三权重模型"改成"四系数模型"时没删掉旧权重。建议实现按纯四系数模型（score 直接累加），把 time_weight/accuracy_weight/sequence_weight 三个字段从 YAML 中去掉或仅作文档说明，避免教官在界面上调了一个不生效的参数。

### P2 诊断/评分规则 YAML 化 + 按工序分组（02 v1.2 核心增量）

**目标形态**（02 §五 / 03 §二）：
- `config/diagnosis_rules.yaml`：五类规则（bottleneck/error/sequence/interval/stddev）+ regression，支持 `processes` 按工序分组、`common_rules` 通用回退、每条含 threshold/enabled/suggestion；
- `config/scoring_rules.yaml`：见 P1；
- 加载机制：启动加载 + `POST /api/v1/config/reload` 热重载；YAML 为规则定义源；
- 按工序回退链：先查 `process_name` 专属规则 → 缺失回退通用规则（`process_name=''`）。

**现有基础**：
- 诊断引擎已有 4 类规则实现（bottleneck/persistent_error/sequence_chaos/student_regression），阈值来自插件配置 `thresholds`（默认值：1.5/0.30/0.20/3/5/0.85），支持 YAML config 覆盖——**离 YAML 化只差"文件结构对齐 + 按工序分组 + 热重载接口"三步**；
- SOP 标准已按 process_type 分组加载（disass/assembly），是"按工序区分"的现成先例；
- 阈值热加载在本工程有成熟惯例（doc/28 参数热加载、doc/30/31 YAML 拆分先例）。

**需要开发**：
1. 新 YAML 结构（processes 分组 + common_rules 回退 + suggestion 文本入配置）；
2. 规则加载器与 `POST /api/v1/config/reload`；
3. `diagnosis_engine` 改造：4 类方法接受规则对象而非常量；补第 5 类 stddev（用时标准差 > 均值×threshold）；
4. 诊断输出按 process_name 过滤（SQL 加条件即可，reports 表已有该列）；
5. 测试：回退链正确性（专属命中/回退通用/都缺失跳过）。

### P3 证据管理增强（BMP→JPG 转换 + 元数据表 + 诊断关联）

**目标形态**（01 §七 / 03 §3.7）：
- `evidence` 元数据表：file_path/jpg_path/thumb_path/file_size，UNIQUE(device_id, round_start_ms, sub, ts) 幂等；
- 原始 BMP 落盘 `data/evidence/{device_id}/sub05_t12000.bmp`（与 dev01 §5 落盘规则 `evidence/<device_id>/...` 一致）；
- 异步转 JPG（Pillow）+ 缩略图；列表页缩略图、详情页原图；
- 诊断规则触发"操作错误/顺序混乱"时自动关联该子步骤抓拍图；
- 90 天保留期定时清理，重要轮次可标记永久保留。

**现有基础**：
- 已落盘 BMP（`report_repo.save_evidence`，目录 `{evidence_dir}/{device_id}/{round_start_ms}/sub_{sub}_ts_{ts}.bmp`）；

**需要开发**：

5. 清理任务挂入现有运维定时清理体系（doc/20 异常日志清理有现成模式）。

### P4 诊断第 5 维（interval）+ 诊断结果关联证据

- 证据关联：诊断结果结构加 evidence 字段（查 evidence 表 by device_id+round+sub），前端诊断卡片带缩略图。依赖 P3 的表。

### P5 教学改进闭环（teaching_actions）

**目标形态**（01 §6.4 / 02 §4.4）：教官记录教学调整事件（日期/描述/目标子步骤/工序/班级）→ 平台自动对比调整前后班级平均分、完成率、诊断指标 → 生成改进效果报告。

**现有基础**：`dashboard_repo.get_improvement_validation` 已实现"调整前后班级统计对比"查询（有 cls/start/end 参数），**计算内核已存在**，缺：
1. `teaching_actions` 表 + CRUD 接口（02 已给 DDL 与路由代码）；
2. 前端"教学闭环"页面（记录列表 + 创建表单 + 验证报告展示）。

### P6 看板按工序维度 + APScheduler 预聚合

- APScheduler 是**新增依赖**；鉴于现有 TTL 缓存 + WS 推送已满足"毫秒级读取"目标（01 §6.5），建议仅加工序筛选参数，**不引入 APScheduler**（YAGNI，避免为对齐文档而加依赖）。

### 决策 2：评分汇总公式（P1 开工前确认）

两文档均存在"子步骤得分已含用时系数，汇总再乘 time_weight"的双重计权矛盾（详见 §四 P1）。建议按纯四系数模型实现（得分直接累加），删除或注释三个未生效的 weight 字段。**此项建议向产品方书面确认**，避免验收争议。

### 决策 3：规则数据源（P1/P2 开工前确认）

- 02 §5.3："引擎优先 YAML，数据库规则表作界面编辑持久化"；

- **建议采用 03 的简化方案（完全 YAML 驱动）**：单一数据源、Git 可管、热重载已够用；省掉规则表 + 界面编辑 + 双源同步三块工作量；后续若教官强需求界面编辑，再加"编辑写回 YAML"。
