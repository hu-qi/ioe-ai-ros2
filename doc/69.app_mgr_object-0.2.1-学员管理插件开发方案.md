## 一、背景与目标

### 1.1 背景

机修培训场景由两端构成：

- **边缘端（AI智能实操监测终端）**：部署在学员工位旁，通过 AI 视觉无感记录学员拆解/装配全过程，输出结构化轮次报告（doc/38 schema 1.0）与实时增量事件（doc/45 schema 1.1）。
- **教官操作端（AI智能教学分析平台）**：部署在教官办公室，接收边缘端上报数据，进行学员管理、报告归档、统计分析、教学诊断。

需求说明（.docx）明确教官操作端的核心定位为"集学员管理-报告接收-统计分析于一体的AI辅助教学平台"，其中**学员管理**是整个平台的入口与基础数据源：边缘端考前绑定 `student_id`，平台侧维护学员档案库，后续报告、统计、诊断均以学员为关联主键。

### 1.2 目标

本方案规划 **学员管理插件（`student_mgr_plugin`）** 的开发，覆盖：

1. 学员档案的增删改查（CRUD）；
2. 批量导入（CSV）/ 导出（CSV），Excel 导入作为可后补能力；
3. 多条件模糊检索（姓名 / 工号 / 班级）；
4. 学员详情页骨架（档案 + 历史考试记录占位，为后续报告插件预留挂载点）。

### 1.3 范围与边界

| 维度 | 本期 P0 | 后续 P1-P3（另立方案） |
|---|---|---|
| 插件 | `student_mgr_plugin` | `report_recv_plugin` / `report_analysis_plugin` / `teaching_dashboard_plugin` |
| 数据 | `students` 表 | `reports` / `report_details` / `events` 等表 |
| 接口 | `/api/v1/students/**` | `/api/v1/reports/**`、`/api/v1/events/**`、`/api/v1/subscriptions/**` |
| 页面 | `students.html`（列表+详情骨架） | 报告详情页、统计图表页、教学看板页 |
| 对接 | 仅平台侧 CRUD，不涉及边缘端 | 接收 doc/38 整包 + doc/45 增量，按 `student.id` 关联报告 |

> **关键约束**：学员管理是独立业务域，与现有 app_mgr_object 的 AGV/仓位/任务域**完全解耦**。本期不修改现有插件逻辑，仅在 web 层新增路由组、在 plugins 目录新增插件、在 db 层新增仓储。

```
│   └── ...
config/
└── students.yaml                    【新增】学员管理插件配置（启用开关、分页大小、导入上限等）
```

### 2.2 与现有插件的协作关系

学员管理插件是**纯数据域插件**，不依赖 RCS 适配、任务缓存、触发器等业务插件，仅依赖：

- `base_plugin.py`：插件生命周期（configure / activate / deactivate / cleanup）；
- `web_server.py`：注册 HTTP 路由（复用现有 `@self.app.get/post` 注册模式）；
- SQLite：通过新建的 `student_repo.py` 访问，单文件数据库，与产品文档"零配置部署"对齐。

插件间事件：学员增删改可通过 `event_bus` 发布 `student.created` / `student.updated` / `student.deleted` 事件，供后续报告插件订阅（本期仅发布，不消费）。

### 2.3 数据流向

```
教官浏览器 ──HTTP──> web_server (/api/v1/students/**)
                          │
                          ▼
                  student_mgr_plugin（业务逻辑 + 校验）
                          │
                          ▼
                  student_repo（SQLite 仓储）
                          │
                          ▼
                  students 表（单文件 SQLite）
```

导入流：`浏览器上传 CSV → student_mgr_plugin 解析 → 逐行 upsert → 返回成功/失败统计`

导出流：`浏览器请求 /export → student_repo 全量查询 → 生成 CSV 流响应`

### 3.2 学员档案字段定义

对应边缘端上报 `student` 对象（doc/38 §3、doc/45 §2），平台侧维护完整档案：

| 字段 | 数据库列 | 类型 | 必填 | 说明 |
|---|---|---|---|---|
| 工号 | id | TEXT PK | ✅ | 唯一标识，如 S2024001；与边缘端 `student.id` 对齐 |
| 姓名 | name | TEXT | ✅ | |
| 班级 | cls | TEXT | 可选 | 对应边缘端 `student.cls` |
| 工种 | trade | TEXT | 可选 | 如"火炮维修"、"底盘维修" |
| 入学日期 | enroll_date | TEXT | 可选 | ISO 格式 YYYY-MM-DD |
| 状态 | status | TEXT | ✅ | 枚举：active（在训）/ graduated（结业）/ dropped（退学）/ deleted（软删除） |
| 备注 | remark | TEXT | 可选 | |
| 扩展字段 | extra | TEXT(JSON) | 可选 | 预留未来扩展（如性别、年龄、联系方式） |
| 创建时间 | created_at | INTEGER | ✅ | epoch ms |
| 更新时间 | updated_at | INTEGER | ✅ | epoch ms |

> **设计说明**：
> 1. 工号 `id` 作为主键，与边缘端 `student.id` 直接对齐，报告按 `student.id` 关联档案，无需中间映射表。
> 2. `status` 用枚举字符串而非数字，便于人类可读与前端筛选；软删除统一用 `deleted`。
> 3. `extra` 用 JSON 字符串预留扩展，避免频繁改表。

## 四、数据模型与建表

### 4.1 DDL（`config/students_schema.sql`）

```sql
CREATE TABLE IF NOT EXISTS students (
    id            TEXT    PRIMARY KEY,
    name          TEXT    NOT NULL,
    cls           TEXT,
    trade         TEXT,
    enroll_date   TEXT,
    status        TEXT    NOT NULL DEFAULT 'active'
                            CHECK (status IN ('active','graduated','dropped','deleted')),
    remark        TEXT,
    extra         TEXT,   -- JSON 字符串
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL
);

-- 检索索引：name / cls / status 高频查询
CREATE INDEX IF NOT EXISTS idx_students_name   ON students(name);
CREATE INDEX IF NOT EXISTS idx_students_cls    ON students(cls);
CREATE INDEX IF NOT EXISTS idx_students_status ON students(status);
```

### 4.2 数据库初始化策略

- 数据库文件路径：`config/app.db`（与现有底座 SQLite 文件位置一致；若底座尚未有统一 db，则插件配置项 `db_path` 指定）。
- 插件 `_configure_impl` 中执行 `students_schema.sql`（`CREATE TABLE IF NOT EXISTS`，幂等）。
- 连接方式：`sqlite3.connect(db_path)`，每次操作短连接，避免多线程并发问题（学员管理写入频率低，无需连接池）。
- 编码：UTF-8（`PRAGMA encoding = "UTF-8"`）。

### 4.3 与后续报告表的关系（预留设计）

后续 `report_recv_plugin` 会新建 `reports` 表，其中 `student_id TEXT` 外键引用 `students.id`。为保证本期可独立部署，**不在本期内建外键约束**，仅在 DDL 注释中说明关联关系。学员删除采用软删除（`status='deleted'`），避免破坏报告关联完整性。

## 五、接口规范（教官操作端 Web API）

### 5.1 路由总览

所有学员管理接口统一挂载在 `/api/v1/students` 前缀下，与 doc/38/45 的 `/api/v1/` 命名规范一致。

| 方法 | 路径 | 功能 | 请求体 | 响应 |
|---|---|---|---|---|
| GET | `/api/v1/students` | 分页列表 + 检索 | Query: `keyword`, `cls`, `status`, `page`, `page_size` | `{code, data:{total, list}}` |
| GET | `/api/v1/students/{id}` | 学员详情 | — | `{code, data:{student, recent_reports:[]}}` |
| POST | `/api/v1/students` | 新增学员 | JSON: 学员字段 | `{code, data:{id}}` |
| PUT | `/api/v1/students/{id}` | 修改学员 | JSON: 可改字段 | `{code, data:{id}}` |
| DELETE | `/api/v1/students/{id}` | 软删除学员 | — | `{code, message}` |
| POST | `/api/v1/students/import` | CSV 批量导入 | multipart/form-data: `file` | `{code, data:{success, failed, errors:[]}}` |
| GET | `/api/v1/students/export` | 导出 CSV | Query: 同列表检索 | `text/csv` 流响应 |
| GET | `/students` | 学员管理页面（HTML） | — | HTML |

### 5.2 统一响应格式

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... }
}
```

错误码遵循 doc/45 §8：`0` 成功 / `400` 参数错误 / `404` 资源不存在 / `422` 校验失败 / `500` 内部错误。

### 5.3 关键接口详述

#### 5.3.1 列表检索 `GET /api/v1/students`

**Query 参数**：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| keyword | string | 空 | 模糊匹配 name / id / cls（三列 OR LIKE） |
| cls | string | 空 | 精确匹配班级（空=不过滤） |
| status | string | `active` | 状态过滤；传 `all` 表示不过滤 |
| page | int | 1 | 页码，从 1 开始 |
| page_size | int | 20 | 每页条数，上限 100 |

**响应 data**：

```json
{
  "total": 156,
  "page": 1,
  "page_size": 20,
  "list": [
    {"id":"S2024001","name":"张明","cls":"机修一班","trade":"火炮维修",
     "enroll_date":"2024-09-01","status":"active","created_at":1787569000000}
  ]
}
```

#### 5.3.2 新增学员 `POST /api/v1/students`

**请求体**：

```json
{
  "id": "S2024001",
  "name": "张明",
  "cls": "机修一班",
  "trade": "火炮维修",
  "enroll_date": "2024-09-01",
  "remark": "",
  "extra": {}
}
```

**校验规则**：

| 字段 | 规则 |
|---|---|
| id | 必填，非空，长度 1-32，**全局唯一**（已存在返回 422） |
| name | 必填，非空，长度 1-32 |
| cls | 可选，长度 0-32 |
| trade | 可选，长度 0-32 |
| enroll_date | 可选，格式 YYYY-MM-DD |
| status | 新增时固定 `active`，不接受传入 |
| extra | 可选，任意 JSON 对象，序列化后存 TEXT 列 |

#### 5.3.3 CSV 导入 `POST /api/v1/students/import`

**请求**：`multipart/form-data`，字段名 `file`，上传 `.csv` 文件（UTF-8 编码）。

**CSV 格式**（首行为表头）：

```csv
id,name,cls,trade,enroll_date,remark
S2024001,张明,机修一班,火炮维修,2024-09-01,
S2024002,李华,机修一班,火炮维修,2024-09-01,转校生
```

**处理逻辑**：

1. 解析 CSV（标准库 `csv.DictReader`）；
2. 逐行校验（同 §5.3.2 规则）；
3. 校验通过行执行 `INSERT OR REPLACE`（upsert 语义：工号已存在则覆盖更新）；
4. 单次导入上限 1000 行（插件配置项 `import_max_rows`，可调）；
5. 事务包裹：整批成功才提交，任一行失败则整批回滚并返回错误明细。

**响应 data**：

```json
{
  "success": 48,
  "failed": 2,
  "errors": [
    {"row": 5, "reason": "name 为空"},
    {"row": 12, "reason": "id 格式非法：包含空格"}
  ]
}
```

#### 5.3.4 CSV 导出 `GET /api/v1/students/export`

**Query**：同列表检索（keyword / cls / status），不支持分页（导出全量匹配结果）。

**响应**：

```
Content-Type: text/csv; charset=utf-8
Content-Disposition: attachment; filename="students_20260906.csv"

id,name,cls,trade,enroll_date,status,remark
S2024001,张明,机修一班,火炮维修,2024-09-01,active,
...
```

> 导出包含 `status` 列（便于导出后区分在训/结业），不包含 `extra` / `created_at` / `updated_at`（保持导出文件简洁，字段与导入对称）。

## 六、插件实现

### 6.1 插件类结构（`plugins/student_mgr_plugin.py`）

```python
class StudentMgrPlugin(BasePlugin):
    """学员管理插件"""

    PLUGIN_NAME = "student_mgr"
    PLUGIN_VERSION = "1.0.0"

    def __init__(self, node, config=None):
        super().__init__(node, config)
        self._db_path: str = self.config.get('db_path', 'config/app.db')
        self._page_size_default: int = int(self.config.get('page_size', 20))
        self._page_size_max: int = int(self.config.get('page_size_max', 100))
        self._import_max_rows: int = int(self.config.get('import_max_rows', 1000))
        self._repo: StudentRepo = None

    def _configure_impl(self) -> bool:
        # 执行建表 DDL（幂等）
        self._repo = StudentRepo(self._db_path, self.logger)
        self._repo.init_schema()
        self.logger.info(f"StudentMgr 配置完成: db={self._db_path}")
        return True

    def _activate_impl(self) -> bool:
        # web 路由注册由 web_server 在启动时统一扫描插件并调用 register_routes
        self.logger.info("StudentMgr 激活成功")
        return True
```

### 6.2 仓储层（`components/web/student_repo.py`）

```python
class StudentRepo:
    """学员表 SQLite 仓储"""

    def __init__(self, db_path: str, logger): ...
    def init_schema(self) -> None: ...
    def list(self, keyword='', cls='', status='active',
             page=1, page_size=20) -> dict: ...
    def get(self, student_id: str) -> Optional[dict]: ...
    def create(self, student: dict) -> None: ...
    def update(self, student_id: str, fields: dict) -> None: ...
    def soft_delete(self, student_id: str) -> None: ...
    def bulk_upsert(self, rows: List[dict]) -> None: ...
    def count_by_cls(self) -> dict: ...
```

**实现要点**：

1. 所有方法内部 `sqlite3.connect(self.db_path)` 短连接，`with conn:` 自动事务提交/回滚；
2. `list` 方法构造 WHERE 子句：keyword 命中 name/id/cls 三列 LIKE；cls/status 精确匹配；
3. `bulk_upsert` 用单事务 + `INSERT OR REPLACE` 批量执行，性能优于逐行；
4. `created_at` / `updated_at` 在 create/update 时由仓储层自动填充 `int(time.time()*1000)`。

### 6.3 Web 路由注册（`web_server.py` 改动）

在 `web_server.py` 的路由注册区域新增学员管理路由组。**实现策略**：在 `WebServer` 类中新增 `_register_student_routes()` 方法，于 `setup_routes()` 中调用。

```python
def _register_student_routes(self):
    app = self.app

    @app.get("/students", response_class=HTMLResponse)
    async def students_page(request: Request):
        return self.templates.TemplateResponse("students.html", {"request": request})

    @app.get("/api/v1/students")
    async def list_students(keyword: str = '', cls: str = '',
                            status: str = 'active',
                            page: int = 1, page_size: int = 20):
        repo = self._get_student_repo()
        result = repo.list(keyword, cls, status, page, page_size)
        return {"code": 0, "message": "ok", "data": result}

    @app.get("/api/v1/students/{student_id}")
    async def get_student(student_id: str):
        repo = self._get_student_repo()
        student = repo.get(student_id)
        if not student:
            raise HTTPException(status_code=404, detail="学员不存在")
        return {"code": 0, "message": "ok",
                "data": {"student": student, "recent_reports": []}}

    @app.post("/api/v1/students")
    async def create_student(payload: dict): ...

    @app.put("/api/v1/students/{student_id}")
    async def update_student(student_id: str, payload: dict): ...

    @app.delete("/api/v1/students/{student_id}")
    async def delete_student(student_id: str): ...

    @app.post("/api/v1/students/import")
    async def import_students(file: UploadFile): ...

    @app.get("/api/v1/students/export")
    async def export_students(keyword: str = '', cls: str = '',
                              status: str = 'active'): ...
```

> **`_get_student_repo()` 来源**：插件激活时将 `StudentRepo` 实例挂到 `WebServer` 上（通过 `node` 共享或显式注入）。具体注入路径在实施时根据 `web_server` 与 `plugin_manager` 的现有交互模式确定（参考 `task_controller.py` 与 `status_monitor` 的协作方式）。

## 八、校验与异常处理

### 8.1 输入校验矩阵

| 字段 | 校验规则 | 失败码 |
|---|---|---|
| id | 非空，长度 1-32，正则 `^[A-Za-z0-9_-]+$`，全局唯一 | 422 |
| name | 非空，长度 1-32 | 422 |
| cls | 长度 0-32 | 422 |
| trade | 长度 0-32 | 422 |
| enroll_date | 格式 YYYY-MM-DD（可空） | 422 |
| status | 枚举值（新增不接受传入） | 422 |
| remark | 长度 0-200 | 422 |
| extra | 可解析为 JSON 对象 | 422 |

### 8.2 异常处理策略

| 场景 | 处理 |
|---|---|
| 工号已存在（新增） | 返回 422，message="工号已存在: {id}" |
| 学员不存在（修改/删除/详情） | 返回 404 |
| CSV 解析失败 | 返回 400，message="CSV 格式错误" |
| CSV 行数超限 | 返回 422，message="导入行数超过上限 {import_max_rows}" |
| 数据库操作异常 | 捕获 `sqlite3.Error`，返回 500，日志记录完整堆栈 |
| 导入部分行失败 | 不返回错误码，返回 200 + data 中 errors 明细 |

### 8.3 并发与事务

- 列表查询：只读，无事务需求。
- 单条 CRUD：单事务，失败回滚。
- 批量导入：整批单事务（`BEGIN ... COMMIT/ROLLBACK`），保证原子性。
- 软删除后再新增同工号：`INSERT OR REPLACE` 会覆盖软删除记录并重置为 `active`（符合"恢复"语义）。

### 9.1.1 P1 前置约束：报告接收去重与幂等键

P1 期 `report_recv_plugin` 接收边缘端上报时，**必须按 doc/38 §7.6 幂等约定实现去重**，否则重试会导致同一轮次报告重复入库：

| 约束项 | 约定 | 来源 |
|---|---|---|
| 整包去重键 | `device_id + round.start_ms` | doc/38 §7.6 |
| 增量去重键 | `device_id + round_start_ms + events[].ts` | doc/45 §1 |
| 重试容忍 | 边缘端整包重试 3 次为同一 payload，平台须容忍重复提交 | doc/38 §7.6 |
| 增量丢帧自愈 | touch 端不做队列级重试，下个周期自动全量 diff 补偿 | doc/45 §2 响应说明 |

> **对 P0 的影响**：P0 期 `students` 表的 `id`（工号）必须与边缘端上报 payload 中 `student.id` 严格一致（doc/38 §3），否则 P1 期报告无法按 `student.id` 关联学员档案。本期学员档案的工号编排规则需在部署时与边缘端 `student.id` 命名约定统一对齐。

### 9.1.2 P2 前置约束：步骤瓶颈诊断阈值规则

P2 期 `report_analysis_plugin` 的诊断逻辑**必须严格按需求说明.docx §3.3.3 的 4 类判断阈值实现**，这些阈值是教学建议的客观依据，不可随意调整：

| 诊断类型 | 判断逻辑 | 教官行动建议 | 来源 |
|---|---|---|---|
| 全班性瓶颈 | 某步骤全班平均用时 > SOP标准×1.5 | "该步骤需在下次课重点讲解" | .docx §3.3.3 |
| 顽固性错误 | 某步骤遗漏率 > 30% | "需增加该步骤的专项训练" | .docx §3.3.3 |
| 顺序混乱 | 某步骤顺序错误率 > 20% | "需强调步骤间的依赖关系" | .docx §3.3.3 |
| 学员退步预警 | 最近3次平均分 < 前5次×0.85 | "建议安排个别辅导" | .docx §3.3.3 |

> **P2 实现要求**：
> 1. 上述 4 类阈值需可配置（YAML），默认值即上表，便于不同机型/SOP 调整；
> 2. SOP 标准用时来源：边缘端 `model_a.json` / `model_as.json` 配置（doc/38 §5 steps.duration_ms 为实际用时，SOP 标准需 P2 期另行从 model JSON 解析加载）；
> 3. 每条诊断结果须同时输出"判断依据数据"（如实际平均用时、遗漏率数值）与"教官行动建议文本"，满足产品文档"从数据到行动"的价值主张。

### 9.1.3 P3 前置约束：教学看板模块定义

P3 期 `teaching_dashboard_plugin` 的看板模块**必须按需求说明.docx §3.4 的三模块定义实现**，模块内容与数据来源需在 P2 统计数据基础上聚合：

| 看板模块 | 内容定义 | 数据来源 | 来源 |
|---|---|---|---|
| 今日概览 | 今日考试人数、平均得分、通过率、待辅导学员数 | P2 当日 reports 聚合 | .docx §3.4 |
| 高频错误点TOP5 | 遗漏率/超时率/顺序错误率最高的5个步骤 | P2 步骤级统计排序 | .docx §3.4 |
| 需关注的学员 | 退步预警、波动较大、薄弱环节突出的学员列表 | P2 学员累计统计 + 退步预警 | .docx §3.4 |

> **P3 实现要求**：
> 1. "需关注的学员"列表须可直接点击进入学员详情页（P0 期学员详情页已预留挂载点），形成"看板→诊断→个别辅导"闭环；

> 3. 看板数据实时性要求：今日概览与需关注学员列表 30s 刷新一次（复用现有 WebSocket 主动推送机制，参考 doc/42）。

## 十、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 现有底座无统一 SQLite 访问层 | 仓储层需自建，可能与后续报告插件重复 | 本期 `student_repo.py` 独立实现；后续若报告插件需要 db 访问，再抽象统一 `db` 组件 |

| CSV 大文件导入性能 | 1000 行 + upsert 可能耗时 | 事务内批量 `executemany`，预计 < 2s；超限拒绝 |
| 学员工号命名规范未定 | 数据质量参差 | 本期仅做格式正则校验；命名规范由教官自行约定 |
| 边缘端 student.id 与平台 students.id 不一致 | 报告无法关联学员 | doc/38 已明确 student.id 由边缘端绑定传入；平台侧工号需与边缘端保持一致，部署时由教官统一编排 |
