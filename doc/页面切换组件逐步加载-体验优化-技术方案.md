# 页面切换「组件逐步加载」体验优化技术方案

- 日期：2026-08-26
- 状态：规划（待审核后实施）
- 工程：app_mgr_object-0.2.0(标准版)

---

## 一、问题

切换页面仍存在**组件逐步加载显示**（先仓位后任务后状态…碎片化出现），体验不佳。

## 二、根因分析（代码实勘）

### 根因 1：多页面整页跳转（无状态共享）
- base.html 导航为**整页链接跳转**——切换页面 = 全量 HTML+CSS+JS 重载 + DOMContentLoaded 后所有初始化 API 重新发起；页面间无缓存/状态共享，每次切换都从零开始。

### 根因 2：组件容器无骨架/加载态（主因）
- base.html **无全局 loading/spinner/skeleton**；
- index.html 组件容器（7 个 bay 容器 + agv/task 等）**空容器待 JS 填充**；monitor.html 3 个空 tbody；control 节点卡空；
- 每个组件 = API 完成后才 render 填充 → **按 API 响应顺序逐个出现**（业务快先亮、状态/OPS 慢后亮）→ 碎片化加载观感。

### 根因 3：API 响应时间差异
- 业务接口快（本地）、`/api/status`（2.5s 兜底 + TTL）、OPS 代理（5s 缓存首次仍等）——后出现组件延迟 2-5s；
- 前端拆分（业务先渲染 + 状态异步）**加剧**「逐步出现」（组件分两批亮起）。

## 三、解决思路（体验优化，纯前端零后端）

### P6-1 骨架屏（核心，平滑渐进）
- custom.css 加 `.skeleton`（灰块 + shimmer 动画）+ `.skeleton-row/col`；
- 前端工具 `window.Skeleton = { fill(el, rows, cols), clear(el) }`；
- **各组件容器初始填充骨架**：render 前容器已是骨架行，API 完成 `Skeleton.clear(el)` 替换真实内容——组件就绪即平滑替换，无空白/碎片感；
  - index：bay 区/dest 区/agv 卡/task 表/队列/告警；
  - monitor：nodes/channels/agv 表（tbody 骨架行）；
  - control：节点运维卡（快速操作/下拉/状态表骨架）。

### P6-2 统一加载指示（辅助）
- base.html 加**顶部加载条**（`.top-loader`，CSS 动画，页面切换即显示）；
- 页面主业务加载完成调用 `window.pageLoaded()` 隐藏（骨架替换后）——用户感知「页面就绪」而非碎片等待；
- 状态类后台填充不阻塞加载条隐藏（业务就绪即视为页面可用）。

### P6-3 渲染优先级与分批（已有拆分基础上补骨架）
- 骨架 → 业务组件（快）→ 状态组件（慢）；每批就绪即替换骨架（保持现有拆分，仅补骨架占位）。

### P6-4 页面切换预取/缓存（可选，后续）
- 业务数据 localStorage TTL 缓存 → 切换页秒开旧数据 + 后台刷新（减少等待）；
- **SPA 化**（大改造，后续迭代）：多页 → 单页组件切换，避免整页重载（列入 roadmap）。

## 四、开发步骤

1. custom.css：.skeleton 系列（灰块 shimmer）；
2. base.html：顶部加载条 + `window.pageLoaded()` 约定；
3. dashboard.js：render 前容器骨架化（bay/dest/agv/task/queue/alarm）；主业务完成后 pageLoaded；
4. monitor.js：nodes/channels/agv tbody 骨架行；主数据就绪 pageLoaded；
5. control.js/内联：节点卡骨架；
6. 验证：切换页面 → 骨架即刻显示（无白屏/碎片）→ 业务组件平滑替换 → 加载条隐藏；状态后台填充。

## 七、假设

- 纯前端改动（骨架+加载条），零后端；不影响现有数据流；
- SPA 化/预取缓存为后续迭代（本方案先解决「碎片化加载」体验）。
