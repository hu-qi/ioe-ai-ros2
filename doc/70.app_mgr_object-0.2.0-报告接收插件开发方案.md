## 1. 背景与目标

### 1.1 背景

需求说明.docx §3.2 明确"报告管理"为教官操作端核心功能：自动接收并存储边缘端上报的每一份操作报告，实现可追溯、可复查、可导出。

边缘端通过两套协议上报数据：

- **doc/38 schema 1.0（整包）**：轮次结束时 POST `/api/v1/reports`，含完整事件流、步骤明细、子步骤明细、未执行清单。
- **doc/45 schema 1.1（订阅 + 实时增量）**：平台先 POST `/api/v1/subscriptions` 订阅设备 → 边缘端轮询订阅状态 → 订阅 active 后步骤变化时 POST `/api/v1/events` 上报增量事件 → 平台可 DELETE 退订停止实时上报。

本插件负责**接收并存储这两路数据**，是教官操作端数据汇聚的唯一入口。

### 1.2 目标

开发 `report_recv_plugin`，实现：

1. 接收 doc/38 整包报告，解析入库（reports / report_details / events / substeps 四张表）；
2. 接收 doc/45 增量事件，追加到对应轮次的事件流（增量 + 整包事件流去重合并）；
3. 实现 doc/45 §4 订阅管理接口（订阅 / 查询状态 / 退订 / 设备列表，支持多设备同时订阅）；
4. 接收 doc/45 §6 evidence 抓拍图（multipart 存储）；
5. 按去重键实现幂等（整包 `device_id + round.start_ms`，增量 `device_id + round_start_ms + events[].ts`）；
6. 报告检索（按学员 / 设备 / 时间 / 完成率多条件）与报告详情查看；
7. 原始 JSON 完整留存，支持未来深度分析。

> **联调优先策略**：本插件分两子阶段开发（详见 §8.0）。**P1a 联调最小集优先开发**，目标是跑通"边缘端真机 → 平台"完整数据链路（整包接收 + 多设备订阅管理 + 增量接收 + 报告详情），与边缘端真机联调验证。联调通过后补全 **P1b 完整接收层**（evidence 接收、实时进度快照、事件流合并器、原始 JSON 落盘、步骤/子步骤明细入库）。

### 1.3 范围与边界

| 维度 | 本期 P1 | 不做 |
|---|---|---|
| 数据接收 | doc/38 整包 + doc/45 增量 + evidence | 边缘端改造（边缘端已有上报能力） |
| 订阅管理 | doc/45 §4 全部接口 | 主动发起订阅（由教官在 UI 操作触发） |
| 数据存储 | reports / report_details / events / substeps 四表 + 原始 JSON 文件留存 | 统计计算（归 P2 统计插件） |
| 检索 | 报告列表多条件筛选 + 报告详情 | 统计图表、诊断建议（归 P2/P3） |
| 实时推送 | 增量事件通过 event_bus 发布 `report.realtime_delta`，web 层 WebSocket 推送 | 前端看板实时展示（归 P3 看板插件） |

> **关键决策**：不单独做"边缘端对接插件"。对接逻辑（HTTP 端点接收 + 订阅管理 + 增量合并）全部内聚到本插件，因为这些都是 `reports` 数据域的输入环节。理由详见 doc/69 问答讨论与既有插件按数据域内聚的惯例（status_poller / smart_trigger 等均读写同域数据）。

```

   │
   ├──POST /api/v1/reports ──────────→ report_recv_plugin
   │   (doc/38 整包，轮次结束触发)       │ 解析 → 入库 reports/report_details/events/substeps
   │                                    │ 去重键: device_id + round.start_ms
   │                                    │ 原始 JSON 落盘留存
   │                                    ↓
   ├──POST /api/v1/events ───────────→ event_merge → 追加到该轮 events 流
   │   (doc/45 增量，步骤变化时)        │ 去重键: device_id + round_start_ms + events[].ts
   │                                    │ 发布 event_bus: report.realtime_delta
   │                                    ↓
   ├──POST /api/v1/evidence ─────────→ evidence 存储（按 device_id/round_start_ms 分目录）
   │   (multipart 抓拍图)
   │
   ├──POST /api/v1/subscriptions ────→ 订阅登记（设备级 active 状态）
   ├──GET  /api/v1/subscriptions/{id}→ 订阅状态查询（边缘端轮询用）
   ├──DELETE /api/v1/subscriptions ──→ 退订（停止该设备增量上报）
   │
   └──(教官端检索) GET /api/v1/reports?student_id=&device_id=&limit=&offset=
                   GET /api/v1/reports/{report_id}
```

### 2.3 与 P0 学员管理插件的协作（软关联，可独立部署）

**核心定位**：报告接收插件**不硬依赖学员管理插件**，可独立部署运行。边缘端上报的数据无条件接收入库，学员关联做"事后软关联"。

**独立运行依据**（对接文档佐证）：

- doc/38 §3 明确 `student` 可为空对象 `{}`："平台按'未绑定'归档"——即边缘端未绑定学员也照常上报，平台照常接收；
- doc/38 §3 `student.source` 有 `manual / csv / scan / rfid` 多种来源，平台不预先知道边缘端会用哪种绑定方式；
- 报告数据本身完整（events/steps/substeps/用时/得分），不依赖学员档案即可独立存储、检索、统计。

**软关联机制**：

| 场景 | 入库行为 | student_bound 值 |
|---|---|---|
| student 为空对象 `{}` | 照常入库，student_id=NULL | false（未绑定） |
| student.id 在 students 表**存在** | 照常入库，student_id=边缘端传入值 | true（已关联） |
| student.id 在 students 表**不存在** | 照常入库，student_id=边缘端传入值 | false（未关联档案，可能是教官还没录入，或边缘端传了未登记工号） |
| 后续教官补录学员档案 | 可通过 `student_bound=false` 的报告反查回溯关联（本期不做自动回溯，仅标记） | — |

**与 P0 的协作边界**：

| 协作点 | 方式 |
|---|---|
| 软关联查询 | 入库时查 `students` 表判断 `student.id` 是否存在，仅用于设置 `student_bound` 标记，**不阻塞入库** |
| 学员档案查询 | 本插件**不直接读 students 表做业务逻辑**，仅做"存在性检查"设置标记；教官端检索报告时走 reports 表冗余字段（student_name/student_cls），不依赖 students 表 |
| 删除学员影响 | P0 采用软删除（status=deleted），报告关联不受影响，历史报告仍可查 |
| 独立部署 | P1 可在 P0 未部署时独立运行；学员管理未上线时，所有报告 student_bound=false，不影响接收入库 |

> **跨插件读库的合法性**：既有 `smart_trigger_plugin` 跨插件读 `task_cache` 数据做触发判断，本插件跨插件读 `students` 表做存在性检查（仅设置标记，不阻塞主流程），符合既有底座"同库跨插件读"的惯例。

## 3. 数据模型与建表

### 3.1 DDL（`config/reports_schema.sql`）

```sql
-- 报告主表：一轮操作的元信息
CREATE TABLE IF NOT EXISTS reports (
    report_id           TEXT    PRIMARY KEY,   -- 平台生成：R{device_id}_{round_start_ms}
    device_id           TEXT    NOT NULL,
    student_id          TEXT,                   -- 关联 students.id；未绑定=NULL
    student_name        TEXT,                   -- 冗余存边缘端上报时的 name（学员删除后仍可追溯）
    student_cls         TEXT,                   -- 冗余存 cls
    student_bound       INTEGER NOT NULL DEFAULT 0,  -- 0=未关联/未绑定 / 1=已关联 students 表
    process_name        TEXT,
    process_type        TEXT,                   -- disass / assembly（由前端推断，doc/38 §6）
    finish_reason       TEXT,                   -- completed / manual / timeout / reset
    is_stub             INTEGER NOT NULL DEFAULT 0,  -- 0=完整 / 1=存根（增量先到，待整包补全）
    start_ms            INTEGER NOT NULL,       -- 轮次起点（引擎单调绝对 ms，doc/45 §5）
    end_ms              INTEGER,                -- 轮次终点（引擎单调绝对 ms）
    duration_ms         REAL,                   -- 用时（= end_ms - start_ms，引擎可能输出小数 ms）
    process_elapsed_ms  INTEGER,                -- 操作用时（引擎单调差值，doc/58 统一计时）
    total_score         REAL,                   -- 综合得分（doc/38 §7 后续扩展字段）
    raw_json_path       TEXT,                   -- 原始 JSON 文件留存路径
    ts_upload_ms        INTEGER NOT NULL,       -- 上报时刻（epoch ms，唯一墙钟时间）
    created_at          INTEGER NOT NULL
);

-- 步骤聚合表：8 步骤级元信息
CREATE TABLE IF NOT EXISTS report_steps (
    report_id       TEXT    NOT NULL,
    idx             INTEGER NOT NULL,       -- 步骤序号 1..8
    name            TEXT,
    state           INTEGER,                -- 0 未开始 / 1 进行中 / 2 完成 / 3 跳过
    start_ms        INTEGER,                -- 步骤起始（引擎单调绝对 ms，doc/58 v1.1）
    end_ms          INTEGER,                -- 步骤结束（引擎单调绝对 ms，doc/58 v1.1）
    duration_ms     REAL,                   -- 步骤用时 ms（首子步骤 start ~ 末子步骤 end）
    interval_ms     REAL,                   -- 与上一步间隔（= 本步 start - 上步 end，doc/58 v1.1）
    PRIMARY KEY (report_id, idx),
    FOREIGN KEY (report_id) REFERENCES reports(report_id)
);

-- 子步骤明细表：全局连续子步骤
CREATE TABLE IF NOT EXISTS report_substeps (
    report_id       TEXT    NOT NULL,
    idx             INTEGER NOT NULL,       -- 子步骤全局序号 1..N
    name            TEXT,
    state           INTEGER,
    start_ms        INTEGER,                -- 子步骤起始（引擎单调绝对 ms，doc/58 v1.1）
    end_ms          INTEGER,                -- 子步骤结束（引擎单调绝对 ms，doc/58 v1.1）
    duration_ms     REAL,                   -- 最近一次片段用时 ms
    count           INTEGER,                -- 操作片段数（>1=重复/中断重入）
    total_duration_ms REAL,                 -- 全部片段累计用时 ms
    timeout         INTEGER,                -- 0/1 bool
    PRIMARY KEY (report_id, idx),
    FOREIGN KEY (report_id) REFERENCES reports(report_id)
);

-- 事件流表：原子级时序事件（START/COMPLETE/INTERRUPT/TIMEOUT/FINISH_EOF/FINISH_EIO）
CREATE TABLE IF NOT EXISTS report_events (
    report_id       TEXT    NOT NULL,
    ts              INTEGER NOT NULL,       -- 相对轮次起点偏移 ms（= 引擎绝对 ts - round_start_ms）
    kind            INTEGER NOT NULL,       -- 0..5（doc/38 §4 + doc/45 §3）
    step            INTEGER,
    sub             INTEGER,
    source          TEXT    DEFAULT 'batch',-- batch=整包 / delta=增量
    PRIMARY KEY (report_id, ts, kind, sub), -- 天然去重键
    FOREIGN KEY (report_id) REFERENCES reports(report_id)
);

-- 实时进度快照表：增量上报携带的进度状态（供看板实时展示）
CREATE TABLE IF NOT EXISTS report_progress (
    report_id           TEXT    PRIMARY KEY,
    device_id           TEXT    NOT NULL,
    done                INTEGER,                -- 已完成子步骤数
    total               INTEGER,                -- 总子步骤数
    current             TEXT,                   -- 当前进行中子步骤名（空串=无进行中）
    current_sub_index   INTEGER,                -- 当前进行中子步骤全局序号（0=无进行中）
    process_elapsed_ms  INTEGER,                -- 本批上报时刻操作用时（引擎单调差值）
    last_delta_ts       INTEGER,                -- 最近一次增量事件 ts（相对偏移）
    updated_at          INTEGER NOT NULL,       -- 最近增量上报时刻（epoch ms）
    FOREIGN KEY (report_id) REFERENCES reports(report_id)
);

-- 订阅状态表：设备级订阅管理
CREATE TABLE IF NOT EXISTS subscriptions (
    device_id       TEXT    PRIMARY KEY,
    active          INTEGER NOT NULL DEFAULT 0,  -- 0/1
    note            TEXT,
    subscribed_at_ms INTEGER,
    updated_at_ms   INTEGER
);

-- 索引
CREATE INDEX IF NOT EXISTS idx_reports_device   ON reports(device_id);
CREATE INDEX IF NOT EXISTS idx_reports_student  ON reports(student_id);
CREATE INDEX IF NOT EXISTS idx_reports_start    ON reports(start_ms);
CREATE INDEX IF NOT EXISTS idx_reports_upload   ON reports(ts_upload_ms);
CREATE INDEX IF NOT EXISTS idx_progress_device  ON report_progress(device_id);
```

> **统一计时字段说明（doc/58 v1.1 落地）**：
> 1. `reports.process_elapsed_ms`：引擎单调差值（= 操作用时），与 `/disass_status.process_elapsed_ms` 同口径，用于"实时→归档"时间序列衔接；
> 2. `report_steps.start_ms/end_ms/interval_ms` 与 `report_substeps.start_ms/end_ms`：均为引擎单调绝对 ms，与整包 doc/38 v1.1 字段一一对应；
> 3. `report_events.ts`：相对 `round_start_ms` 的偏移 ms（= 引擎绝对 ts − round_start_ms），与增量 doc/45 §2 同口径；
> 4. `report_progress` 表：存储增量上报携带的 `progress` 与可选 `process_elapsed_ms` 字段，供 P3 看板实时展示学员操作进度。`current_sub_index` 为 doc/45 v1.1 新增可选字段，缺省 0。

### 3.2 去重与幂等策略

| 数据类型 | 去重键 | 机制 | 来源 |
|---|---|---|---|
| 整包报告 | `device_id + round.start_ms` | reports 表查询同 device_id + start_ms，存在则跳过（幂等） | doc/38 §7.6 |
| 增量事件 | `device_id + round_start_ms + events[].ts` | report_events 表 PRIMARY KEY (report_id, ts, kind, sub) 天然去重，INSERT OR IGNORE | doc/45 §1 |
| 重试容忍 | 整包重试 3 次同一 payload | 平台按去重键判断已存在则直接返回成功 | doc/38 §7.6 |
| 增量丢帧自愈 | touch 端不做队列级重试 | 下个周期全量 diff 补偿，平台 INSERT OR IGNORE 容忍重复 | doc/45 §2 |

### 3.3 原始 JSON 留存策略

- 路径：`config/data/reports/{device_id}/{report_id}.json`
- 时机：整包入库时同步落盘
- 用途：完整保留边缘端原始 payload，支持未来深度分析、数据回溯校验
- evidence 抓拍图：`config/data/evidence/{device_id}/{round_start_ms}/sub_{sub}_ts_{ts}.jpg`

## 4. 接口规范

### 4.1 路由总览

所有接口遵循 doc/38/45 的 `/api/v1/` 命名规范，复用主 web 端口（与 P0 学员管理插件同端口）。

| 方法 | 路径 | 功能 | 协议来源 |
|---|---|---|---|
| POST | `/api/v1/reports` | 接收整包报告 | doc/38 §1 |
| GET | `/api/v1/reports` | 报告列表检索 | 需求说明.docx §3.2 |
| GET | `/api/v1/reports/{report_id}` | 报告详情 | 需求说明.docx §3.2 |
| POST | `/api/v1/events` | 接收增量事件 | doc/45 §2 |
| POST | `/api/v1/subscriptions` | 订阅设备 | doc/45 §4.1 |
| GET | `/api/v1/subscriptions/{device_id}` | 查询订阅状态 | doc/45 §4.2 |
| DELETE | `/api/v1/subscriptions/{device_id}` | 退订设备 | doc/45 §4.3 |
| GET | `/api/v1/subscriptions` | 订阅设备列表 | doc/45 §4.4 |
| POST | `/api/v1/evidence` | 接收抓拍图 | doc/45 §6 |

### 4.2 接收整包报告 `POST /api/v1/reports`

**请求体**：doc/38 §2 完整 payload（schema_version / device_id / edge_node / ts_upload_ms / student / round）。

**处理流程**：

1. 校验必填字段（schema_version / device_id / edge_node / ts_upload_ms / student / round）；
2. 生成 `report_id = R{device_id}_{round.start_ms}`；
3. 去重检查：查 reports 表同 device_id + start_ms，已存在则直接返回成功（幂等）；
4. **软关联标记**：从 payload.student 取 id/name/cls 存入 reports 表冗余字段；若 student.id 非空，查 students 表判断是否存在，设置 `student_bound`（存在=1，不存在=0）；student 为空对象时 student_id=NULL、student_bound=0。**此步骤不阻塞入库，students 表不存在时照常入库**；
5. 解析 round 内 events / steps / substeps，分别入库；
6. 原始 JSON 落盘 `config/data/reports/{device_id}/{report_id}.json`；
7. 发布 event_bus 事件 `report.received`（供统计插件订阅）。

**响应**（doc/38 §1 期望格式）：

```json
{ "code": 0, "message": "ok", "data": { "report_id": "Rdev01_1787569113000" } }
```

### 4.3 接收增量事件 `POST /api/v1/events`

**请求体**：doc/45 §2 event_delta payload（schema 1.1）。

**处理流程**：

1. 校验 schema_version=1.1、type=event_delta、必填字段（device_id / round_start_ms / events / progress）；
2. 按 `device_id + round_start_ms` 定位或创建对应 report 记录（增量可能先于整包到达）；
3. events 数组逐条 `INSERT OR IGNORE` 到 report_events 表（source=delta），天然去重；
4. 更新 `report_progress` 表：写入/刷新 `done` / `total` / `current` / `current_sub_index`（可选，缺省 0）/ `process_elapsed_ms`（可选，缺省 NULL）/ `last_delta_ts`（本批最大 events[].ts）/ `updated_at`（当前 epoch ms）；
5. 发布 event_bus 事件 `report.realtime_delta`（含 device_id / round_start_ms / progress / events），供 web 层 WebSocket 推送。

> **doc/45 v1.1 可选字段处理（对齐 doc/58 统一计时）**：
> - `process_elapsed_ms`：引擎单调差值，存 `report_progress.process_elapsed_ms`，用于实时看板展示"已用时 X 秒"；缺省 NULL。
> - `progress.current_sub_index`：当前进行中子步骤全局序号，存 `report_progress.current_sub_index`，用于看板高亮当前子步骤；缺省 0。
> - 上述可选字段"缺省即不影响主链路"（doc/45 §2），本插件按 NULL/0 存储，前端按缺省值渲染。

**响应**（doc/45 §2）：

```json
{ "code": 0, "message": "ok", "data": { "device_id": "dev01", "delta_events": 2 } }
```

### 4.4 订阅管理（doc/45 §4 四接口）

| 接口 | 关键逻辑 |
|---|---|
| POST `/api/v1/subscriptions` | 按 device_id upsert subscriptions 表，active=1，记录 subscribed_at_ms |

        增量事件合并逻辑：

## 6. 关键实现细节

### 6.1 增量先于整包到达的处理

时序问题：边缘端可能先上报增量事件，整包（轮次结束时）后到。

**处理策略**：

1. 增量到达时，按 `device_id + round_start_ms` 查 reports 表；
2. 若不存在，`get_or_create_report_stub()` 创建存根记录（finish_reason=NULL，end_ms=NULL，student 信息从增量 payload 取）；
3. 整包到达时，`reconcile_full_report()` 补全存根的 finish_reason / end_ms / duration_ms / 完整 student 信息，并 INSERT OR IGNORE 整包 events（与已存 delta 事件去重合并）。

### 6.2 实时增量事件到前端的推送链路

```
边缘端 POST /api/v1/events
    ↓
report_recv_plugin 入库
    ↓
event_bus.publish('report.realtime_delta', {device_id, round_start_ms, progress, events})
    ↓
web 层订阅该事件 → ConnectionManager.broadcast_json() → WebSocket 推送到前端看板
```

**复用既有机制**：web_server.py 已有 `ConnectionManager` 与 WebSocket 广播能力（参考现有 `/ws` 端点），本插件只需发布事件，推送由 web 层统一处理。

### 6.3 evidence 抓拍图存储

- 接收：`POST /api/v1/evidence`，multipart/form-data（file + sub + ts + device_id）
- 存储：`{evidence_dir}/{device_id}/{round_start_ms}/sub_{sub}_ts_{ts}.jpg`
- 触发条件：边缘端仅在 `evidence_forward=true` 且 `capture_on_timeout=true` 时发送（doc/45 §6）
- 关联：通过 device_id + round_start_ms 关联到对应 report

### 6.4 多设备并发处理

- 每个边缘端 device_id 独立上报，平台按 device_id 分别归档（doc/45 §1）；
- SQLite 写锁并发：整包入库用单事务，增量事件用 INSERT OR IGNORE 批量，预计并发 < 10 设备，SQLite 足够；
- 若后续设备数增长，可切换 WAL 模式（`PRAGMA journal_mode=WAL`）提升并发读。

### 6.5 时钟口径与统一计时（对齐 doc/45 §5、doc/58）

**核心原则**：引擎内部时间轴为单调毫秒（steady_clock since boot），平台**严禁将引擎单调数值与墙钟 epoch 混减**（只有差值才有意义）。

**三处时间字段同源**（doc/58 统一计时）：

| 字段 | 口径 | 存储列 |
|---|---|---|
| `round.start_ms` / `round_start_ms` | 引擎单调绝对 ms（轮次起点） | `reports.start_ms` |
| `events[].ts` | 相对 round_start_ms 偏移 ms（= 引擎绝对 ts − round_start_ms） | `report_events.ts` |
| `process_elapsed_ms` | 引擎单调差值（操作用时） | `reports.process_elapsed_ms` / `report_progress.process_elapsed_ms` |
| `steps[].start_ms/end_ms` | 引擎单调绝对 ms | `report_steps.start_ms/end_ms` |
| `steps[].interval_ms` | 与上一步间隔（= 本步 start − 上步 end） | `report_steps.interval_ms` |
| `substeps[].start_ms/end_ms` | 引擎单调绝对 ms | `report_substeps.start_ms/end_ms` |

**墙钟时间**：仅 `ts_upload_ms` 为真实 epoch 毫秒，用于按日检索/展示。**推荐做法**：以"相对时间线"入库（round_start_ms + events[].ts），另存 `ts_upload_ms` 作 wall 参考。

**增量与整包的时间衔接**：

1. 增量 `events[].ts` 与整包 `round.events[].ts` 同口径（均为相对 round_start_ms 偏移），可直接合并去重；
2. 增量 `process_elapsed_ms` 与整包 `round.process_elapsed_ms` 同口径，实时过程可显示"已用时 X 秒"，整包到达后用整包值覆盖（更精确）；
3. 增量 `progress.current_sub_index` 与整包 substeps 序号对齐，看板可据此高亮当前子步骤。

> **对齐方法（doc/56 新字段）**：平台可从整包 round（或最后一次 /disass_status 快照）取 `step/substep_start_ms·end_ms` 与事件流合并还原每一步的真实起止与间隔（步骤 i 完成时刻 → 步骤 i+1 开始时刻间隔见 `round.steps[].interval_ms`），实时过程可用增量 `progress.current_sub_index` + `/disass_status` 的 `substep_start_ms` 定位当前动作起点。

| 场景 | 处理 |
|---|---|

| 增量事件重复提交 | INSERT OR IGNORE 静默跳过，返回 delta_events=0 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 增量先于整包到达，存根报告状态不完整 | 前端可能在整包到达前看到半完整报告 | 存根报告标记 `is_stub=true`，前端展示"数据接收中"状态；整包到达后自动补全 |
| 多设备并发写入 SQLite 锁竞争 | 高并发时写入延迟 | 启用 WAL 模式；若设备数 > 20 考虑迁移至 PostgreSQL |
| 增量事件丢帧 | 事件流不完整 | doc/45 已明确"下个周期全量 diff 补偿"，平台 INSERT OR IGNORE 容忍重复，丢帧由边缘端自愈机制保证 |
| 原始 JSON 文件增长占用磁盘 | 长期运行磁盘满 | 配置保留策略（如保留 90 天），定期清理；或压缩归档 |
| evidence 图片存储路径冲突 | 同一 ts + sub 重复写入覆盖 | 文件名包含 device_id + round_start_ms + sub + ts，保证全局唯一 |
