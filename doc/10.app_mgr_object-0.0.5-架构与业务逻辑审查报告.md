### 2.2 依赖规则

- **向下依赖**: 上层插件通过 `self.node.xxx_plugin` 或 `plugin_manager.get_plugin()` 获取下层插件实例
- **横向通信**: 通过 EventBus 发布/订阅事件实现松耦合
- **生命周期**: 按 `plugin_load_order` 顺序依次 configure → activate
- **线程模型**: 上层同步调用下层方法（如 `rcs_adapter.bind_ctnr_and_bin()` 为同步 HTTP 调用），由调用方（workflow_engine）在 asyncio 协程中调用

## 5. 业务逻辑完整流

### 5.1 自动搬运任务完整流水线（42 步）

```
步骤 ── 插件 ── 动作
─────────────────────────────────────────────────────────────
 1     AI 推理节点         → 发布 BayStatus 消息
 2     bay_status_fusion    → 收到话题消息
 3     bay_status_fusion    → 遍历 msg.channels → channel.areas
 4     bay_status_fusion    → AreaStatusFilter.update(has_cargo)
 5     bay_status_fusion    → 连续 3 帧有货 → 稳定确认
 6     bay_status_fusion    → BayCache.set_binding(bay_id)
 7     bay_status_fusion    → rcs_adapter.bind_ctnr_and_bin()
 8     rcs_adapter           → POST /bindCtnrAndBin
 9     bay_status_fusion    → 成功 → BayCache.set_bound()
10     bay_status_fusion    → publish('bay.bound')
─────────────────────────────────────────────────────────────
11     smart_trigger        → 收到 bay.bound → _scan_once()
12     smart_trigger        → TriggerEngine.scan(cargo_type)
13     smart_trigger        → AND 条件：已绑定 + 空终点 + 空闲叉车 + 工作窗口
14     smart_trigger        → ResourceLocker.lock() 原子锁定
15     smart_trigger        → publish('trigger.task_created')
─────────────────────────────────────────────────────────────
16     workflow_engine      → 收到 trigger.task_created
17     workflow_engine      → engine.create_instance('agv_transport_atomic')
18     workflow_engine      → WorkflowInstance.run()
19     workflow_engine      → 状态: calling_rcs → _action_invoke_gen_task
20     workflow_engine      → rcs_adapter.gen_task(context)
21     rcs_adapter           → POST /genAgvSchedulingTask
22     workflow_engine      → 记录 rcs_task_no → 'rcs_ack_ok'
23     workflow_engine      → calling_rcs → monitoring
24     workflow_engine      → _action_wait_for_completion → 挂起
─────────────────────────────────────────────────────────────
25     RCS 系统              → HTTP POST /agvCallback
26     callback_handler      → _on_agv_callback() → publish('rcs.agv_callback')
27     event_bridge          → _on_rcs_agv_callback()
28     event_bridge          → task_status=9 → 'callback_completed'
29     event_bridge          → engine.inject_event(task_code, 'callback_completed')
30     workflow_engine      → monitoring → releasing
31     workflow_engine      → _action_release_resources
32     workflow_engine      → publish('workflow.resources_released')
33     workflow_engine      → RobotCache.set_idle(robot_id)
34     workflow_engine      → releasing → completed
35     workflow_engine      → _action_publish_completed
36     workflow_engine      → publish('workflow.task_completed')
37     workflow_engine      → 持久化到 SQLite
─────────────────────────────────────────────────────────────
38     smart_trigger        → 收到 workflow.task_completed
39     smart_trigger        → release_task_resources()
40     smart_trigger        → _scan_once() → 寻找下一个任务
```

### 5.2 异常处理路径

| 异常场景 | 处理链 |
|:---|:---|
| AI 抖动误触 | `AreaStatusFilter` 防抖 3 帧确认 → 不触发绑定 |
| RCS 绑定失败 | `BayCache.set_unbound()` 回滚 → 等待下次 AI 检测 |
| 任务下发失败 | `_action_invoke_gen_task` 返回 `rcs_ack_fail` → 状态转移至 `failed` |
| 回调超时（10 分钟） | `monitoring` → `compensating_query` → 主动 `queryTaskStatus` |
| 补偿查询确认失败 | `rcs_failed` → `manual_intervention` → 发布 `workflow.task_needs_manual` |
| AGV 异常 / 告警 | `warnCallback` → `event_bridge` → `callback_exception` → `manual_intervention` |
| 双车抢单 | `ResourceLocker.lock()` 原子检查 → 返回 `False` 阻止分配 |
| 断电恢复 | `WorkflowEngine.recover_all()` 从 SQLite 恢复未完成实例 |

## 9. 架构优势分析

### 9.1 分层解耦优势

**四层架构带来的直接收益**:

| 优势 | 体现 | 具体影响 |
|:---|:---|:---|
| **独立演进** | 每层可独立修改 | 例如 RCS 接口升级 V3.3→V4.0，只需修改 `rcs_adapter` 和 `rcs_http_client`，上层代码无感知 |
| **故障隔离** | 单层异常不扩散 | `rcs_adapter` 网络超时不导致 `bay_status_fusion` 崩溃（仅绑定失败回滚） |
| **测试独立性** | 组件层无 ROS2 依赖 | `BayCache` / `RobotCache` 等可用纯 `pytest` 单元测试，无需 ROS2 环境 |
| **并行开发** | 4 个 Phase 可独立并行 | 不同开发者同时开发 rcs_adapter、fusion、workflow、trigger，接口契约确定后互不阻塞 |

### 9.2 插件生命周期统一性

**BasePlugin 模式带来的工程一致性**:

- 11 个插件全部继承 `BasePlugin`，遵循 `configure → activate → deactivate → cleanup` 四阶段生命周期
- `PluginManager` 按 `plugin_load_order` 顺序统一管理
- 每个插件通过 `_configure_impl() → _activate_impl() → _deactivate_impl() → _cleanup_impl()` 四个钩子实现业务逻辑
- 新增插件只需实现 4 个钩子 + 定义 `PLUGIN_NAME` 和 `PLUGIN_VERSION`，零样板代码

### 9.3 双通道通信模型的灵活性

系统同时使用两种通信方式，各取所长：

| 通信方式 | 适用场景 | 优势 |
|:---|:---|:---|
| **直接调用**（`self.node.rcs_adapter.method()`） | 同步请求-响应（如 RCS HTTP 调用） | 零延迟、强类型、调用链可追踪 |
| **EventBus 发布/订阅** | 异步通知（如 `bay.bound`、`task_completed`） | 解耦发布者和订阅者、支持多订阅者、可动态注册/注销 |

这种混合模式避免了"全部走事件总线"的过度设计，也避免了"全部直接调用"的紧耦合。

### 9.4 YAML 驱动的状态机

**workflow 组件的 YAML 定义带来了业务可配置性**:

- 工作流定义（`agv_transport_atomic.yaml`）与执行引擎（`WorkflowInstance`）分离
- 新增搬运流程类型只需新增一个 YAML 文件，无需修改 Python 代码
- 状态转移逻辑在 YAML 中可视化：`states → transitions → on_enter/on_exit actions`
- Action 函数通过 `ActionRegistry` 按名称注册，YAML 中按名称引用

**示例**: 如果要新增一个"双点位搬运"流程（起点 A→中转点 B→终点 C），只需新建一个 YAML 文件，注册新的 Action 函数即可。

### 9.5 防抖滤波的工程化设计

`bay_status_fusion` 的 AI 信号处理链路体现了工业级设计：

```
AI 原始信号 (逐帧) → AreaStatusFilter (滑动窗口) → 稳定判断 → 触发绑定
```

- 每个仓位独立 `AreaStatusFilter` 实例，互不干扰
- `stable_threshold=3, timeout=2.0` 可配置，适应不同场景
- 降级兼容：自定义消息未编译时自动切换 JSON 模式

### 9.6 内存缓存 + SQLite 持久化的双重存储策略

| 存储层 | 用途 | 特性 |
|:---|:---|:---|
| **内存缓存** (task_cache) | 高频读写（微秒级） | `threading.RLock` 线程安全、`__slots__` 优化内存 |
| **SQLite** (persistence) | 断电恢复 + 审计 | WAL 模式支持并发读写、`ON CONFLICT DO UPDATE` 保留原始创建时间 |

### 9.7 超时补偿 + 人工兜底的韧性设计

工作流状态机中设计了三级容错：

```
正常路径: calling_rcs → monitoring → releasing → completed
           └─ 回调超时 10min ──→ compensating_query ──→ releasing
                                   └─ 查询失败 ──→ manual_intervention ──→ Web 人工处理
```

- **L1 自动恢复**: 回调超时 → 主动查询 RCS（`compensating_query`）
- **L2 人工介入**: 查询也失败 → 进入 `manual_intervention` 终态，等待运维人员通过 Web 操作
- **L3 断电恢复**: 启动时 `recover_all()` 从 SQLite 恢复所有未完成实例

## 10. 优化建议

### 10.1 高优先级（建议近期实施）

#### 建议 1: 添加插件健康检查机制

**现状**: 各插件仅在 `_activate_impl` 中做一次连通性检查，运行期间无主动健康探针。

**建议**: 在 `BasePlugin` 中增加 `health_check()` 方法 + 可选的 ROS2 Timer 定期自检：

```python
class BasePlugin:
    def start_health_check(self, interval: float = 30.0):
        """启动定期健康检查（子类重写 _health_check_impl）"""
        self._health_timer = self.node.create_timer(
            interval, self._health_check_wrapper
        )
    
    def _health_check_impl(self) -> bool:
        """子类重写：返回 True 表示健康"""
        return True
```

**预期收益**: 可在 Web 面板上实时查看各插件健康状态，超时时自动告警。

#### 建议 2: 完善 setup.py 中 data_files 的 config 文件安装

**现状**: `glob('config/*.yaml')` 只匹配一级 `.yaml`，遗漏 `db_schema.sql` 和 `config/workflows/agv_transport_atomic.yaml`（详见 `11.app_mgr_object-0.0.5-setup安装部署分析报告.md`）。

**建议**: 按 §5.2 方案拆分为三个独立 `data_files` 条目，确保所有 config 文件被正确安装。

**预期收益**: `workflow_engine` 能正确加载工作流定义，避免 `load_definitions()` 返回 0。

#### 建议 3: 运行时路径改用 get_package_share_directory()

**现状**: `workflow_engine_plugin` 的 `definitions_dir` 和 `db_path` 使用相对路径。

**建议**: 使用 `ament_index_python.packages.get_package_share_directory('app_mgr_object')` 获取安装后的绝对路径。

**预期收益**: 安装部署到任意位置后路径自动正确。

#### 建议 4: task_instances.db 移至用户可写目录

**现状**: 数据库路径默认在 `share/` 下的只读目录。

**建议**: 使用 `~/.app_mgr_object/task_instances.db` 或 `APP_MGR_DB_PATH` 环境变量指定。

**预期收益**: 生产环境可正常写入。

### 10.2 中优先级（建议下个迭代实施）

#### 建议 5: 增加工作流实例的超时全局监控

**现状**: 每个实例独立管理自己的超时，但无法从外部感知某个实例已超时。

**建议**: 在 `WorkflowEngine` 中增加 `_timeout_monitor` 协程，每秒扫描所有活跃实例，超过全局最大执行时间（如 30 分钟）的实例自动 `inject_event('global_timeout')`。

**预期收益**: 防止因事件桥异常导致实例永久挂起。

#### 建议 6: 增加 RCS 接口调用指标收集

**现状**: 每次 RCS HTTP 调用只有日志，无可量化的成功/失败/延迟统计。

**建议**: 在 `rcs_adapter` 中增加轻量指标收集（成功次数、失败次数、平均延迟），暴露到 `get_status()`。

```python
class RCSAdapterPlugin:
    def __init__(self, ...):
        self._metrics = {
            'gen_task_ok': 0, 'gen_task_fail': 0,
            'bind_ok': 0, 'bind_fail': 0,
            'query_ok': 0, 'query_fail': 0,
            'total_latency_ms': 0, 'call_count': 0,
        }
```

**预期收益**: Web 面板可展示 RCS 接口健康度仪表盘。

#### 建议 7: 为 trigger 扫描增加优先级和限流

**现状**: 扫描循环遍历 6 种货物类型，每次成功触发后可能在同一轮中创建多个任务。

**建议**: 
1. 增加 `max_tasks_per_scan` 限制（默认 2），防止一次扫描创建过多任务
2. 支持 cargo_type 优先级排序（如类型 1、2 优先于 5、6）

**预期收益**: 避免资源瞬间被占满，支持业务优先级调度。

#### 建议 8: params.yaml 配置热加载

**现状**: 配置在启动时读取一次，修改后需重启生效。

**建议**: 在 `ParamManager` 中增加文件监控（`watchdog` 或 `inotify`），检测 `params.yaml` 变化后自动调用各插件的 `configure(config)` 方法热更新。

**预期收益**: 工作时间窗口、防抖阈值、轮询间隔等参数可在 Web 上修改后即时生效。

### 10.3 低优先级（建议远期考虑）

#### 建议 9: 增加 Web 端任务流程图可视化

在 `web_monitor` 的 `tasks.html` 中，用流程图形式展示每个工作流实例的当前状态和转移路径，高亮当前所在状态节点。

#### 建议 10: 增加 RCS 回调重放保护

当前 RCS 回调到达后直接注入工作流实例。如果 RCS 因网络重试重复发送同一回调，可能导致状态机异常。建议在 `event_bridge` 中增加最近 N 秒内的回调去重（基于 `task_code + task_status`）。

#### 建议 11: 组件层单元测试补充

`task_cache/` 和 `trigger/` 组件包无 ROS2 依赖，可直接用 `pytest` 编写单元测试：
- `test_bay_cache.py` — 测试并发读写、bind_status 状态机
- `test_trigger_engine.py` — 测试 AND 条件匹配、资源锁定与释放
- `test_resource_locker.py` — 测试并发锁竞争
