## 一、总体架构概览

### 1.1 定位

`app_mgr_object` 是一个 **ROS2 (Humble) 应用底座节点**（节点名 `app_mgr_object`），承载「AI 智能教学分析平台」的后端：

- **向下对接**：RCS（机器人调度系统，HTTP）、AI 视觉节点（ROS2 话题）、边缘端设备（HTTP 报告/证据上传）；
- **向上提供**：Web 服务（Flask，端口 9183，页面 + REST API + WebSocket）；
- **内部组织**：管理器（base/）+ 插件（plugins/）+ 组件（components/）三层，以「事件总线 + 生命周期状态机 + 独立 YAML 配置」为骨架。

## 二、启动流程与生命周期（main.py + LifecycleManager）

### 2.1 AppMgrNode 初始化序列（main.py L34-79）

严格按序执行 9 步：

1. **创建事件总线** `EventBus()`（L40，先于一切，插件经 `node.event_bus` 获取）；
2. **初始化六大管理器** `_init_base_managers()`（L81-97）：ParamManager / LifecycleManager / PluginManager / ServiceManager / SubscriptionManager / TimerManager，且六个管理器自身也注册进 LifecycleManager（L91-95，可被统一停用）；
3. **启动后台 asyncio 事件循环**（L46-53）：新建 loop 由 daemon 线程 `run_forever` 驱动，供插件 `run_coroutine_threadsafe` 投递协程；
4. **配置日志级别** `_configure_logging()`（L99-111）：按参数 `log_level` 映射 LoggingSeverity；
5. **取插件配置** `_get_plugin_configs()`（L113-122）：来源 `plugin_configs` 参数（ParamManager 已从 `config/plugin_configs/*.yaml` 目录装载，文件名=插件名），字符串则 YAML 兜底解析；
6. **发现插件** `_discover_plugins()`（L125-130）：`plugin_manager.discover('app_mgr_object.plugins')`；
7. **按序加载插件** `_load_plugins_in_order(configs)`（L132-165）；
8. **注册生命周期** `_register_plugins_to_lifecycle(configs)`（L178-198）：加载成功者注册为 `plugin_<name>`，`auto_activate = config.get('auto_start', True)`；
9. **configure 全部 → activate 全部**（L201-208）。

**插件加载顺序与依赖**（L132-176）：

- 顺序取自参数 `plugin_load_order`（逗号分隔字符串，ParamManager 解析为列表）；未配置则回退 `configs.keys()`；
- 特殊豁免：`web_monitor` 即使不在 configs 中也允许以空配置加载（L147-151，其配置由自身读取 `config/web_monitor.yaml`）；
- 依赖检查 `_check_dependencies()`（L169-176）：读插件配置 `dependencies` 列表，逐项检查 `plugin_manager.get_plugin(dep)` 实例是否已加载；任一未加载 → 该插件跳过。**依赖检查是"线性顺序 + 实例存在性"检查，配置依赖环或顺序颠倒会导致插件被静默跳过**（error 日志）。

**运行与关闭**（`main()` L218-269）：

- `MultiThreadedExecutor` 在独立 daemon 线程 spin（L244-246）；
- SIGINT/SIGTERM 信号处理只停 executor，不 `sys.exit`（L226-234），主线程自然退出；
- `finally`：`node.shutdown()`（→ `lifecycle_manager.shutdown()`，先 deactivate 全部再 cleanup 全部）→ `destroy_node()` → `rclpy.shutdown()`（RuntimeError 忽略，防重复）。

### 2.2 LifecycleManager 状态机（base/lifecycle_manager.py，302 行）

仿 ROS2 Managed Node 生命周期，对注册模块统一编排：

```
UNCONFIGURED ──configure()成功──> INACTIVE ──activate()成功──> ACTIVE
     │                                │                           │
     │ (异常/失败)                     └──deactivate()成功──────────┘
     ▼                                            │
   ERROR <──────────异常/失败──────────────┘
                                        INACTIVE ──cleanup()──> FINALIZED
```

- 状态枚举（L12-18）：`UNCONFIGURED / INACTIVE / ACTIVE / FINALIZED / ERROR`；
- 每模块独立状态（`self._modules[name]['state']`，L31），系统级状态 `self._state`（L27）；
- **关键方法**：

| 方法 | 行号 | 要点 |
|---|---|---|
| `register_module(name, module, auto_activate=False)` | L36-44 | `auto_activate` 决定批量 activate 是否包含该模块 |
| `configure(name=None)` | L46-82 | 单个：有 `configure()` 则调用→INACTIVE；无该方法直接置 INACTIVE；异常→ERROR。不传 name：配置全部模块，全部成功系统才置 INACTIVE |
| `activate(name=None)` | L84-125 | 单个：**必须当前为 INACTIVE**（L94），调用 `module.activate()`→ACTIVE。批量：仅激活 `auto_activate=True` 的模块 |
| `deactivate(name=None)` | L127-166 | 状态非 ACTIVE 仅警告不阻断；成功→INACTIVE |
| `cleanup(name=None)` | L168-201 | 调 `module.cleanup()`（有则调）→FINALIZED |
| `shutdown()` | L203-213 | 依次 deactivate + cleanup 全部 |
| `get_health_status()` | L226-242 | `{system_state, modules:{...}, healthy}`；任一模块 ERROR → healthy=False |
| `get_module_status(name)` | L244-268 | 模块状态 + 合并模块自身 `get_status()` 返回 dict |
| `add_state_change_callback()` | L283-293 | ⚠️ 状态变更回调机制存在，但 configure/activate/deactivate 内部**并未实际调用** `trigger_state_change`，回调仅能被外部手动触发 |

**插件侧约定**：BasePlugin 的 `activate()` 在未 configure 时会**先自动 configure**（base_plugin.py L73-76），因此生命周期编排对插件是容错的。

### 2.3 ServiceManager（base/service_manager.py，145 行）

- `create_service(srv_type, name, callback)`（L30-70）：创建 ROS2 服务并登记 `{name: {service, srv_type, callback, created_at}}`，重名先 remove 再建；
- `create_trigger_service(...)`（L72-101）：包装回调（wrapped_callback L77-91），用于触发类服务；
- `get_service / get_all_services / remove_service / remove_all_services`（L103-137）：查询与卸载（remove 调 `destroy_service`）；
- `get_status()`（L139-145）：服务数量与清单摘要。

## 三、六大基础管理器

### 3.1 ParamManager（base/param_manager.py，691 行）—— 参数与配置中枢

职责：ROS2 参数声明/读取/回调分发 + 独立 YAML 配置体系 + 原子化热加载持久化。是全系统最重的底座文件。

**初始化流程**（`__init__` L38-60）：

1. `_declare_common_parameters()`（L64-132）：声明 ~33 个通用参数（dry_run、log_level、network 系列、request 系列、QoS 系列、`plugin_configs_dir='config/plugin_configs'`、`web_monitor_config='config/web_monitor.yaml'`、`plugin_load_order` 等）；`plugin_load_order` 逗号分隔字符串解析为列表（L107-114）；字符串值尝试 JSON→YAML 解析（L117-124）；
2. `_load_external_configs()`（L136-159）：
   - **目录模式**：`_load_plugin_configs_from_dir`（L161-195）遍历 `config/plugin_configs/*.yaml`，**文件名（去 .yaml）= 插件名**，汇总进 `_params['plugin_configs']`；
   - **单文件模式**：加载 `web_monitor.yaml`（L152-159，`_load_config_from_file` L197-222）；
   - 相对路径基准：`_get_pkg_share_dir()`（L224-233，ament 失败回退 cwd）；
3. `_setup_param_callback()`（L237-241）：注册 `node.add_on_set_parameters_callback`，外部 `set_parameters` 时自动解析 JSON 并分发 `register_param_callback` 注册的回调（`_on_parameters_changed` L243-262）。

**参数读写**：`get_param(name, default)`（L268-282，内存 `_params` 优先，miss 落 ROS2 参数并回填缓存）；`get_all_params()` L284；`update_param()` L287-294（走 `node.set_parameters`）。

**热加载核心 `update_plugin_config_nested(path, value)`**（L298-378）——Web 端改配置的落盘主通道，以 `path=['bay_status_fusion','bay_configs']` 为例七步：

1. `plugin_name = path[0]`（L312-316）；
2. 定位目标 YAML `_get_plugin_config_file`（L380-385）→ `<configs_dir>/<plugin_name>.yaml`，文件必须存在；
3. 读取 + `copy.deepcopy`（L326-331）；
4. 沿 `path[1:-1]` 导航到父节点，**同时支持 dict key 与 list 整数索引**（L333-343）；
5. 写叶子节点（同样支持 list 下标，L345-354）；
6. `_write_yaml_atomic` **原子写回**（临时文件 + replace，L357）；
7. 更新内存 `_params['plugin_configs'][plugin_name]`（L362-363）→ `_notify_plugin_config_changed`（L387-406）：触发注册在 `'plugin_configs'` 上的参数回调（插件按各自 key 分发处理，见 §5.9 web_monitor 热加载）。

### 3.2 SubscriptionManager / TimerManager / ros2_logger

- `SubscriptionManager`：ROS2 订阅的统一创建/登记/销毁（`create_subscription(topic, msg_type, callback, qos)` → 登记表，`remove_*` 统一 `destroy_subscription`），插件用它创建话题订阅便于运维期统一清理；
- `TimerManager`：ROS2 定时器统一管理（`create_timer(period, callback)` 登记、销毁），插件周期任务（轮询/扫描）统一经此创建，避免插件散落自持 timer 句柄；
- `ros2_logger.py`：`get_logger(name, node=None)` 统一日志工厂（0.1.3 统一日志方案），全代码库日志入口收敛于此，级别由 ParamManager 的 `log_level` 控制。

### 3.3 ServiceManager

（已在 §2.3 详述）`create_service / create_trigger_service / remove_service(s)` 共 11 个方法，管理 ROS2 服务全生命周期并登记状态。

## 四、事件总线与跨插件事件流

### 4.1 EventBus（plugins/event_bus.py）

进程内发布/订阅，是插件间解耦通信的唯一通道（插件互不 import，只依赖 node.event_bus）：

- `subscribe(event_type, callback)` / `unsubscribe`（L20-31）：RLock 保护的 `{event_type: [callback]}` 表；
- `publish(event_type, data)`（L33-55）：**同步发布**——拷贝监听器列表锁外执行；协程回调自动探测（`asyncio.iscoroutinefunction`）：有运行中 loop 则 `create_task`，无则 `asyncio.run`；单回调异常仅 error 日志不中断其他监听者；
- `async_publish()`（L57-87）：异步版——同步回调丢线程池（`run_in_executor`）、协程回调直接 await，`asyncio.gather(*, return_exceptions=True)` 并发执行互不阻塞；
- `clear()`（L89-92）：清空全部监听器。

### 4.2 事件类型全景

| 事件 | 发布方 | 订阅方 | 用途 |
|---|---|---|---|
| `bay.bound` / `bay.status_changed` / `bay.unbound` | bay_status_fusion | event_bridge、rcs_adapter | 仓位绑定状态流转 → Web 推送/告警 |
| `rcs.agv_callback` / `rcs.warn_callback` / `rcs.bind_notify` | callback_handler | event_bridge、相关缓存同步 | RCS 推送 → 缓存/告警/推送 |
| `workflow.task_started` / `workflow.task_completed` / `workflow.task_failed` | workflow_engine / 各 action | task_monitor、event_bridge | 任务生命周期 → 轮询启动/停止、看板 |
| `report.received` | report_recv | scoring_plugin | 整包报告 → 触发评分 |
| `report.scored` | scoring_plugin | event_bridge | 评分完成 → Web 推送 |
| `report.realtime_delta` | report_recv | teaching_dashboard | 增量事件 → 看板 WebSocket 实时转发 |
| `plugin.configured/activated/deactivated/cleaned` | BasePlugin | event_bridge | 插件生命周期 → 监控页 |
| `alarm.*` | alarm_manager | event_bridge | 告警产生/确认 → Web WS 推送 |

### 4.3 全链路数据流总览

```
AI 视觉 (ROS2 /ai_bay_status)
   └─> BayStatusFusionPlugin ──bay.status_changed / bay.bound / bay.unbound──> EventBus
          └─(稳定有货, 防抖 debounce_threshold=3)──> rcs_adapter.bind_ctnr_and_bin ──HTTP──> RCS

RCS 轮询: StatusPollerPlugin ──3s/10s 定时器──> rcs_adapter.query_agv_status / query_pod_berth_and_mat
   └─> RobotCache（AGV 状态） / DestBayCache（货架货位, pairing_policy）

RCS 推送: HTTP POST /eyeSky/robot/reporter/{agvCallback|warnCallback|bindNotify}
   └─> CallbackHandlerPlugin ──rcs.agv_callback / rcs.warn_callback / rcs.bind_notify──> EventBus
          └─(bind_notify)──> BayCache + DestBayCache 双向同步

触发: SmartTriggerPlugin [2s 扫描线程, sys_config.trigger_scan_interval]
   ├─候选: BayCache 有货未锁定仓位（货物类型优先级 → bay_id 字典序）
   ├─配对: DestBayCache.select_by_strategy（巷道规则 L1 始发仓 > L2 货型 > L3 默认 + fifo/filo）
   ├─选车: round_robin / specified（未实现 least_busy 校验）
   └─派发: workflow_engine.create_instance("agv_transport_atomic", ctx)

状态机: WorkflowEnginePlugin (config/workflows/agv_transport_atomic.yaml)
   calling_rcs → monitoring → releasing → completed
   分支: warn_pause / compensating_query / manual_intervention / failed / auto_recovery
   ├─超时: _timeout_monitor_loop 5s 扫描 → trigger(iid, 'timeout')
```

### 5.1 网络与对接类

**network_plugin.py — NetworkPlugin**
网络自适应组件装配：加载 `components/network/`（http_adapter / interface_manager / network_utils）。`HttpAdapter` 统一 requests Session（连接池/重试/超时，参数取自 ParamManager 的 network/request 系列）；`InterfaceManager` 网卡状态监测（多网卡环境选择出口）；`network_utils.generate_signature` 完整 HMAC-SHA256→MD5[:16] 签名算法（出站方向，`enable_signature` 默认 false 未启用）。

**rcs_adapter_plugin.py — RcsAdapterPlugin**
RCS HTTP 客户端适配层，封装 `components/rcs_client/`：
- `rcs_http_client.py`：统一出站 HTTP（经 HttpAdapter），自动附带 token；
- `rcs_payload_builder.py`：构造 RCS 请求报文（下发搬运任务 genTask / 查询 AGV 状态 / 查询货架货位 / 容器绑定 / 继续任务）；
- `rcs_response_parser.py`：解析响应。注意 AGV 状态语义（L69-74）：**RCS 状态 1 和 4 都映射为 AVAILABLE**（4=空闲可调度，刻意业务语义）；
- `components/token/`：`AuthClient` 登录获取 token → `TokenManager` 自动续期（过期前刷新）→ `TokenStorage` 本地持久化；
- 对外方法（供其他插件经 `get_plugin('rcs_adapter')` 调用）：`bind_ctnr_and_bin`、`query_agv_status`、`query_pod_berth_and_mat`、`continue_task(rcs_no)` 等。

**callback_handler_plugin.py — CallbackHandlerPlugin**
接收 RCS 主动推送：在 **aiohttp** 上启动回调 HTTP 服务（`components/callback/`），路由基路径 `/eyeSky/robot/reporter/{agvCallback|warnCallback|bindNotify}`（routes.py；⚠️ params.yaml 写的 `/api/callback` 与之不一致，实际以 callback_handler.yaml 为准）。`receiver.py` 验签（utils.validate_signature 为 TODO 占位恒 True）→ 解析 models.py 数据结构 → 发布 `rcs.agv_callback` / `rcs.warn_callback` / `rcs.bind_notify` 事件；bind_notify 触发 BayCache + DestBayCache 双向同步。注意 `status_query.py` / `channel_status_query.py` 两个 Handler 全代码库无实例化调用，属遗留/待接线代码。

**status_poller_plugin.py — StatusPollerPlugin**
RCS 状态周期轮询：定时器 3s 轮询 `query_agv_status` → 写 `robot_status` 表 + RobotCache；10s（dest 轮询 60s）轮询 `query_pod_berth_and_mat` → 更新 DestBayCache（reserved 仓位忽略外部置空）。同时持有 `HotReloadRegistry` 注册项：`pairing_policy` → `dest_cache.set_pairing_policy`（热加载在此侧生效）。

**task_monitor_plugin.py — TaskMonitorPlugin**
任务状态按需轮询 + 自动闭环（v2.0）：订阅 `workflow.task_started/completed/failed`；有活跃实例时以 10s 周期调 TaskStatusMonitor（components/task_monitor/monitor.py）轮询 RCS 任务状态码（`FINAL_STATES={7,8,9}`，状态 9 → `callback_completed` 注入引擎）；`manual_intervention` 挂起实例 30s 周期轮询，RCS 侧恢复则注入 `auto_resolved` / `auto_failed` 实现自动闭环。`_count_active_tasks` 读 `workflow_engine.list_instances`。

**bay_status_fusion_plugin.py — BayStatusFusionPlugin**

## 六、组件层详解

### 6.1 task_cache/ —— 三大资源缓存 + 状态协调器（调度正确性的核心）

**RobotCache**（robot_cache.py，AGV 状态缓存与选车）
- 由 status_poller 轮询维护；`select_policy()`（L116-134）热加载 `{round_robin | least_busy | specified}` + `available_statuses`（默认 `('AVAILABLE',)`）+ `specified_ids`；
- `get_available_robot()`（L150-171）：round_robin 游标 `_next_index` 轮询；least_busy 取 update_time 最小（空闲最早）；specified 取指定编号列表命中第一个；`has_idle_robot()` L184。

**BayCache**（bay_cache.py，起始仓位缓存）
维护起始仓实时状态（与 `source_bay_status` 表同步）：`mark_in_task(bay, True/False)` 任务期锁定仓位防重复派发；`get_cargo_bays/get_all_bays/get_empty_bays_of_type(cargo_type)` 供触发器候选收集。

**DestBayCache**（dest_bay_cache.py，L54-400，终点仓位 + 配对策略）
- 条目 `DestBayCacheEntry`（L25）：bay_id/cargo_type/floor_no/lane/is_empty/update_time/source/revision；
- **保留占用机制（匹对稳定的核心，doc/51 幽灵锁定修复）**：`self._reserved: {bay_id: queued|matched|dispatched}`（L71）；`update()`（L87-102）中 reserved 仓位**忽略外部轮询置空**（L97-98）；`mark_occupied()` L252（派发即占用）；`release_occupied(bay_id, set_empty, source)`（L267-286）：任务失败/取消→`set_empty=True` 回空；任务完成→保留 is_empty=False 由 RCS 轮询接管；`source='unbind'` 记录 `_unbind_released` 蓝色标记（解绑后可再匹配）；
- **前端四色状态** `get_bay_state()`（L297-311）：reserved（橙）> unbind（蓝）> occupied（灰黑）> empty（绿）；
- **配对策略** `set_pairing_policy()`（L157-213）：解析 lanes/type_rules/bay_rules/default_strategy 重建 `_lanes/{lane_id: Lane}`、`_bay_lane`；`_resolve_rule()`（L220-250）**三级回退**：bay_rules（L1 始发仓精确）> type_rules（L2 货物类型）> 类型匹配巷道+default（L3）；
- **选位** `select_by_strategy(cargo_type, src_bay, exclude)`（L334-366）：无巷道配置回退字典序最小空位；`lane_state_management=True` 走 `_max_occupied_next_slot()`（L313-332，巷道最大真实占用索引 n → 候选 = n+1 起第一个真实空位，reserved 不算真实占用）；否则 `pairing_policy.select_slot`（fifo/any/nearest 取最小索引、filo/lifo 取最大索引，pairing_policy.py:55）。未找到返回 None，**不降级任意空位**。

**ConfigCache**（config_cache.py，L24-113）
Web 可动态修改的业务配置热缓存：`get_sys/get_int/get_float/set_sys`（L50-73）；source/dest 仓位-货物类型映射（L77-95）；`schedules` 工作时间窗（ScheduleEntry：day_of_week/start_time/end_time，L16-21、L99-110）。

**StateCoordinator**（state_coordinator.py，L8-114，统一资源联动入口）
- `dispatch_task(robot_id, src_bay, dst_bay, task_id)`（L19-37）：`locker.lock()`（冲突返回 False）→ 清除该 task_id 历史释放记录（支持同 id 重试）→ `bay_cache.mark_in_task(src, True)` → `robot_cache.set_busy(robot, task_id)` → `dest_cache.mark_occupied(dst, source='dispatched')`；
- `release_task(task_context, force=False)`（L39-64）：**幂等**（`_released_task_ids` 集合）；
- `_release_task_impl()`（L66-89）：locker.release + src 释放 + robot 置 idle + dst 分流：`status ∈ {failed,cancelled,aborted,error}` → `release_occupied(set_empty=True)`；否则 `set_empty=False` + `update(is_empty=False, source='task_complete')`（货已到位由 RCS 接管）；
- `get_snapshot()` L100 / `reset_release_state()` L95。

## 九、核心业务链路

### 9.1 AGV 搬运任务全链路（调度域主线）

```
[1] 感知：AI 视觉 /ai_bay_status ──> BayStatusFusion 防抖(3次) ──> BayCache + source_bay_status
     └─ 稳定有货 → rcs_adapter.bind_ctnr_and_bin（RCS 绑定，token 鉴权）
[2] 状态同步：
     ├─ 轮询：StatusPoller 3s AGV / 10s 货架（dest 60s）→ RobotCache / DestBayCache
     └─ 推送：RCS → /eyeSky/robot/reporter/* → CallbackHandler → rcs.* 事件 → 缓存同步
[3] 触发：SmartTrigger 2s 扫描 → 候选(货型优先级+bay_id 序) → 配对(巷道 L1>L2>L3)
     → 选车 → workflow_engine.create_instance("agv_transport_atomic", ctx)
[4] 状态机：calling_rcs(RCS 下发 genTask) → monitoring(轮询任务状态)
     → releasing(StateCoordinator.release_task) → completed
     异常分支：warn_pause / compensating_query / manual_intervention(人工) / failed
     ├─ 超时兜底：引擎 5s 扫描注入 timeout
     └─ 自动闭环：TaskMonitor 10s/30s 轮询 → auto_resolved/auto_failed
[5] 资源释放：StateCoordinator.release_task（幂等）：
     失败/取消 → 目的仓回空；完成 → 保留占用由 RCS 接管
[6] 展示：business_collector 快照 hash 变更 → WS business_update → 前端四色仓位图
```

### 9.2 教学报告链路（教学域主线）

```
边缘端设备 ──POST /api/v1/events(增量)──> EventMerge 合并(存根→补全) ──report.realtime_delta──> 看板 WS
          ──POST /api/v1/reports(整包)──> insert_full_report ──report.received──> ScoringPlugin
          ──POST /api/v1/evidence(BMP)──> 落盘+登记 ──> EvidenceConverter(BMP→JPG+缩略图)
ScoringEngine 四系数评分 → save_scoring_result 回写 ──report.scored──> WS
AnalysisRepo 统计(缓存 TTL 300s) → DiagnosisEngine 六类诊断(关联证据图) → 教学调整 verify
DashboardRepo 看板聚合(dashboard 缓存 86400s) → /api/v1/dashboard/*
```

### 9.3 评分模型（scoring_rules.yaml）

- **子步骤得分** = `max_score × 用时系数 min(1, std/actual) × 正确性系数(完成1.0/进行中0.5/未执行0/中断0.5) × 顺序系数(正确1.0/错误0.7)`；超时再 × `timeout_penalty 0.5`；无 std 时用时系数=1.0；规则回退链 `processes[name].substeps[idx] → default(max_score 10)`；
- **整轮**：累计 − 未执行×2 − 重复×1；`finish_reason ∈ (timeout,3)` 总分 ×0.9；下限 0；
- **等级**：≥90 优秀 / ≥75 良好 / ≥60 合格 / else 不合格；
- 顺序错误检测：各子步骤首个 START 事件序 vs idx；
- 拆解 8 子步骤标准用时 12/8/15/10/9/12/14/11 s，组装 8 子步骤 15/10/9/12/13/11/10/12 s。

### 9.4 任务操作（task_controller.task_control）

| action | 逻辑 |
|---|---|
| `query` | 先 `engine.get_instance_snapshot(task_id)`，无则查 DB（archived） |
| `retry` / `cancel` | 注入引擎事件 user_retry / user_cancel（⚠️ 依赖不存在的 `engine.inject_event`，见 §11） |
| `force_trigger` | 校验/自动分配 AGV（robot_cache.get_available_robot，须 AVAILABLE）→ 生成 `WEB_{ms}` 任务号 → `state_coordinator.dispatch_task` 锁资源（失败回滚 release_task）→ `engine.create_instance('agv_transport_atomic', ctx)` |
| `continue` | 取实例 `rcs_task_no` → `rcs_adapter.continue_task(rcs_no)` |

## 十一、关键发现与风险点（改进建议清单）

1. **`engine.inject_event` 不存在**：TaskController.retry/cancel 与 task_monitor 自动闭环均经 `asyncio.run_coroutine_threadsafe(engine.inject_event(...))` 注入事件，但 WorkflowEnginePlugin 只有同步 `trigger`——Web 恢复与自动闭环链路实际不可用，是当前最高优先级断层。
2. **smart_trigger 与热加载断层**：web_monitor 热加载 handler 引用的 `trigger._trigger_engine/_config_cache` 属性不存在（AttributeError/空转）；`_dest_bay_cache` 为 None 导致 **pairing_policy 不在 smart_trigger 派发路径生效**（只能 bay_cache 降级字典序匹配）；`aging_ttl/队列老化/src_scan_order 非 by_bay_id_asc` 均未实现。
3. **回调基路径不一致**：params.yaml `/api/callback` vs callback_handler.yaml 与 routes.py 的 `/eyeSky/robot/reporter`，以 callback_handler.yaml 实际装配为准，建议统一。
4. **验签占位**：callback/utils.validate_signature TODO 恒 True（入站未验签）；出站 network_utils.generate_signature 完整但 `enable_signature: false`。
5. **遗留未接线代码**：status_query.py / channel_status_query.py 无实例化调用；workflow YAML 的 `on_error[]` 引擎未消费。
6. **LifecycleManager 状态回调未触发**：`trigger_state_change` 定义了但生命周期转换处未调用。
7. **笔误**：hot_reload.py L47 `self.logger = section`（register 时覆盖 logger）。
8. **AGV 可用性校验缺口**：smart_trigger._select_agv 未用 robot_cache/available_statuses 校验（task_controller.force_trigger 有校验）；rcs_response_parser 把 RCS 状态 1 和 4 都映射 AVAILABLE（刻意语义，注释与常量不一致易误读）。
9. **并发模型**：MultiThreadedExecutor + 后台 asyncio loop + 多插件自有线程（触发扫描/监控/超时扫描）并存；EventBus 同步 publish 在订阅者线程内执行回调，慢回调会阻塞发布方，重回调应使用 async_publish 或自行入队。
10. **双库分布**：调度域 `/data/task_manager.db` 与教学域 `app_mgr_object/config/app.db` 分离；教学域 repo 全部短连接 + WAL，高频写入需关注 IO。
