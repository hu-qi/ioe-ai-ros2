## 一、需求

用户可能需要根据生产编号变更**始发仓位/目的仓位名称与类型**，期望在**前端界面**直接修改编排。

## 二、数据流实勘（权威源确认）

### 2.1 rtsp 节点是名称+类型源头（用户判断正确）
- **名称**：`polygon_chX_names` 参数（rtsp 节点）——area_config 组件读取（area_assembler.cpp L12/L29）+ **热更新**（`on_area_config_changed` L26-37，param set 后实时生效）；
- **类型**：`bay_cargo_types.<bay_id>` 参数（rtsp 节点）——话题 cargo_type = `get_cargo_type(bay_id)`（bay_status_publisher.cpp L45）+ **热重载**（yolov8_inference_plugin.cpp L479-488：bay_cargo_types.* 参数 set 实时生效）；
- **话题**：`/dev01_object_status` 发布 `bay_id + has_cargo + cargo_type`（BayStatusPublisher，bay_id=area.name）。

### 2.2 app_mgr 订阅（话题为准）
- bay_status_fusion_plugin 订阅话题：`bay_id = area.bay_id`、`cargo_type = area.cargo_type`（**来自话题**）→ BayCache 更新；
- `bay_status_fusion.yaml bay_configs`（A1001:1 等）**仅作启动初始/校验**——话题到达后以话题为准（与 rtsp bay_cargo_types 重复，非权威）。

### 2.3 OPS 已具备修改通道（P4 已实现）
- app_mgr `/api/calibration/set_param` 已代理 OPS → ParamProxy.set（原生 rclpy + subprocess 回退，**支持任意参数含数组 polygon_chX_names**）→ rtsp 节点热加载。

## 三、推荐方案：前端仓位编排界面

### 3.1 入口与界面
- index.html 仓位区加「**仓位编排**」按钮 → 新增 `bayArrangeModal`：
  - 表格列出全部仓位（通道 / 当前名称 / 类型 1-6），名称可编辑文本框、类型下拉（对齐现有 bayEditModal 风格）；
  - 保存/重置按钮；说明文案「修改将写入 rtsp 节点参数（权威源），app_mgr 自动同步」。

### 3.2 保存链路（零后端新增——复用 P4 代理）

```
前端 bayArrangeModal 保存
  → 名称：按通道聚合 → POST /api/calibration/set_param {name: 'polygon_chX_names', value: [新名称数组]}
  → 类型：逐仓 → POST /api/calibration/set_param {name: 'bay_cargo_types.<bay_id>', value: type}
  → OPS ParamProxy.set → ros2 param set /rtsp_multi_inference → rtsp 热加载
  → 话题 /dev01_object_status 重发新 bay_id/cargo_type
  → app_mgr bay_status_fusion 自动更新（BayCache）→ 前端 business_update 刷新
```

### 3.3 前端实现
- api.js：`setCalibrationParam(name, value)`（POST /api/calibration/set_param，P4 已代理）；`getCalibrationParam(name)`（GET inference_param/{name}）；
- dashboard.js：
  - 打开 modal：读 6 通道 `polygon_chX_names`（OPS 权威）+ 类型（话题 business_update 数据或 bay_cargo_types.*）；
  - 保存：名称按通道整数组 set（**仅改名称文本，不增删数量**——polygon_chX_points 关联不变，安全）；类型逐仓 set（热重载）；
  - 成功后 toast + 重新 loadAllData（business_update 自动到达）。
- index.html：bayArrangeModal（表格 + 保存/重置）。

### 3.4 app_mgr 配置去重
- `bay_status_fusion.yaml bay_configs` 保留为**启动初始/校验**，注释标注「名称/类型权威 = rtsp 节点参数（polygon_chX_names / bay_cargo_types），话题为准自动同步；此处仅降级初始」；
- 不删除（降级安全），但文档明确非权威。

## 六、假设与边界

- 仓位名称修改仅文本（数量与 polygon_chX_points 绑定，增删名称需同步改 points——本方案不做增删，仅改名）；

- cargo_type 来自 rtsp bay_cargo_types 映射（非 AI 实时识别类别）；若未来类型由 AI 类别决定，本方案映射仍可热更新；
- app_mgr bay_configs 保留降级（话题为准）。

## 十、改名后前端仍显示旧名——修复（2026-08-26）

### 10.1 问题
仓位名改为 A1000 后（rtsp polygon_chX_names 已更新、话题 bay_id=A1000），前端仍显示 A1001；再次操作报「未找到仓位 A1001 所在通道」。

### 10.2 根因
- `renderBayGrid` / `renderDestGrid` 用**硬编码仓位 id 列表**（BAY_GROUP_MAP / DEST_FLOOR_MAP）渲染：话题 bay_id 改 A1000 后 `bayMap['A1001']` 不存在 → 渲染空 idle cell 显示旧名；A1000 不在固定列表 → 永不渲染；
- BayCache 后端动态 OK（`_ensure_entry` 自动接受新键）——问题纯在前端渲染层；
- 报错链：改名成功 → 前端按固定列表渲染旧名空壳 → 再点旧名读通道找不到（rtsp 已新名）。

### 10.3 修复
1. **renderBayGrid/renderDestGrid 动态化**：按话题 bays 渲染（名称以话题为准）——起始仓按前缀 A/B/C/D 分组填区、目的仓按 T2/T3/T4；无法匹配依序补位（6 格/区）；无数据回退默认 ids 占位；
2. **名称修改同步 bay_configs 键**（可选）：改名成功后 getConfigBay → 删旧键加新键 → setConfigBay——保持显示定义/badge 可用。

### 10.4 验证
1. 改名 A1001→A1000 → 话题 A1000 → 前端立即显示 A1000（区域正确），无 A1001 空壳；
2. 连续改名正常（读通道找当前名），无「未找到」报错；
3. 前缀分组正确；生产编号无前缀依序填充；
4. 目的仓改名同理；bay_configs 键同步；回归。

## 十一、修改仓位名称操作流程与方法（修复"改名后新增仓位"，2026-08-26）

### 11.1 问题
前端修改仓位名称后**自动增加了一个名称的仓位**（未实现修改反而新增）；前端名称应来源于 rtsp 话题适配，app_mgr 定义名称和类型驱动显示。

### 11.2 根因
- rtsp 热更新正确（`on_area_config_changed` clear+重建，替换非追加）；
- "新增"根因在**前端链路缺校验**：①set 数组长度未校验（若 OPS get 结构异常/解析错 → 数组长度 ≠ points 长度 → rtsp area 重建异常 → 话题多仓位）；②set 后无读回校验（原生 set 失败走 ros2 CLI 格式差异 → 误报成功）；③改名后再次操作读不到旧名。

### 11.3 正确流程（原子化单仓，三步校验）
```
前端改名 A1001→A1000
  ① 读通道 GET polygon_chX_names（6 通道）→ 定位 + 校验数组合法（Array.isArray）
  ② 替换 + 长度校验：新数组长度 == 原长度（不等拒绝）
  ③ set（OPS 透传原生 rclpy → ros2 param set 降级）
  ④ 读回校验：GET 该通道 → 含新名、不含旧名、长度一致 → 成功；否则报错重试
  ⑤ 同步 app_mgr 显示定义：bay_configs 键删旧加新（setConfigBay）
```

### 11.4 防御增强
- 前端：set 前长度校验；set 后读回校验；话题 bays 数量 > channel_count×4 → 渲染防御提示；
- 后端：OPS param set 读回一致性（前端读回）；ros2 CLI 数组 yaml 格式（ParamProxy 已有）。

### 11.5 app_mgr 显示定义同步
- bay_configs（yaml）改名后 setConfigBay 删旧加新（热加载）——等价 "ros2 param set 改 app_mgr"（内部配置机制）；
- 显示链路：名称 = rtsp 话题（polygon_chX_names → /dev01_object_status bay_id）；显示类型/定义 = app_mgr bay_configs 驱动前端。

### 11.6 验证
1. 改 A1001→A1000：读回校验通过 → 前端立即显示 A1000（无残留/重复）；
2. 连续改名正常；长度异常拒绝；set 后读回失败明确报错；
3. bay_configs 键同步；回归。


### 11.7 实施记录（2026-08-26）
- **dashboard.js 三步校验**：
  1. 名称有效性（非空、不与其他仓位重名）；

## 十三、改名后前端仍显示旧名并新增仓位——运行时缓存根因分析（2026-08-26）

> 用户指示：rtsp 话题已改为 1000、前端 1001 仍存在且多出 1000 仓位——先做根因分析（本节 13.1~13.3）；
> **2026-08-27 用户批准方案 A 并实施**（§13.4 已实施、§13.6 实施记录）。

### 13.1 现象
- rtsp 侧改名 A1001→A1000 成功：`/dev01_object_status` 话题已发布 `A1000`（cargo_type=0，样例确认）；
- 前端仍显示 A1001（空单元格），且新增 A1000（新单元格）→ 视觉上"多了一个仓位"。

### 13.2 根因链（逐环实勘验证）
| # | 环节 | 代码位置 | 行为 |
|---|------|----------|------|
| 1 | 启动预填充 | `BayStatusFusionPlugin._configure_impl` → `BayCache(bay_configs)`；`BayCache.__init__` 遍历 `bay_configs.items()` 预填充 `_bays` | 启动时 yaml `bay_configs` 含 A1001 → `_bays = {A1001: ...}` |
| 2 | 改名不动缓存 | 改名链路仅改 rtsp `polygon_chX_names` 参数（热更新，AreaAssembler clear+rebuild）与前端同步 app_mgr yaml `bay_configs` | **BayCache 内存中 A1001 键从未被删除**；`bay_cache.py` 全文件无 remove/prune/pop/del |
| 3 | 动态加键 | rtsp `BayStatusPublisher::publish` 全量周期发布（`status_publish_interval=0.3s`，遍历所有 channels×areas，`bay_id=area.name`=最新 polygon 名称）→ app_mgr `_on_bay_status` → `_process_single_bay` → `cache.update_ai_result(A1000,…)` → `_ensure_entry(A1000)` | topic 只含 A1000；BayCache 新建键 A1000 |
| 4 | 全量返回 | `get_all_bay_status` 返回 `_bays` 全部键 → `business_collector.get_bay_status` → `GET /api/business/bay_status` → 前端 `API.getBayStatus()` → `renderBayGrid` | 返回 {A1001(残留), A1000(新增)} → 前端渲染两个单元格 |
| 5 | 连带问题 | `_filters`（每仓位 AreaStatusFilter）`_get_filter` 同样只增不减 | `filter_count`/内存随改名次数累积 |

### 13.3 结论
"新增仓位"是 **app_mgr 运行时缓存残留（`_ensure_entry` 只增不删）+ 启动预填充旧键**，非真实仓位配置；rtsp/topic 侧无此问题（topic 仅含 A1000）。前端 §11 三步校验/长度校验/读回校验已防住"rtsp 参数层新增仓位"，但防不住"BayCache 内存层残留键"。

### 13.4 修复方案（方案 A 已实施 ✅；B/C 存档）
- **方案 A（✅ 已实施 2026-08-27，根治，后端最小改动）**：BayCache 增加「主题活跃集修剪」——利用 topic 全量周期发布特性（0.3s 一帧、每帧含全部仓位），在 `_on_bay_status`/fallback 处理完一帧后调用 `cache.prune_stale(timeout)`，删除 `last_seen > 0 且 now - last_seen > timeout` 的键；插件侧同步清理 `_filters` 对应滤波器与历史残留（防内存累积）。安全保护：`last_seen <= 0` 的初始配置键（rtsp 未启动/首帧未到）不删。窗口可配：`bay_status_fusion.yaml` `prune_timeout: 2.0`（默认 2.0s > 多帧 0.3s 周期）。
- **方案 B（未实施，存档）**：改名成功时把 BayCache 旧键改名为新键（保留 cargo_type/绑定状态）。难点：改名发生在 rtsp 参数层，app_mgr 无法直接感知，需额外同步机制；仅作补充。
- **方案 C（未实施，存档）**：`renderBayGrid` 用最近一帧 topic 出现的 bay_id 集合过滤后端 bays 白名单（§11.7 已有 >24 警告防御，可扩展为过滤）。治标，绑定状态残留仍在。
- **验证回归基线**：方案 A 部署后，改名旧键约 2s 内自动消失；部署前板端 A1001+A1000 并存为已知状态。
