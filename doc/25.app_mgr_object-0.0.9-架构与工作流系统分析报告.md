## 0. 结论摘要

`app_mgr_object` 是一个基于 ROS2 (rclpy) 的**插件化应用底座**，0.0.9(基础版) 面向"视觉检测 + AGV 任务调度"场景，形成了一条完整的自动化闭环：

**AI 视觉识别仓位有货 → 防抖确认 → RCS 绑定 → 智能触发匹配 → 工作流下发 AGV 搬运 → 回调/轮询监控 → 资源释放 → 终态归档/人工介入**

架构上采用"微内核 + 插件 + 组件 + YAML 工作流"四层结构，优点是分层清晰、业务可插拔、状态机可配置、具备断电恢复与审计能力。经代码核查，当前基础版存在 3 个**可达性缺陷**（人工介入闭环不可达、L1 告警暂停分支不可达、智能触发器周期扫描绑定错误事件循环）和若干并发/工程化隐患，详见第 7 章。

| 项目 | 说明 |

| Web/HTTP | FastAPI + uvicorn（回调服务 8080，Web 监控 9183 规划中）+ WebSocket |

### 1.1 0.0.9 相对 0.0.8 的变更

逐文件对比 0.0.8 与 0.0.9 源码，**仅 `app_mgr_object/components/trigger/batch_matcher.py` 发生变化**：

- 匹配算法从**笛卡尔积**升级为**贪婪匹配（1:1 配对）**：每个起始仓位/终点仓位只参与一次配对，消除冗余候选，避免组合爆炸；
- 起始仓位按 `bind_time` 降序（最新优先）排序后与终点仓位顺序配对；
- 优先级排序规则不变：`cargo_type → src_bay → dst_bay → bind_time`。

`23/24` 号 Web 可视化规划方案（0.0.9）目前仍处于规划阶段，基础版默认配置中 `web_monitor` 未加入插件白名单。

## 2. 总体架构

### 2.1 分层结构

```
┌─────────────────────────────────────────────────────────────┐
│ 应用层：main.py AppMgrNode（唯一 ROS2 节点 + 组装器）          │
├─────────────────────────────────────────────────────────────┤
│ 插件层 plugins/：业务装配单元（继承 BasePlugin，按序加载）      │
│  network / callback_handler / rcs_adapter / bay_status_fusion│
│  status_poller / workflow_engine / task_status_monitor       │
│  smart_trigger / object_status / web_monitor                 │
│  通信：EventBus（同步/异步发布-订阅）                          │
├─────────────────────────────────────────────────────────────┤
│ 组件层 components/：可复用功能单元                             │
│  workflow(引擎/实例/持久化) trigger(匹配/队列/锁) task_cache   │
│  task_monitor rcs_client callback web network device_status  │
│  reporting token request_handler                             │
├─────────────────────────────────────────────────────────────┤
│ 基础框架层 base/：与 ROS2 紧耦合的微内核                       │
│  ParamManager LifecycleManager PluginManager ServiceManager │
│  SubscriptionManager TimerManager ROS2Logger                 │
└─────────────────────────────────────────────────────────────┘
```

依赖方向自上而下：插件依赖组件与 base，组件依赖 base 或纯 Python，业务之间通过 EventBus 解耦。

### 2.2 启动流程（main.py）

1. `rclpy.init()` → 创建 `AppMgrNode`；
2. 初始化 EventBus 与 6 个基础管理器，并注册到 LifecycleManager；
3. 启动独立 asyncio 事件循环线程（`node.asyncio_loop`）；
4. 从 `params.yaml` 读取 `plugin_configs`（YAML 内嵌字符串，自动解析为 dict）；
5. `PluginManager.discover('app_mgr_object.plugins')` 自动发现 BasePlugin 子类；
6. 按 `plugin_load_order` 白名单 + 依赖声明依次加载插件；
7. 插件注册到生命周期管理器；
8. `lifecycle_manager.configure()` → 各插件 `_configure_impl()`；
9. `lifecycle_manager.activate()` → 各插件 `_activate_impl()`（auto_start）；
10. `MultiThreadedExecutor` 独立线程 spin；SIGINT/SIGTERM 优雅关闭（deactivate → cleanup）。

## 3. 端到端业务链路

### 3.1 主链路：识别 → 绑定 → 触发 → 搬运 → 完成

```
AI 推理节点 (BayStatus / AllObject)
  │  ROS2 Topic /dev01_object_status（BEST_EFFORT QoS）
  ▼
bay_status_fusion：通道信号校验 → AreaStatusFilter 防抖（stable_threshold=3）
  │  稳定有货 → BayCache.set_binding → RCS bindCtnrAndBin("1")
  │  EventBus: bay.status_changed / bay.bound
  ▼
smart_trigger（2s 扫描循环 + bay.bound 事件触发）
  │  ScheduleChecker 工作时间窗口 → TaskBatchMatcher 贪婪匹配
  │  → TaskQueue 入队（去重、按 cargo_type 优先级插入）
  │  → try_dequeue：AGV 空闲(AVAILABLE) + ResourceLocker 原子锁定(robot/src/dst)
  │  → RobotCache.set_busy + BayCache.mark_in_task
  │  EventBus: trigger.task_created
  ▼
workflow_engine：create_instance('agv_transport_atomic', ctx)
  │  WorkflowInstance 状态机启动（asyncio 协程 + 信号量 max_concurrent=10）
  ▼
calling_rcs：invoke_gen_task → RCS genAgvSchedulingTask
  │  成功 → rcs_ack_ok → monitoring；失败/超时(10s×2次) → failed
  ▼
monitoring：wait_for_completion 挂起等待（超时 100s）
  │  RCS agvCallback(9) → callback_completed → releasing
  │  超时 → compensating_query（queryTaskStatus 核实）
  ▼
releasing：release_resources（AGV 置闲、起点仓位解锁、终点仓位置有货、释放锁）
  ▼
completed：publish_completed_event → EventBus workflow.task_completed
  │  → smart_trigger 释放资源并立即分发下一任务；task_status_monitor 停表
  └─ SQLite：status=SUCCESS，state_change_log/exception_log 落库
```

### 3.2 补偿与恢复链路

- **回调丢失补偿**：`task_status_monitor` 按需启停定时器（有 monitoring 任务才轮询），批量 `queryTaskStatus`，检测到终态（9/7/8）注入 `callback_completed/callback_exception`；两轮连续空闲后停止定时器。
- **监控超时补偿**：monitoring 超时 → `compensating_query` 主动查 RCS：9→releasing、7/8→人工介入、2→回到 monitoring；`compensate_cycle_count` 上限 3 次后强制 `manual_intervention`。
- **断电恢复**：启动时 `recover_all()` 读取 SQLite 中未完成实例（status 非 SUCCESS/FAILED/MANUAL），反序列化 pickle 上下文，重建实例并继续运行。
- **启动校准**：`_validate_and_recover()` 对 monitoring/compensating_query 实例逐个查询 RCS 真实状态：9→直接完结、7/8→标记失败、2→正常恢复、无响应→标记人工介入，避免悬挂任务。

### 3.3 告警分级链路（warnCallback）

`AlarmClassifier` 按 warnCode 关键词（优先）或 warnLevel（兜底）分级：

| 级别 | 处置 | 引擎事件 | 示例 warnCode |
|---|---|---|---|
| L0 INFO | 仅记录日志 | 不注入 | BATTERY_LOW, APPROACHING |
| L1 WARNING | 暂停 60s 自动恢复 | warn_l1 → warn_pause | PATH_BLOCKED, OBSTACLE, SIGNAL_WEAK |
| L2 SEVERE | 转人工介入 | callback_exception | COLLISION, MECH_FAILURE, DERAIL |
| L3 CRITICAL | 转人工介入 + 全局告警 | callback_exception | EMERGENCY, FIRE, POWER_OFF |

告警同时写入 `alarm_logs` 表，供 Web 面板查询；人工介入超过 10 分钟（`manual_timeout=600s`）触发 `rcs.alarm_escalated` 升级事件。

### 3.4 运维链路

- `/task_control` ROS2 服务：force_trigger（手动下发）/ cancel / retry / query；
- Web 面板（规划）：任务列表、状态变更历史、异常统计、告警分布、WebSocket 实时推送；
- 日志定期清理：启动时 + 每 7 天清理 `alarm_logs/state_change_log/exception_log`（默认保留 90 天）。

## 4. 状态管理全景

系统存在**五类状态**，分别由不同机制管理：

### 4.1 模块生命周期状态（LifecycleManager）

`UNCONFIGURED → INACTIVE → ACTIVE → FINALIZED / ERROR`

所有基础管理器与插件统一注册，由 `configure/activate/deactivate/cleanup` 模板方法驱动，`get_health_status()` 提供健康巡检。

### 4.2 插件内部状态（BasePlugin）

`_initialized / _configured / _enabled / _error` 四标记 + `get_status()/get_status_summary()` 对外输出（running/stopped/error/configured/initialized）。

### 4.3 工作流实例状态（双状态并存）

| 维度 | 取值 | 说明 |
|---|---|---|
| 实例状态 `_status` | running / completed / failed / cancelled | 内存态，决定是否继续执行 |
| 状态机状态 `current_state` | calling_rcs / monitoring / warn_pause / compensating_query / releasing / completed / failed / manual_intervention / auto_recovery | YAML 驱动，决定下一步转移 |

### 4.4 业务对象内存缓存（task_cache）

| 缓存 | 关键状态字段 | 更新来源 |
|---|---|---|
| BayCache（起点仓位） | ai_detected、bind_status(0/1/2)、in_task、bind_time | AI 融合插件、RCS 绑定/回调 |
| DestBayCache（终点仓位） | is_empty、source | status_poller 轮询、bindNotify 回调、任务完成 |
| RobotCache（AGV） | AVAILABLE / BUSY / OFFLINE / ERROR、current_task_id | status_poller 轮询、工作流释放 |
| ConfigCache（业务配置） | 仓位映射、工作时段 | 规划中（Web 热配置） |

### 4.5 持久化状态（SQLite）

工作流状态 → 业务状态码映射（`persistence._status_from_state`）：

| 工作流状态 | 业务状态码 |
|---|---|
| calling_rcs | DISPATCHING |
| monitoring / compensating_query / releasing / releasing_and_done / auto_recovery | RUNNING |
| completed | SUCCESS |
| failed | FAILED |
| manual_intervention | MANUAL |

`task_instances` 表以 `INSERT ... ON CONFLICT DO UPDATE`（UPSERT）保留 `created_at`，终态写入 `completed_at`；上下文以 **pickle BLOB** 存储；`state_change_log / alarm_logs / exception_log` 三张审计表记录状态迁移、告警与异常（写入失败不影响主流程）。

> 恢复口径注意：`get_incomplete_instances()` 排除 `MANUAL` 状态，即人工介入中的任务**不会**在重启后自动恢复监控。

## 5. 工作流系统深度分析

工作流是整套系统的核心，采用 **YAML 定义 + 事件驱动状态机 + SQLite 持久化** 的实现模式。

### 5.1 组件职责

| 组件 | 职责 |
|---|---|
| `WorkflowDefinitionLoader/Definition` | 加载并解析 YAML（states/transitions/on_enter/on_exit/retry/timeout/final/on_error） |
| `WorkflowEngine` | 实例生命周期、并发信号量、create/inject/cancel、断电恢复、实例查询 |
| `WorkflowInstance` | 单实例执行器：on_enter → action(超时/重试) → 事件匹配转移 → on_exit → 持久化 |
| `ActionRegistry` | Action 函数注册与执行（异步函数签名 `async (context, instance) -> event`） |
| `WorkflowPersistence` | SQLite CRUD、状态变更/告警/异常日志、定期清理 |
| `WorkflowEventBridge` | EventBus ↔ Engine 双向桥：RCS 回调状态码 → 工作流事件、告警分级路由 |
| `AlarmClassifier` | warnCode/warnLevel → AlarmLevel + 处置策略 |

### 5.2 状态机定义（agv_transport_atomic.yaml）

```
                    ┌────────────────────────────┐
                    ▼                            │
calling_rcs ──rcs_ack_ok──▶ monitoring ──callback_completed──▶ releasing ──done──▶ completed
    │                      │  ▲                        │
    │                      │  │timeout                 │
    │                      │  └──▶ compensating_query ──┼──rcs_completed──▶ releasing
    │                      │                            │
    │                      │  warn_l1                   ├──rcs_running──▶ monitoring（补偿循环计数）
    │                      ▼                            │
    │                  warn_pause ──timeout(60s)──▶ monitoring
    │                      │
    │                      └──callback_exception(L2/L3)──┐
    │                                                    ▼
    └──rcs_ack_fail/timeout──▶ failed ◀──user_cancel      manual_intervention
                                    ▲                     │
                                    └──auto_failed        ├──user_retry──▶ calling_rcs
                                                          └──auto_resolved──▶ auto_recovery
```

每个状态支持：`on_enter` 动作、主动作（带 retry/timeout）、事件转移表、`on_exit` 动作；未知事件统一兜底转 `manual_intervention`；全局 `on_error` 提供 log_error + release_resources + publish_failed_event。

### 5.3 事件驱动模型

- 每个实例持有 `asyncio.Queue`，外部事件（ROS2 回调线程 → `run_coroutine_threadsafe`）写入队列；
- 实例在 `asyncio` 循环内消费队列完成转移；
- 主动作超时由 `asyncio.wait_for` 控制，超时返回 `timeout` 事件，重试耗尽返回 `action_error`；
- Action 返回的字符串即为转移事件名（约定优于配置）。

### 5.4 持久化与恢复机制

- WAL 模式 + `threading.Lock` 串行化写库；
- 每次状态转移执行 `log_state_change` + `save`（pickle 整个 context）；
- 恢复前先做 RCS 状态校准（消除悬挂），再重建实例对象续跑；
- 补偿循环上限 3 次防止死循环；
- 所有审计写入均 try/except 吞异常，保证不拖垮主链路。

### 5.5 已注册 Action（9 个）

`invoke_gen_task`、`wait_for_completion`、`compensate_query`、`release_resources`、`publish_completed_event`、`publish_failed_event`、`publish_manual_event`、`log_error`、`log_manual_entry`。

## 6. 架构优势

1. **分层清晰、职责单一**：base/components/plugins 三层，依赖自上而下；新增业务无需改动底座。
2. **插件化微内核**：自动发现（pkgutil）+ 白名单加载顺序 + 依赖声明；插件即业务单元，可插拔可裁剪。
3. **事件驱动解耦**：EventBus 提供同步/异步发布，RCS 回调、任务状态、仓位变化均以事件方式在插件间流转，避免硬编码相互调用。
4. **YAML 驱动的工作流**：业务流程与代码分离，状态/转移/超时/重试/补偿策略全部可配置，新增流程只需写 YAML + 注册 Action。
5. **断电恢复 + 启动校准**：SQLite WAL + pickle 上下文 + recover_all + RCS 状态校准，显著降低悬挂任务风险。
6. **多级数据融合**：AI 原始信号 → 防抖滤波 → 稳定状态 → 业务缓存（Bay/Dest/Robot），缓存全部线程安全，脏数据过滤完备（超时清窗）。
7. **资源原子锁定**：ResourceLocker 对 AGV/起终点仓位做原子抢占，TaskQueue 去重 + AGV 感知分发，防止并发冲突。
8. **可观测性**：状态变更/告警/异常三张审计表 + 日志定期清理 + TimerManager 执行统计 + 插件健康状态查询。
9. **容错设计**：Action 异常映射为事件而非崩溃；审计写入失败不阻塞主流程；消息导入失败降级（BayStatus → String JSON）。
10. **面向场景演进**：告警分级、人工介入、自动闭环、Web 运维均为分版本演进预留，扩展点清晰。

## 7. 关键问题与优化建议

按影响程度分为 P0（正确性/可达性）、P1（并发一致性/健壮性）、P2（工程化）。

### P0-1 【状态机】manual_intervention 语义冲突：人工恢复与自动闭环不可达

**现象**：`agv_transport_atomic.yaml` 中 `manual_intervention` 声明 `final: true`，但同时定义了 `user_retry / user_cancel / auto_resolved / auto_failed` 转移。

**代码证据链**：
1. `WorkflowInstance.run()` 主循环条件为 `while not is_final_state(current_state)`，进入 manual_intervention 后循环立即退出，`_status` 被置为 **COMPLETED**；
2. `WorkflowEngine._run_instance()` 的 finally 将该实例从 `engine._instances` **弹出**；
3. 实例弹出后：`task_monitor._poll_manual_instances` 因 `task_code not in engine._instances` 直接跳过 → `auto_resolved/auto_failed` 注入无效；
4. `/task_control retry` 因实例不存在返回"任务不存在"；
5. `manual_intervention` 的 `on_enter`（log_manual_entry/publish_manual_event）因循环退出**从未执行**，`manual_entered_at` 不会写入，10 分钟告警升级也失效；
6. 引擎事件注入写入的队列无人消费，事件全部滞留。

**影响**：L2/L3 告警、补偿超限、未知事件兜底转入的"人工介入"实际是死胡同，任务既不能人工重试也不能自动闭环，且内存态与 DB 态（COMPLETED vs MANUAL）不一致。

**修复方向**：
- 方案 A（推荐）：将 `manual_intervention` 改为**非终态**挂起状态，去掉 `final: true`，将 `on_enter` 中的 log/publish 动作保留，动作设为 `wait_for_completion`（需让 Action 原样透传事件名，见 P0-2），超时设大值；主循环保持运行即可消费恢复事件；
- 方案 B：将人工介入作为真正的终态，由外部守护（task_monitor）直接通过持久化 + 引擎公开 API 完结/重跑，不再依赖注入事件。

### P0-2 【状态机】warn_l1 事件被 wait_for_completion 吞掉，L1 暂停分支不可达

**现象**：YAML 定义 `monitoring` 存在 `warn_l1 → warn_pause` 转移，但 `_action_wait_for_completion` 只识别 `callback_completed / callback_exception`，其余事件（含 warn_l1）统一返回 `callback_exception`。

**后果**：L1 告警（路径阻塞、信号弱、障碍物等）会直接升级为 manual_intervention，`warn_pause` 状态成为死代码；结合 P0-1，L1 任务将进入死胡同。

**修复方向**：`wait_for_completion` 对未知事件**原样透传事件名**（`return event`），把匹配职责完全交给 YAML 转移表；或在 Action 内显式识别 warn_l1/warn_info。

### P0-3 【并发】smart_trigger 周期扫描循环绑定错误事件循环

**现象**：`SmartTriggerPlugin._activate_impl` 使用 `asyncio.get_event_loop()` 创建 `_scan_task`，此时主线程并无运行中的事件循环（真正的循环是 `node.asyncio_loop`，运行在独立线程），返回的是**从未 run_forever 的新循环**。

**后果**：周期扫描协程永不执行；系统实际只能依赖 `bay.bound / task_completed` 等事件触发的单次扫描（`_scan_and_dispatch_once`）维持运转，批次编排能力（批量匹配、工作时段节流）名存实亡。

**修复方向**：统一使用 `self.node.asyncio_loop` + `run_coroutine_threadsafe` 创建扫描任务；同理审查 `cancel_task` 中的 `asyncio.ensure_future`（ROS2 回调线程无运行循环）。

### P1-1 同步阻塞 IO 位于 asyncio 循环内

RCS HTTP 请求（requests 同步库）在 Action 与轮询回调中直接执行，会阻塞 asyncio 事件循环，影响所有工作流实例的并发执行。建议：用 `asyncio.to_thread / run_in_executor` 包装同步 IO，或 RCSHttpClient 改为 aiohttp 异步实现。

### P1-2 多缓存状态一致性依赖分散更新

RobotCache/BayCache/DestCache/ResourceLocker/TaskQueue 的状态由多个插件（status_poller、workflow、callback、smart_trigger）分散写入，缺少统一状态聚合与版本校验，存在轮询覆盖/时序竞态风险（例如轮询旧数据覆盖刚释放的状态）。建议：为状态更新引入时间戳/版本号校验，或收敛为单一"状态服务"。

### P1-3 pickle 序列化上下文的兼容性风险

`context_blob` 使用 pickle：Python 版本升级、类路径变化、字段变更都会导致恢复失败或读到脏数据；pickle 本身也不安全。建议：改为 JSON + schema 版本字段，反序列化失败时降级为人工介入并保留原始数据。

### P1-4 跨插件访问私有成员

`task_monitor_plugin` 直接访问 `engine._instances / _persistence`，`smart_trigger` 访问 `_trigger_engine._locker`、`workflow_engine_plugin` 访问 `_engine._persistence` 等。建议为 Engine/TriggerEngine/Persistence 补齐公开查询 API（如 `get_manual_instances()`、`query_exceptions()`），杜绝私有字段耦合。

### P1-5 队列无老化机制

TaskQueue 中的任务若始终无法满足出队条件（AGV 全忙/资源冲突）会永久滞留，且每次扫描不断重新入队计数。建议：候选任务加入超时老化（如 N 轮后移除）或按需重新匹配。

### P1-6 SQLite 写放大

每次状态转移执行 `save` + `log_state_change` 两次独立连接写库，高并发下锁竞争明显。建议：合并为单次事务，或引入异步批量写入（队列 + 后台刷盘）。

### P2-1 自动化测试缺失

仅有 ament 默认测试（copyright/flake8/pep257），业务链路（匹配→下发→回调→补偿→闭环）无任何自动化测试。建议：基于 `bay_status_simulator.py` / jmsy-rcs_server 构建 pytest 集成测试，覆盖状态机各分支（尤其 P0-1/P0-2 场景）。

### P2-2 配置内嵌 YAML 字符串 + 热更新未生效

`plugin_configs / web_monitor` 以字符串块内嵌于 params.yaml，无 schema 校验；`ParamManager` 已注册参数变更回调但插件未消费。建议：配置拆分为独立文件或使用 YAML 锚点，Web 热配置与 `ConfigCache` 打通。

### P2-3 日志分级与路径

大量调试日志以 INFO 级别输出（AI 每帧消息、轮询详情），生产环境性能与可读性受影响；`UnifiedLogger` 文件日志路径硬编码 `/var/log/app_mgr` 且默认关闭。建议：级别分级规范化 + 日志路径参数化 + 按天轮转。

### P2-4 Web 监控与告警存在未启用/禁用代码

`web_monitor_plugin._init_components` 中 `AlarmManager` 创建与告警回调被注释；`auth_required` 默认 false；`execute_command` 可执行任意系统命令。部署前需：启用告警、强制认证、命令白名单化、移除标定配置中的明文密码。

### P2-5 版本与死代码治理

`setup.py` version 仍为 0.0.0（与 0.0.9 不一致）；`package.xml` description/license 为 TODO；main.py 与多处保留大量注释旧实现；token / request_handler 组件未被任何插件使用（预留）。建议：统一版本号、清理死代码、为预留组件标注"未接线"。

### P2-6 事件总线健壮性

`EventBus.publish` 同步串行执行所有回调，慢回调会阻塞发布者线程；协程回调在无运行循环线程中执行 `asyncio.run` 可能产生循环冲突。建议：统一走异步发布或线程池分发，并限制单事件处理超时。

## 8. 开发工程师上手指南

### 8.1 新增一个业务插件

1. 在 `app_mgr_object/plugins/` 新建 `xxx_plugin.py`，继承 `BasePlugin`，定义 `PLUGIN_NAME/PLUGIN_VERSION`，覆写 `_configure_impl/_activate_impl/_deactivate_impl/_cleanup_impl`；
2. 在 `plugins/__init__.py` 导出类；
3. 在 `config/params.yaml` 的 `plugin_configs` 增加配置，并加入 `plugin_load_order`（注意依赖顺序）；
4. 跨插件访问统一走 `node.xxx`（插件 configure 时挂载）或 EventBus。

### 8.2 新增一个工作流

1. 在 `config/workflows/` 新建 YAML（name/version/initial_state/states/transitions/on_error）；
2. 在 `workflow_engine_plugin._register_actions` 注册 Action 函数（`async (context, instance) -> event`）；
3. 引擎按 name 创建实例，事件注入点通过 `engine.inject_event(task_id, event, data)`。

### 8.3 常见调试入口

- 插件健康：各插件 `get_status()`，聚合于 `LifecycleManager.get_health_status()`；
- 任务状态：`/task_control` service（query/cancel/retry/force_trigger）；
- 审计：`~/.app_mgr_object/task_instances.db` 的 `state_change_log / alarm_logs / exception_log`；
- 状态机行为：观察日志中 `[Instance]`/`[Engine]`/`[EventBridge]` 前缀链路；
- 性能：`TimerManager.get_timer_stats()` 观察各定时器执行时长。
