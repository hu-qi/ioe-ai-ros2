## 一、目标与范围（v2 更新）

- **控制统一委托 OPS 单点执行**：app_mgr 节点/服务控制（start/stop/restart）不再各自一套（systemctl/脚本），统一经 OPS（:1818）执行，自动协调看门狗（stop→pause 防拉起 / restart→reset / start→resume）；
- **节点源统一从 OPS 获取**：app_mgr 运维**节点列表/状态/控制全部直接消费 OPS /api/nodes**（权威源，managed_nodes.yaml 已注册 rtsp_node/app_mgr），**不维护本地节点硬映射**（消除 node_map 对齐问题）；显示名仅用可选 display_map 覆盖（缺省用 OPS 节点名）；
- **全部配置 yaml 驱动**：ops_integration 段（enabled/base_url/timeout_s/display_map）配置化，无硬编码；
- **同机部署 + 通用性**：base_url 配置化；OpsControlProxy 设计支持多端点/多设备集群扩展（未来可能接入其他设备接口）；
- **灰度期双路径并存 → 稳定后移除干净**：原 /api/control/* 保留灰度，稳定后完整移除（含 ControlExecutor 运维路径、deployment_services/dev_scripts 运维用途清理）；
- **成功标准**：app_mgr 页面重启 rtsp_node/app_mgr → OPS 执行 + 看门狗协调；OPS 停止时 app_mgr 显示「OPS 不可达」；无「app_mgr 停的节点被 OPS 看门狗拉起」冲突。

## 二、现状分析（已实勘）

- OPS 最先部署，managed_nodes.yaml 已注册 **rtsp_node / app_mgr**（含 restart cmd_*、install_dir、node_name），watchdog 探活已生效；
- OPS 侧统一能力（零改动）：GET /api/nodes（注册节点列表 + watchdog 状态）、POST /api/nodes/{name}/restart|stop|start（**restart→reset / stop→pause 防拉起 / start→resume**）、GET /api/nodes/{name}/service（systemd is-active 或进程探测）、GET /api/status（P3 复用）；

### 2.2 app_mgr 现有控制链路（各自一套，待替换/移除）
- control.html `controlServiceAction → showConfirmationModal → performServiceAction → POST /api/control/{action}_service → ControlExecutor._deploy_*(systemctl)`；
- web_monitor.yaml 现有 deployment_services / dev_scripts / node_names / node_aliases——改造后**仅保留配置兼容，运维用途移除**；
- **问题**：与 OPS node_governor 重复控制，app_mgr 手动 stop 会被 OPS watchdog 拉起（冲突根源）。

## 三、架构与数据流

```
app_mgr control.html 节点运维卡
  → GET  /api/ops/nodes                    （节点列表，实时来自 OPS /api/nodes）
  → POST /api/ops/nodes/{name}/action {action}  （start|stop|restart）
  → web_server.py 路由 → node.ops_proxy.execute(name, action)
  → OpsControlProxy（requests → base_url/api/nodes/{name}/{action}）
  → OPS：RestartCtl 执行（systemd/cmd）+ watchdog pause/reset/resume
  → 返回 {success, error, detail} → 前端状态回显
```

- 节点清单/状态：`/api/ops/nodes` = OPS `/api/nodes`（watchdog_status）+ 逐节点 `/api/nodes/{name}/service`——**权威源，无本地映射**；
- 显示名：display_map 可选覆盖（缺省 OPS 节点名）。

## 四、实现明细（v2 更新）

### 4.1 配置（config/web_monitor.yaml 新增 ops_integration 段，全部 yaml 驱动）

```yaml
ops_integration:
  enabled: true
  base_url: "http://127.0.0.1:1818"    # 同机部署；多设备集群时可为设备级/多 OPS 端点（扩展预留）
  timeout_s: 10
  display_map: {}                       # 可选：OPS 节点名 → UI 展示名（缺省直接用 OPS 节点名）
```

- 无 node_map 硬映射——**节点清单以 OPS /api/nodes 为准**（权威源），display_map 仅覆盖 UI 展示名；
- 多设备集群扩展：OpsControlProxy 以 base_url 注入 + 统一接口（list_nodes/execute/ops_status），未来多设备 = 每设备一个 proxy 实例或 OPS 网关（配置层扩展，接口不变）。

### 4.2 新增 components/web/ops_proxy.py（OpsControlProxy）

```python
class OpsControlProxy:
    def __init__(self, base_url, timeout_s=10, display_map=None, logger=None):
        ...
    def list_nodes(self) -> dict          # GET /api/nodes（权威节点源；display_map 覆盖展示名）
    def node_status(self, name) -> dict   # GET /api/nodes/{name}/service（name 即 OPS 注册名，无本地转换）
    def execute(self, name, action) -> dict # POST /api/nodes/{name}/restart|stop|start
    def ops_status(self) -> dict          # GET /api/status（P3 复用）
```

- 实现：requests（同步；FastAPI 同步 def 路由 OK）；统一 `_call(method, path, **kw)` 封装；
- 异常/超时 → `{success: False, error: 'OPS 不可达: ...'}`；OPS 离线 5s 短缓存快速失败（参考 OPS doc/78）；
- base_url 构造注入（同机 127.0.0.1 / 跨机 IP / 未来多设备），**接口与地址解耦**；
- 挂载：web_monitor_plugin `_configure_impl` 读 ops_integration → 创建 `self.node.ops_proxy`（enabled=false 不创建）。

### 4.3 web_server.py 新路由
- `GET /api/ops/nodes`：节点运维列表（OPS 实时数据 + display_map 显示名 + watchdog 状态）；
- `POST /api/ops/nodes/{name}/action`：body `{action}` ∈ start/stop/restart → OpsControlProxy.execute；
- `GET /api/ops/status`：OPS /api/status（P2/P3 状态展示）。

### 4.4 control.html 节点运维卡改造（需求 1 UI）
- 「服务管理 (部署模式)」卡 → 「节点运维（经 OPS 统一控制）」：
  - 节点列表/下拉：**实时来自 /api/ops/nodes**（OPS /api/nodes 权威源，非静态映射）；
  - 每节点行：显示名 + OPS 节点名 + watchdog 状态（在线/离线/暂停）；
  - 快速操作：推理节点（rtsp_node）/ RCS 节点（app_mgr）重启按钮；通用：节点下拉 + 启动/停止/重启 + 执行；
  - 结果区：OPS 返回（success/error + probe）；失败/不可达 → AppDialog.alert + toast；
  - **停止二次确认**（AppDialog.confirm danger:true，提示「停止后 OPS 看门狗暂停自愈，需手动启动恢复」）；
- 移除旧服务操作 UI 依赖（灰度期代码兼容，稳定后清理）。

### 4.5 灰度与移除（v2：稳定后移除干净）
- **灰度期**：/api/control/start_service|stop_service|restart_service|available_services 等保留（原 controlServiceAction 等代码兼容），UI 默认走 /api/ops/*；
- **稳定后移除（干净）**：
  1. 删除 web_server.py 原 /api/control/* 运维路由（start/stop/restart_service、available_services、execute_command 等运维类）；
  2. 移除 ControlExecutor 运维调用路径（start_service/stop_service/restart_service/_deploy_* 等；类文件按需整体清理或保留空壳）；
  3. web_monitor.yaml 清理 deployment_services / dev_scripts / node_names 运维用途（保留业务所需字段）；
  4. 前端移除旧 controlServiceAction / performServiceAction / service-select 等代码；
  5. grep 验证无残留引用（除注释/历史文档）。
