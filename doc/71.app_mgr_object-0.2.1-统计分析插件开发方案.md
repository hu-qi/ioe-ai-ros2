## 1. 背景与目标

### 1.1 背景

需求说明.docx §3.3 明确"统计分析"为教官操作端核心功能：将原始数据转化为可指导教学改进的洞察。平台提供**三个层次**的分析能力：

| 层次 | 解决的问题 | 输出内容 |
|---|---|---|
| 描述性 | 发生了什么？ | 步骤平均用时、完成率、得分分布 |
| 诊断性 | 为什么发生？ | 哪些步骤是全班性瓶颈？哪些学员有特定问题？ |
| 处方性 | 教官该做什么？ | "建议加强步骤X的练习""建议对学员Y进行个别辅导" |

P1 期 `report_recv_plugin` 已完成报告接收与入库（reports / report_steps / report_substeps / report_events / report_progress 五表）。本插件负责**基于这些已入库数据，计算统计指标并生成诊断建议**。

### 1.2 目标

开发 `report_analysis_plugin`，实现：

1. 步骤用时分布统计（平均用时、标准差、合规率、与 SOP 对比）；
2. 学员累计统计（考试次数、平均得分、完成率趋势、薄弱步骤 TOP3）；
3. 步骤瓶颈诊断（4 类阈值规则，对齐 .docx §3.3.3）；
4. 教学建议生成（每条诊断结果配对"教官行动建议"文本）；
5. 统计结果缓存（避免重复计算，支持按时间窗/班级/设备过滤）。

### 1.3 范围与边界

| 维度 | 本期 P2 | 不做 |
|---|---|---|
| 数据来源 | 直连 `reports` / `report_steps` / `report_substeps` / `report_events` 表读聚合 | 不通过 P1 报告插件 API 间接拿数据（同库直读，既有惯例） |
| 统计粒度 | 步骤级 + 子步骤级 + 学员级 + 班级级 | 不做实时增量统计（增量数据由 P1 入库，P2 按需算） |
| 诊断规则 | .docx §3.3.3 的 4 类阈值，可配置 | 不做 AI 模型诊断（本期纯规则引擎） |
| 输出形式 | REST API 返回 JSON 统计结果 + 诊断建议 | 不做前端图表渲染（归 P3 看板插件） |
| SOP 标准 | 从 model JSON（`model_a.json` / `model_as.json`）加载步骤标准用时 | 不做 SOP 编辑器（SOP 配置由边缘端管理） |

> **关键决策**：本插件**直连 reports 系列表读**，不通过 P1 的 `report_recv_plugin` API 间接调用。理由：既有 `smart_trigger_plugin` 跨插件读 `task_cache` 数据做触发判断，同库跨插件读是既有底座的合法模式；统计是高频读操作，走 API 性能差且增加不必要的插件间耦合。

| 协作点 | 方式 |
|---|---|

## 3. 数据模型与建表

### 3.1 DDL（`config/analysis_schema.sql`）

```sql
-- 统计结果缓存表：按维度缓存统计结果，避免重复计算
CREATE TABLE IF NOT EXISTS analysis_cache (
    cache_key          TEXT    PRIMARY KEY,   -- 维度组合键，如 "step_duration|cls=一班|date=2026-09"
    dimension          TEXT    NOT NULL,      -- 统计维度：step_duration / student_cumulative / class_summary
    filters_json       TEXT,                  -- 过滤条件 JSON（cls / device_id / date_range）
    result_json        TEXT,                  -- 统计结果 JSON
    computed_at        INTEGER NOT NULL,      -- 计算时刻（epoch ms）
    report_count       INTEGER                -- 参与统计的报告数
);

-- 诊断结果表：每条诊断结果独立存储，支持历史追溯
CREATE TABLE IF NOT EXISTS diagnosis_results (
    diagnosis_id       TEXT    PRIMARY KEY,   -- 平台生成：D{timestamp}
    diagnosis_type     TEXT    NOT NULL,      -- bottleneck / persistent_error / sequence_chaos / student_regression
    scope              TEXT    NOT NULL,      -- class / student / step
    target_id          TEXT,                  -- 学员工号 / 步骤序号 / 班级名
    metric_value       REAL,                  -- 判断依据数值（如实际平均用时、遗漏率）
    threshold_value    REAL,                  -- 阈值（如 SOP×1.5、30%、20%）
    advice_text        TEXT,                  -- 教官行动建议文本
    computed_at        INTEGER NOT NULL,      -- 计算时刻
    date_window_start  INTEGER,               -- 统计时间窗起点
    date_window_end    INTEGER                -- 统计时间窗终点
);

-- 索引
CREATE INDEX IF NOT EXISTS idx_cache_dimension  ON analysis_cache(dimension);
CREATE INDEX IF NOT EXISTS idx_diagnosis_type   ON diagnosis_results(diagnosis_type);
CREATE INDEX IF NOT EXISTS idx_diagnosis_target ON diagnosis_results(target_id);
```

### 3.2 SOP 标准用时加载

SOP 标准用时来源：边缘端 `model_a.json`（拆解）/ `model_as.json`（组装）配置文件。

**加载策略**：

1. 配置文件路径通过 `analysis.yaml` 的 `sop_model_paths` 配置；
2. 插件 `_configure_impl` 时加载并解析，缓存到内存；
3. 每个 step 的标准用时 = `steps[idx].standard_duration_ms`（model JSON 字段，需与边缘端约定）；
4. 若 model JSON 未提供标准用时，则"与 SOP 对比"诊断降级为"仅统计实际用时，不做合规判断"。

> **与边缘端的约定**：model JSON 中每个 step 需含 `standard_duration_ms` 字段（SOP 标准用时）。若边缘端 model JSON 暂无此字段，P2 期可先跳过"与 SOP 对比"诊断，待边缘端补充字段后启用。本期方案预留此字段加载逻辑。

## 4. 统计口径与诊断规则

### 4.1 步骤用时分布统计（描述性）

**统计对象**：`report_steps` 表，按 `idx`（步骤序号）聚合。

| 指标 | 计算口径 | 教学意义 |
|---|---|---|
| 平均用时 | `AVG(duration_ms)` 按 step idx 分组 | 判断哪些步骤学员普遍耗时较长 |
| 标准差 | `STDDEV(duration_ms)` 按 step idx 分组 | 评估操作一致性，标准差大→部分学员明显落后 |
| 合规率 | `COUNT(duration_ms <= standard_duration_ms) / COUNT(*)` | 衡量用时规范性 |
| 与 SOP 对比 | `AVG(duration_ms) - standard_duration_ms` | 发现偏离标准最大的步骤 |

**API**：`GET /api/v1/analysis/step_duration?cls=&device_id=&date_start=&date_end=`

**响应 data**：

```json
{
  "steps": [
    {
      "idx": 1, "name": "装缓冲",
      "avg_duration_ms": 8200, "stddev_ms": 1500,
      "compliance_rate": 0.85, "sop_standard_ms": 8000,
      "deviation_ms": 200
    }
  ],
  "report_count": 156
}
```

### 4.2 学员累计统计（描述性 + 诊断性）

**统计对象**：`reports` 表，按 `student_id` 聚合。

| 指标 | 计算口径 |
|---|---|
| 考试次数 | `COUNT(*)` 按 student_id 分组 |
| 平均得分 | `AVG(total_score)` 按 student_id 分组 |
| 完成率趋势 | 按时间排序，计算每次报告的完成率（`1 - len(unexecuted)/total_substeps`），展示趋势 |
| 薄弱步骤 TOP3 | 按 student_id 分组，统计每个 step 的超时率 + 遗漏率，排序取 TOP3 |

**API**：`GET /api/v1/analysis/student_cumulative?student_id=&date_start=&date_end=`

### 4.3 步骤瓶颈诊断（诊断性 + 处方性）

**严格按需求说明.docx §3.3.3 的 4 类判断阈值实现**（doc/69 §9.1.2 已沉淀）：

| 诊断类型 | 判断逻辑 | 教官行动建议 | 阈值配置项 |
|---|---|---|---|
| 全班性瓶颈 | 某步骤全班平均用时 > SOP标准×1.5 | "该步骤需在下次课重点讲解" | `bottleneck_multiplier: 1.5` |
| 顽固性错误 | 某步骤遗漏率 > 30% | "需增加该步骤的专项训练" | `persistent_error_rate: 0.30` |
| 顺序混乱 | 某步骤顺序错误率 > 20% | "需强调步骤间的依赖关系" | `sequence_chaos_rate: 0.20` |
| 学员退步预警 | 最近3次平均分 < 前5次×0.85 | "建议安排个别辅导" | `regression_window_recent: 3` / `regression_window_history: 5` / `regression_threshold: 0.85` |

**诊断引擎实现要点**：

1. 上述 4 类阈值需可配置（`analysis.yaml`），默认值即上表；
2. 每条诊断结果须同时输出"判断依据数据"（`metric_value`，如实际平均用时、遗漏率数值）与"教官行动建议文本"（`advice_text`），满足产品文档"从数据到行动"的价值主张；
3. 诊断结果存 `diagnosis_results` 表，支持历史追溯（可查看往期诊断记录）；
4. 遗漏率计算：`COUNT(report WHERE substep.idx IN unexecuted) / COUNT(report)`；
5. 顺序错误率计算：需从 `report_events` 表解析事件流，统计 `INTERRUPT`（kind=2）后非顺序重入的比例（具体算法实施时细化）。

**API**：`GET /api/v1/analysis/diagnosis?scope=class&date_start=&date_end=`

**响应 data**：

```json
{
  "diagnoses": [
    {
      "diagnosis_type": "bottleneck",
      "target_id": "step_3",
      "metric_value": 12500,
      "threshold_value": 12000,
      "advice_text": "该步骤需在下次课重点讲解",
      "metric_label": "全班平均用时 12.5s（SOP 标准 8s × 1.5 = 12s 阈值）"
    }
  ]
}
```

### 5.3 诊断规则引擎（`components/web/diagnosis_engine.py`）

class DiagnosisEngine:
    """诊断规则引擎：4 类阈值规则计算"""

    def __init__(self, repo, thresholds, sop_standards, logger):
        self._repo = repo
        self._thresholds = thresholds
        self._sop_standards = sop_standards
        self._logger = logger

    def diagnose_class_bottleneck(self, cls: str, date_range: dict) -> list:
        """全班性瓶颈诊断：某步骤全班平均用时 > SOP标准×1.5"""
        results = []
        multiplier = self._thresholds['bottleneck_multiplier']
        for step_idx, standard_ms in self._sop_standards.items():
            avg_ms = self._repo.get_step_avg_duration(step_idx, {'cls': cls, **date_range})
            threshold = standard_ms * multiplier
            if avg_ms > threshold:
                results.append({
                    'diagnosis_type': 'bottleneck',
                    'target_id': f'step_{step_idx}',
                    'metric_value': avg_ms,
                    'threshold_value': threshold,
                    'advice_text': '该步骤需在下次课重点讲解'
                })
        return results

    def diagnose_persistent_error(self, filters: dict) -> list: ...
    def diagnose_sequence_chaos(self, filters: dict) -> list: ...
    def diagnose_student_regression(self, student_id: str) -> list: ...

## 6. 关键实现细节

### 6.1 统计结果缓存策略

- **缓存键**：`{dimension}|{filters_sorted_json}`，如 `step_duration|cls=一班|date=2026-09`；
- **有效期**：`cache_ttl_sec`（默认 300s），过期后重新计算；
- **主动失效**：P1 报告入库时发布 `event_bus` 事件 `report.received`，本插件可选订阅，收到后清除相关维度缓存（可选优化，本期默认 TTL 失效即可）。

### 6.2 顺序错误率计算（doc/38 §4 事件流解析）

顺序错误率的计算需从 `report_events` 表解析事件流：

1. 取该报告所有 `START`（kind=0）事件，按 `ts` 升序排列；
2. 检查 `step` 字段是否满足弱顺序约束（doc/产品说明边缘端 §3.2："弱顺序约束：不强制按标准顺序执行，如实记录学员真实操作轨迹"）；
3. 统计 `INTERRUPT`（kind=2）事件后，该子步骤是否以非标准顺序重入；
4. 顺序错误率 = 顺序错误报告数 / 总报告数。

> **注意**：边缘端采用"弱顺序约束"，学员可不按标准顺序执行。顺序错误率的定义需在实施时与教官确认：是"偏离 SOP 标准顺序"还是"违反物理依赖"。本期方案按"偏离 SOP 标准顺序"计算，具体算法实施时细化。

### 6.3 薄弱步骤 TOP3 算法

**薄弱步骤定义**：超时率 + 遗漏率综合得分最高的 3 个步骤。

**计算口径**：

1. 对每个 step idx，计算：
   - 超时率 = `COUNT(report WHERE step.idx.timeout=true) / COUNT(report)`
   - 遗漏率 = `COUNT(report WHERE step.idx IN unexecuted) / COUNT(report)`
2. 综合得分 = `超时率 × 0.5 + 遗漏率 × 0.5`（权重可配置）；
3. 按综合得分降序，取 TOP3。

### 6.4 完成率趋势计算

**完成率定义**：`1 - len(unexecuted) / total_substeps`。

**趋势展示**：按 `ts_upload_ms` 升序排列该学员所有报告，计算每份报告的完成率，前端折线图展示趋势。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| SOP model JSON 未提供 standard_duration_ms | "与 SOP 对比"诊断无法执行 | 降级处理，日志告警；推动边缘端 model JSON 补充字段 |

| 诊断阈值与实际教学不符 | 误报或漏报 | 阈值可配置，教官可调整；后续可引入按机型/SOP 差异化阈值 |
