# 57. app_mgr_object-0.2.0 触发插件模块优化技术方案

> 状态：**技术方案（评审级，供审核；本次未修改任何业务代码）**
> 依据：`doc/56.app_mgr_object-0.2.0-触发插件模块业务流程与逻辑审查报告.md` + 当前工程代码勘察
> 工程：`app_mgr_object-0.2.0(标准版)`
> 日期：2026-08-31 ｜ 目标：在保持现有触发闭环架构不变的前提下，按 P0→P1→P2→P3 给出可落地的优化方案

## 1. 优化定位与原则

### 1.1 优化原则

1. **架构不变、增量改造**：保留“AI 检测 → RCS 绑定 → 匹对 → 队列 → 派发 → 工作流执行 → 释放 → 观测”主链路与事件模型（doc/56 §3），只做局部增强；
2. **默认行为不变**：所有新增 YAML 字段缺省值 = 现状行为，调整才改变行为，降低现场回归风险；
3. **可配优先**：算法方向的差异尽量以“策略选择器 + 权重”配置化（延续 doc/52-53 已建成的 HotReloadRegistry 体系）；
4. **可观测闭环**：每个优化点配套审计日志/指标/前端展示，可解释“为什么触发/为什么没触发”。

### 1.2 勘察确认的事实（方案输入）

| 事实 | 证据 | 影响 |
|---|---|---|
| 无配置文件监听：改 YAML 需重启或经 Web 保存 | 工程内无 mtime/watchdog/inotify 相关代码（doc/56 O-2） | 现场“直接改 YAML”体验不完整 |
| `bay_status_fusion` 启动时不校准绑定：BayCache.bind_status 重启后从 0 开始 | bay_status_fusion_plugin.py 仅运行期 set_bound | 重启后已绑定仓需等 AI 重新确认，存在短暂不可调度/重复绑定窗口 |
| 候选队列无持久化：重启后 TaskQueue 为空 | smart_trigger_plugin.py:128 激活时新建队列 | 已匹对未派发候选丢失（虽可由重新扫描弥补，但绑定校准缺失时恢复不完整） |
| 任务 ID 为时间戳生成：`TASK_{src}_{int(time.time())}` | trigger_engine.generate_task_id | 极端/重启场景存在 ID 复用隐患（低） |
| AGV least_busy 为“空闲最早”近似 | robot_cache.get_available_robot | 未真正考虑电量/任务数 |
| 匹对排序为固定 key：`(type_rank, src, dst, -bind_time)` | batch_matcher.TaskCandidate.key | 等待时间、巷道深度、AGV 适配无法参与排序 |

## 2. 优化建议分级清单（P0-P3）

### 2.1 P0 可靠性（建议优先实施）

| 编号 | 优化项 | 现状 | 建议 |

| P0-1 | **队列重启恢复** | 队列无持久化 | TaskQueue 快照（SQLite/JSON）→ 启动恢复 + 有效性校验（始发仍绑定/目的仓仍空/未超龄），失效候选按现有释放语义清理 |

## 3. 推荐触发机制技术方案（总体设计）

### 3.1 总体架构（保持现状，增量模块）

```text
现有闭环（不变）：
AI 检测 → bay_status_fusion(绑定/解绑) → smart_trigger(匹对→队列→派发)
        → workflow_engine(执行/补偿/恢复) → 释放 → 再派发 → event_bridge(观测)

新增模块（本方案）：
[P0-3] ParamManager 配置监听器 ── plugin_configs.updated ──▶ 各插件 HotReloadRegistry
[P0-1] TaskQueue 快照/恢复（SQLite 或 JSON）── 启动 restore + 校验 ──▶ 队列
[P0-2] bay_status_fusion 启动绑定校准（AI 有货幂等重绑 / RCS 查询）
[P1-1] TaskCandidate.score() + smart_trigger.yaml scoring.weights ──▶ batch_scan_all 排序
[P1-2] RobotCache least_busy 加权（battery/任务数）
[P2-1] 决策审计（audit 表/结构化日志）
[P2-2] 指标采集（扫描耗时/成功率/等待时长/利用率）
```

### 3.2 可配权重评分模型（P1-1，推荐主线）

**目标**：现场可通过 YAML 调整“谁先被匹配”，默认与现状完全等价。

**设计**：

```yaml
# smart_trigger.yaml 新增段（缺省=现状，零行为变化）
scoring:
  enabled: false            # false=沿用现状固定排序；true=启用评分重排
  weights:
    type_priority: 100      # 货物类型优先级主层
    src_region: 10          # 区域/编号顺序
    wait_time: 0.02         # 入队/绑定等待时间加分（秒）
    lane_depth: 0.5         # 巷道深度惩罚（越深越低优先）
    agv_fit: 1.0            # AGV 适配分（电量/距离）
```

**排序规则**：

1. `enabled: false`（默认）→ 完全走现状 `TaskCandidate.key()`，行为零变化；
2. `enabled: true` → 在现状排序基础上按 `score` 微调同层内次序（保留类型/区域主层确定性，避免跳跃），`score = Σ weights[i] × factor[i]`，供 Web/审计展示明细；
3. 权重校验：非负浮点；`type_priority/src_region` 权重为 0 时回退现状 key 保底，防止评分把不同货物类型混排。

**接入点**：`batch_matcher.batch_scan_all` 最终排序处（现 `all_candidates.sort(key=lambda c: c.key(...))`）替换为 `_sort_candidates(candidates)`，内部按 scoring 配置分发；`TriggerEngine`/`smart_trigger` 通过既有 `set_*`/热加载链路传入配置。

### 3.3 队列重启恢复与绑定校准（P0-1/P0-2）

**队列快照（推荐 SQLite 新表 `queue_snapshot`，复用 workflow 的 DB 连接与事务）**：

| 字段 | 说明 |
|---|---|
| task_key / src_bay / dst_bay / cargo_type | 候选要素 |
| bind_time / enqueue_time / lane_id / strategy | 恢复排序与老化依据 |
| snapshot_ts | 快照时间 |

- `TaskQueue.snapshot()`：入队/出队/移除/老化时同步写快照（或周期写）；`restore()`：启动时读取并按“始发仍绑定（bind_status==1）、目的仓仍空且未 reserved、未超龄”校验，失效项走现有 `release_occupied` 清理；
- 备选（现场不接受新表）：**不持久化队列，重启后依赖扫描重新匹对**，但必须配合 P0-2 绑定校准，否则恢复不完整。

**绑定校准（P0-2）**：

- 方案 A（推荐，若 RCS 提供查询接口）：扩展 `rcs_adapter_plugin` 增加“查询起始仓绑定”方法，启动时批量回填 `BayCache.bind_status=1`；
- 方案 B（无查询接口时的兜底）：`bay_status_fusion` 激活后，对 AI 稳定有货且本地未绑定的仓位调用 `bind_ctnr_and_bin(ind_bind=1)` 幂等重绑（RCS 侧已绑定则视为成功），并在文档/前端标注“重启后绑定自动恢复中”；
- 需现场确认：RCS-2000 是否提供起始仓绑定查询（当前适配器仅有 `queryPodBerthAndMat` 终点仓位查询）。

### 3.4 配置热加载闭环（P0-3/P0-4）

**设计**（复用 doc/52-53 已建成的 HotReloadRegistry 与 `plugin_configs.updated` 事件）：

```text
ParamManager 新增 ConfigWatcher（独立线程，轮询 plugin_configs/*.yaml mtime，防抖 1s）
  ├─ 变更检测 → yaml.safe_load + schema 校验（复用 config_manager 校验器/新 registry）
  ├─ 通过 → 更新内存 → 发布 plugin_configs.updated（各插件已订阅，热应用）
  ├─ 失败 → 保留上次有效配置快照（内存 + .bak），回退并告警
  └─ 启动 → 先校验全部配置；非法项按字段报错并回退默认/快照（P0-4）
```

- 生效档位（沿用 doc/52 §5.4）：hot 项立即生效；restart 项（enabled/operation_mode/robot_ids）仅提示“需重启”；
- 并发写：与 Web 保存共用 `_yaml_lock`；监听器检测到外部修改后以“文件为准”重新加载，Web 保存后以内存为准并跳过本轮监听（mtime 对比）。

### 3.5 AGV 选择增强（P1-2）

- `RobotCache.set_select_policy` 扩展 `least_busy_weight`（battery 权重/任务数权重，默认 0=现状空闲最早）；
- `least_busy` 排序键：`-battery×w_battery - idle_time×w_idle`（任务数可由 `current_task_id` 存在性近似；后续可扩展活动任务计数）；
- 策略/权重经 `smart_trigger.yaml agv` 段热加载（已有链路）。

### 3.6 决策审计与指标（P2-1/P2-2）

- **审计**：`batch_scan_all`/`_task_capacity` 输出 `TriggerAudit` 记录（时间戳、容量、候选列表、每候选 score 明细、排除原因、最终入队/派发结果）；可选落 SQLite `trigger_audit` 表（保留 N 天），Web 提供 `/api/trigger/audit?limit=`；
- **指标**：smart_trigger `get_status` 增加 `scan_duration_ms/avg`、`match_success_rate`、`queue_max_wait_s`；AGV 利用率由 status_poller 汇总（AVAILABLE 时长占比），经 WS `business_update` 推送。

### 3.7 前端与任务 ID（P3-1/P3-2）

- 前端：`renderDestGrid` 蓝色仓增加“可再匹配”角标（后端 `rematchable` 已就绪，doc/55）；配置面板按档位显示“立即生效/需重启”；新增“触发审计”查看页（只读）；
- 任务 ID：`generate_task_id` 改为 `TASK_{process_id短码}_{自增序号}_{src}`，进程内唯一、跨重启不冲突。

## 4. 关键代码示例（供评审，非本次落地）

### 4.1 评分排序接入（batch_matcher）

```python
# components/trigger/batch_matcher.py（目标改动示意）
def _sort_candidates(self, candidates):
    if not self._scoring_cfg or not self._scoring_cfg.get('enabled'):
        # 默认：现状固定排序（行为零变化）
        candidates.sort(key=lambda c: c.key(self._cargo_priority))
        return candidates
    # 评分模式：主层保底 + 权重微调
    candidates.sort(key=lambda c: (c.key(self._cargo_priority)[:2], -c.score(self._scoring_cfg)))
    return candidates
```

### 4.2 配置文件监听（param_manager）

```python
# base/param_manager.py（目标改动示意）
def start_config_watcher(self, interval=2.0, debounce=1.0):
    """轮询 plugin_configs 目录 mtime，变更经校验后发布 plugin_configs.updated"""
    def _watch():
        while not self._stop_watch.is_set():
            changed = self._scan_mtime()
            if changed:
                time.sleep(debounce)
                self._reload_changed_plugins(changed)   # 校验→内存→事件；失败回退快照
            self._stop_watch.wait(interval)
    threading.Thread(target=_watch, daemon=True).start()
```

### 4.3 队列快照/恢复（task_queue）

```python
# components/trigger/task_queue.py（目标改动示意）
def snapshot(self) -> list:
    with self._lock:
        return [{'src_bay': c.src_bay, 'dst_bay': c.dst_bay, 'cargo_type': c.cargo_type,
                 'bind_time': c.bind_time, 'enqueue_time': c.enqueue_time,
                 'lane_id': c.lane_id, 'strategy': c.strategy} for c in self._queue]

def restore(self, rows: list) -> int:
    """启动恢复：仅接受 始发仍绑定 + 目的仓仍空/未保留 + 未超龄 的候选"""
    restored = 0
    for r in rows:
        if not self._is_restorable(r):
            continue
        cand = TaskCandidate(src_bay=r['src_bay'], dst_bay=r['dst_bay'],
                             cargo_type=r['cargo_type'], bind_time=r.get('bind_time', 0),
                             enqueue_time=r.get('enqueue_time', time.time()),
                             lane_id=r.get('lane_id'), strategy=r.get('strategy'))
        self.enqueue_all([cand], max_total=self._max_total)
        restored += 1
    return restored
```

### 4.4 绑定校准（bay_status_fusion）

```python
# plugins/bay_status_fusion_plugin.py（目标改动示意，方案 B）
def _calibrate_bindings(self):
    """激活后：对 AI 稳定有货且本地未绑定的仓位幂等重绑（恢复 bind_status）"""
    for bay_id, st in (self.cache.get_all_bay_status() or {}).items():

            self._do_bind(bay_id, st.get('cargo_type', 0))   # RCS 侧幂等
```

### 4.5 AGV least_busy 加权（robot_cache）

```python
# components/task_cache/robot_cache.py（目标改动示意）
def _least_busy_key(self, rid):
    e = self._robots[rid]
    idle = e.update_time                     # 空闲最早
    batt = e.battery / 100.0 if e.battery else 0.0
    return -(batt * self._w_battery + idle * self._w_idle)   # 权重可配，默认 w=0 回退现状
```

## 5. 测试与验收

### 5.1 单元测试（新增用例）

1. **评分默认等价**：`scoring.enabled=false`（及缺省）时 `batch_scan_all` 输出与现状完全一致（构造混合 bind_time/类型用例）；
2. **权重调参**：`wait_time` 权重增大后，等待更久的候选优先；`lane_depth` 惩罚生效；类型主层不被混排；
3. **队列恢复**：快照→重建队列→restore：有效候选恢复、失效候选（始发已解绑/目的仓被占/超龄）被清理且目的仓释放；
4. **配置监听**：修改 YAML mtime 触发 reload 并发布事件；非法 YAML 回退快照并告警；
5. **绑定校准**：模拟 AI 有货未绑定仓位，校准后 bind_status=1（方案 B 幂等路径）；
6. **AGV 加权**：least_busy 在电量差异下选电量高者（配置权重后）。
7. **回归**：既有 `test_trigger_yaml_config.py`（8 项）与 `test_trigger_ghost_lock.py`（5 项）保持通过。

### 5.2 板端验收清单

- 断电重启：候选队列恢复、已绑定仓自动校准、无重复绑定、无幽灵占用；
- 直接改 YAML：1-2s 内热生效（hot 项），非法内容自动回退并告警；
- 评分调参：现场按权重调整后匹对顺序符合预期，Web 审计可见评分明细；
- AGV least_busy 加权后负载均衡更均匀（可对比轮询/空闲最早）；
- 前端：蓝色仓“可再匹配”角标、配置档位提示、触发审计页可用。

## 6. 兼容性、实施顺序与回滚

### 6.1 兼容性

- 新增 YAML 字段（`scoring`、`agv.least_busy_weight` 等）缺省=现状，旧配置可直接使用；
- 新增 SQLite 表（`queue_snapshot`/`trigger_audit`）不影响现有表；未建表时功能自动降级（快照/审计跳过）；
- 文件监听默认关闭，需在 `params.yaml` 显式开启（`config_watch_enabled: true`），避免现场行为意外变化。

### 6.2 建议实施顺序

1. **P0-3/P0-4 配置闭环**（低风险、收益明显：改 YAML 即生效 + 非法回退）；
2. **P0-2 绑定校准**（需现场确认 RCS 接口后选择方案 A/B）；
3. **P0-1 队列快照恢复**（依赖 P0-2 提供恢复准确性）；
4. **P1-1 评分模型 + P1-2 AGV 加权**（默认等价，现场调参）；
5. **P2 审计与指标**；
6. **P3 前端与任务 ID**。

### 6.3 回滚

- 全部优化项均为增量：关闭 `scoring.enabled`、`config_watch_enabled` 或删除新增表即可回退；
- 业务代码改动集中、可独立回滚；文档/配置字段向后兼容。

---

## 7. 结论

1. 当前触发闭环逻辑正常（doc/56），优化重点是**可靠性（重启恢复/配置闭环）与可解释性（评分/审计）**，而非重写架构；
2. 推荐主线为：**P0 配置闭环 + 绑定校准 + 队列恢复**，随后叠加 **P1 可配权重评分（默认零变化）**，使“改 YAML 调触发机制”从参数层延伸到策略层；
3. 所有优化项均有默认等价/可回滚/可观测保障，建议按 §6.2 顺序分阶段评审实施。
