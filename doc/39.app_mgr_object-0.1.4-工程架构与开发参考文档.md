## 1. 工程总览

### 1.1 项目定位

`app_mgr_object` 是一个基于 ROS2（rclpy）的**插件化应用底座 + AGV 搬运任务调度系统**。业务主线为：

> 视觉 AI 检测起始仓位 → 稳定滤波 → RCS 绑定 → 智能触发器批量匹配 → 优先级任务队列 → 工作流引擎（YAML 状态机）→ RCS 下发/执行 → 回调/轮询双通道闭环 → 资源释放 → Web 运维监控与配置热加载。

项目同时保留 0.0.x 时代的"设备状态采集上报 + Web 运维"能力（`object_status` 等插件仍存在于包内，但未进入 0.1.4 默认加载顺序），核心演进方向已转向**AGV 搬运任务调度与工作流闭环**。

## 2. 分层架构

### 2.1 分层模型

```text
┌────────────────────────────────────────────────────────────────┐
│ 应用层（main.py）                                              │
│ AppMgrNode：EventBus + 6 个基础管理器 + 插件发现/加载/注册       │
├────────────────────────────────────────────────────────────────┤
│ 插件层（plugins/，业务功能载体，继承 BasePlugin）                 │
│ network → callback_handler → rcs_adapter → bay_status_fusion   │
│ → status_poller → workflow_engine → task_status_monitor        │
│ → smart_trigger → web_monitor（默认加载顺序）                    │
├────────────────────────────────────────────────────────────────┤
│ 组件层（components/，无 ROS2 强耦合的可复用单元）                 │
│ task_cache / trigger / workflow / task_monitor / rcs_client /  │
│ callback / device_status / reporting / network / web / …       │
├────────────────────────────────────────────────────────────────┤
│ 基础框架层（base/，与 ROS2 紧耦合）                              │
│ LifecycleMgr / ParamMgr / PluginMgr / ServiceMgr /             │
│ SubscriptionMgr / TimerMgr / UnifiedLogger                     │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 启动时序（main.py → AppMgrNode.__init__）

1. 初始化 `EventBus`；
2. 初始化 6 个基础管理器并注册到 `LifecycleManager`；
3. 启动 **独立 asyncio 事件循环线程**（`node.asyncio_loop`，供工作流/触发器/Web 异步任务使用）；
4. 配置日志级别；
5. `ParamManager` 从 `config/plugin_configs/` 目录加载各插件配置、从 `web_monitor.yaml` 加载 Web 配置；
6. `PluginManager.discover('app_mgr_object.plugins')` 自动发现插件类（继承 `BasePlugin` 且声明 `PLUGIN_NAME`）；
7. 按 `plugin_load_order` 依次加载插件（`web_monitor` 配置独立，特殊放行）；
8. 将已加载插件注册到生命周期管理器（`auto_start` 取自插件配置）；
9. `LifecycleManager.configure()` → 各插件 `_configure_impl()`；
10. `LifecycleManager.activate()` → 各插件 `_activate_impl()`。

关闭时：`SIGINT/SIGTERM` → `executor.shutdown()` → `node.shutdown()` → `lifecycle_manager.shutdown()`（deactivate → cleanup）。

### 2.3 基础管理器职责

| 管理器 | 核心职责 | 关键点 |
|---|---|---|
| LifecycleManager | 模块状态机：UNCONFIGURED → INACTIVE → ACTIVE → FINALIZED/ERROR；configure/activate/deactivate/cleanup/shutdown；健康状态聚合 | 通过 `hasattr` 弱检查方法存在性；`_state_change_callbacks` 注册了但框架内未触发（遗留）|
| ParamManager | ROS2 参数声明 + 独立 YAML 加载 + 原子热加载持久化 | `update_plugin_config_nested(path, value)` 支持 dict/list 嵌套路径；临时文件 + `os.replace` + 回读校验；变更后回调 + EventBus 广播 |
| PluginManager | 包内自动发现、加载、启停、重配置 | 仅支持 Python 包内模块；发现机制为 `pkgutil.iter_modules` |
| ServiceManager | 管理 ROS2 Service | 默认 ReentrantCallbackGroup；`create_trigger_service` 快捷方法 |
| SubscriptionManager | 管理 ROS2 订阅 | 批量创建设备订阅；remove 仅为移除引用（未真正 destroy）|
| TimerManager | 管理 ROS2 Timer + 执行统计（EMA） | **oneshot 模式存在双定时器 bug（见 11.4）** |
| UnifiedLogger | Python logging + ROS2 logger 双通道 | 文件日志默认路径 `/var/log/app_mgr`（硬编码）；`PerformanceTimer` 性能统计 |

### 3.2 BasePlugin 生命周期模板

```text
__init__ → configure() [_configure_impl] → activate() [_activate_impl]
         → deactivate() [_deactivate_impl] → cleanup() [_cleanup_impl]
```

每个阶段成功/失败均通过 `EventBus` 发布 `plugin.configured / plugin.activated / plugin.deactivated / plugin.cleaned` 事件。基类 `_*_impl` 均有默认实现（返回 True），未强制抽象——新插件容易漏实现而静默通过。

### 3.3 EventBus 事件清单（插件间通信主干）

| 事件 | 发布方 | 订阅方 | 用途 |

| `workflow.resources_released` | workflow Action | smart_trigger | 资源已释放 |

## 4. 组件层详解

### 4.1 task_cache —— 内存状态缓存（调度决策数据源）

| 类 | 数据 | 关键接口 |
|---|---|---|
| `BayCache` | 24 个起始仓位（A1001~D1006）：cargo_type、ai_detected、bind_status(0/1/2)、debounce_count、in_task、bind_time | `update_ai_result`、`set_bound/binding/unbound`、`mark_in_task`、`get_bound_bays_of_type`、`reload_config` |
| `DestBayCache` | 终点仓位（T2001~T4006）：cargo_type、floor_no、is_empty、source | `update`、`get_empty_bays_of_type`、`reload_config` |
| `RobotCache` | AGV（1001/1002）：status（AVAILABLE/BUSY/OFFLINE/ERROR）、battery、position | `update_status`、`set_busy/set_idle`、`get_available_robot`（轮询负载均衡）|
| `ConfigCache` | 系统配置 + 仓位映射 + 工作时段 | `get_sys/get_int/get_float`、`set_source_mapping` 等 |
| `StateCoordinator` | 统一资源联动（P1-2）| `dispatch_task`（锁 AGV/起点/终点 + 标记 busy/in_task）、`release_task`、`get_snapshot` |

设计特点：全部读写加 `RLock`；每个条目带 `revision/source/update_time` 便于审计；支持 `reload_config` 热更新。

### 4.2 trigger —— 触发机制组件

| 类 | 职责 | 关键点 |
|---|---|---|
| `ScheduleChecker` | 工作时间窗口判断 | 支持列表式 `{day_of_week,start_time,end_time,enabled}` 与简化格式；解析失败默认放行 |
| `ResourceLocker` | AGV/起点/终点三资源原子锁定 | 线程安全；`lock` 任一占用则整体失败 |
| `TaskBatchMatcher` | 批量贪婪匹配（v2.0）| 显式配对覆盖优先 → 剩余按 bind_time 降序 ↔ 终点字典序 1:1 配对；按 `cargo_priority → src → dst → bind_time` 全局排序；每仓位只参与一次配对 |
| `TriggerEngine` | 触发引擎门面 | 条件：时间窗口 + 已绑定未分配起点 + 空终点 + 可用 AGV；`batch_scan_all` 输出候选（未锁）|
| `TaskQueue` | 任务优先级队列 | FIFO + AGV 感知分发、去重（src/dst）、老化 TTL（默认 300s）、容量上限（默认 50）、统计 |

### 4.3 workflow —— 工作流组件

| 类 | 职责 |
|---|---|
| `WorkflowDefinitionLoader / WorkflowDefinition / WorkflowStateDef` | YAML 定义加载与模型（states/transitions/on_enter/on_exit/retry/timeout/final/on_error）|
| `WorkflowInstance` | 单实例状态机执行器：asyncio 事件队列、超时/重试、补偿循环检测、状态转移持久化 |
| `WorkflowEngine` | 实例管理：创建/恢复/取消/事件注入、`asyncio.Semaphore` 并发控制、回调分发 |
| `ActionRegistry` | Action 注册与执行（异步函数，返回事件名）|
| `WorkflowPersistence` | SQLite 持久化（task_instances / state_change_log / alarm_logs / exception_log）|
| `WorkflowEventBridge` | EventBus ↔ Engine 双向桥（发布任务事件、订阅 RCS 回调并映射注入）|
| `AlarmClassifier` | warnCallback 告警分级（L0~L3）与处置策略 |

## 5. 参数模块架构

### 5.1 配置分层与来源

```text
params.yaml（ROS2 声明参数）
├── log_level / 网络 / 回调 / 请求队列 / QoS / 插件加载顺序
├── plugin_configs_dir: config/plugin_configs    ← 插件配置目录
└── web_monitor_config: config/web_monitor.yaml  ← Web 配置单文件

config/plugin_configs/*.yaml（8 个）→ _params['plugin_configs'][plugin_name]
config/web_monitor.yaml            → _params['web_monitor']
config/workflows/*.yaml            → 工作流定义（WorkflowDefinitionLoader 加载）
~/.app_mgr_object/task_instances.db→ SQLite 持久化（运行时数据）
```

### 5.2 加载时序

1. `_declare_common_parameters()`：声明 30+ 参数并写入 `_params` 缓存；字符串参数自动 JSON/YAML 解析；`plugin_load_order` 按逗号拆分；
2. `_load_external_configs()`：目录加载插件配置 + 单文件加载 web_monitor；
3. `_setup_param_callback()`：注册 ROS2 `on_set_parameters` 回调，参数变更实时更新 `_params` 并分发注册回调；
4. 插件 `configure()` 阶段从 `param_manager` 或自身 config 读取参数。

### 5.3 热加载流程（核心）

```text
Web PUT /api/config/bay|dest|schedule|pairs|params
  → ConfigManager.apply_config(section, value)
    → 业务校验（cargo_type 1~6、时段字段等）
    → ParamManager.update_plugin_config_nested(path, value)
        ① 定位 config/plugin_configs/<plugin>.yaml
        ② 沿路径导航（支持 dict + list index）
```

## 6. 工作流架构

### 6.1 YAML 状态机规范

```yaml
name / version / description / initial_state / max_concurrent
states:
  - id: state_id
    description
    action: action_name          # 主动作（异步函数，返回事件名）
    on_enter: [action...]        # 进入时动作
    on_exit:  [action...]        # 离开时动作
    retry / timeout / final
    transitions:
      - event: "event_name" → target: "next_state"
on_error: [action...]            # 全局异常处理（当前引擎未消费，见 11.3）
```

### 6.2 agv_transport_atomic v3 状态图

```text
calling_rcs ──rcs_ack_ok──▶ monitoring
    │ retry=2/timeout=10          │ timeout=100 → compensating_query
    ├─rcs_ack_fail──▶ failed      │ callback_completed → releasing
    └─timeout───────▶ failed      │ warn_l1 → warn_pause(60s→monitoring)
                                  │ callback_exception / L2/L3 → manual_intervention
                                  │ user_cancel → failed
compensating_query ──rcs_completed──▶ releasing
    │ rcs_failed / max_retry_reached / timeout → manual_intervention
    └─rcs_running──▶ monitoring（补偿循环 ≥3 次强制 manual）

warn_pause ──callback_completed──▶ releasing
    ├─callback_exception──▶ manual_intervention
    ├─warn_l1──▶ warn_pause（继续等待）
    └─timeout──▶ monitoring（60s 自动恢复）

manual_intervention（挂起态，非终态，无限等待）
    ├─user_retry──▶ calling_rcs
    ├─user_cancel──▶ failed
    ├─auto_resolved / callback_completed──▶ auto_recovery
    └─auto_failed / callback_exception──▶ failed

auto_recovery ──done──▶ completed
releasing ──done──▶ completed
completed（final，on_exit 因语义不会执行，见 11.3）
failed（final，同上）
```

### 6.3 引擎执行机制

1. `create_instance(workflow_name, context)`：加载定义 → 生成 task_id → 创建 `WorkflowInstance` → `asyncio.create_task(_run_instance)`；
2. `_run_instance`：`async with asyncio.Semaphore(max_concurrent)` 控制并发 → `instance.run()` → 终态回调（completed → `on_instance_completed`，failed → `on_instance_failed`）；
3. `WorkflowInstance.run()` 主循环：执行 on_enter → 执行主动作（`asyncio.wait_for` 超时 + 重试）或等待外部事件（`asyncio.Queue`）→ 按事件查 transitions → `_transition_to`（先 on_exit，再写状态日志 + UPSERT 实例）；
4. 未知事件：写诊断字段 → 进入 `manual_intervention`（已是挂起态则继续等待）；
5. 事件注入：`inject_event(task_id, event, data)` 由 EventBus 桥 / 轮询插件 / Web / /task_control 服务调用（跨线程用 `run_coroutine_threadsafe` 投递到 `node.asyncio_loop`）。

### 6.4 Action 注册表（workflow_engine_plugin 注册 9 个）

| Action | 行为 | 返回事件 |
|---|---|---|
| `invoke_gen_task` | 调用 RCS genAgvSchedulingTask（线程池化）| rcs_ack_ok / rcs_ack_fail |
| `wait_for_completion` | 挂起等待外部事件 | 原样透传事件名 |
| `compensate_query` | 主动 queryTaskStatus 核实 | rcs_completed / rcs_failed / rcs_running / max_retry_reached |
| `release_resources` | 优先 StateCoordinator 统一释放；缺省走分散释放 | done |
| `publish_completed_event` | EventBus + ROS2 话题 /task_completed | done |
| `publish_failed_event` | 发布 workflow.task_failed | done |
| `publish_manual_event` | 发布 workflow.task_needs_manual | done |
| `log_error` / `log_manual_entry` | 日志 + 异常持久化 | done |

### 6.5 RCS 状态码 → 工作流事件映射

| RCS taskStatus | 含义 | 工作流事件 | 注入来源 |
|---|---|---|---|
| 2 | 执行中 | （忽略）| 回调/轮询 |
| 9 | 已完成 | `callback_completed` | 回调、轮询、补偿查询、恢复校准 |
| 7 / 8 | 失败/取消 | `callback_exception` | 回调、轮询、补偿查询 |
| warnLevel 0/1/2/3 | 告警 | warn_info / warn_l1 / callback_exception（L2/L3）| warnCallback 分级 |

### 6.6 持久化与恢复

- SQLite（WAL）：`task_instances`、`state_change_log`、`alarm_logs`、`exception_log`；状态映射 `calling_rcs→DISPATCHING、monitoring→RUNNING、completed→SUCCESS、failed→FAILED、manual_intervention→MANUAL`；
- 上下文序列化：JSON 信封（schema_version=1），兼容旧 pickle；
- 断电恢复：启动时 `_validate_and_recover()` 先对历史未完成实例查询 RCS 实际状态——已完成(9)直接完结、失败(7)/取消(8)标失败、执行中(2)恢复监控、无响应标 manual；恢复逻辑当前仍直接访问 `_engine._definitions / _instances / _create_instance_obj` 等内部成员（见 11.2）。

## 7. 触发机制架构

### 7.1 触发条件（AND）

1. 当前时间在工作窗口内（ScheduleChecker）；
2. 存在已绑定（bind_status=1）且未分配任务（in_task=false）的起始仓位；
3. 存在同货物类型的空终点仓位；
4. 存在可用 AGV（AVAILABLE，轮询选择）。

### 7.2 批量匹配（v2.0 贪婪）

- 对每种 cargo_type：显式 `pair_overrides` 优先配对 → 剩余按 `bind_time 降序 ↔ 终点字典序` 1:1 贪婪配对；
- 排除已锁定（ResourceLocker）与已入队（TaskQueue）的 src/dst，防止重复；
- 全局排序键：`(cargo_priority 排名, src_bay, dst_bay, -bind_time)`；
- 每轮最多 `max_tasks_per_scan`（默认 10）个候选。

### 7.3 资源锁定与队列

```text
扫描循环（2s）：
  TaskQueue.age_out()（TTL 300s 老化）
  → 时间窗口检查
  → batch_scan_all(exclude=已锁∪已入队)
  → enqueue_all（去重 + 容量 50 上限）
  → _dispatch_from_queue()（每轮最多 3 个）

出队：try_dequeue
  → 选一台可用 AGV
  → StateCoordinator.dispatch_task：ResourceLocker.lock(AGV,src,dst)
      → 成功：mark_in_task(src)、set_busy(AGV)、出队、发布 trigger.task_created
      → 失败：保持队列等待

释放：workflow 完成/失败 → task_completed/task_failed 事件 → smart_trigger._release_via_coordinator
  → StateCoordinator.release_task：释放锁、src 解除 in_task、AGV 置 AVAILABLE、终点置非空
  → 立即尝试分发下一任务（事件驱动闭环）
```

### 7.4 事件驱动入口

- `bay.bound`：仓位绑定成功 → 刷新终点仓位 → 单次扫描 + 分发；
- `workflow.task_completed / task_failed / resources_released`：释放资源后立即续发。

## 8. 业务流说明（端到端）

### 8.1 总业务闭环

```text
AI 检测消息（/dev01_object_status, BayStatus）
  → bay_status_fusion：通道信号校验 → 逐仓位 AreaStatusFilter 防抖
  → 稳定有货 → RCS bindCtnrAndBin → bay.bound 事件
  → smart_trigger：扫描 → 贪婪匹配 → 队列 → 分发（锁资源）
  → trigger.task_created → workflow_engine：创建 agv_transport_atomic 实例
  → calling_rcs：RCS genAgvSchedulingTask（taskNo 回填 context）
  → monitoring：等待 rcs.agv_callback / task_status_monitor 轮询
  → callback_completed → releasing（释放资源）
  → completed → workflow.task_completed → 队列续发下一个任务
```

### 8.2 流程 1：仓位绑定链路

`BayStatus(msg) → 通道信号 OK → area.has_cargo → AreaStatusFilter.update()`，稳定翻转时：

- 有货：发布 `bay.status_changed` → `bindCtnrAndBin(ind_bind=1)` → 成功 `set_bound` + 发布 `bay.bound`，失败 `set_unbound`；
- 无货：发布事件 + 缓存解绑（**仅本地缓存，未调用 RCS 解绑**，依赖 bindNotify 回调补偿，见 11.2）。

### 8.3 流程 2：任务生成链路

见 7.3。关键时序：**先锁资源再发布任务**，避免同一 AGV/仓位被并发下发；任务失败/完成均通过事件回到触发器释放资源。

### 8.4 流程 3：工作流执行链路

见 6.2/6.3。双通道闭环：RCS 主动回调（agvCallback/warnCallback）+ 轮询补偿（task_status_monitor 按需轮询，monitoring 每 10s、manual 每 30s）。

### 8.5 流程 4：告警处置与人工介入

```text
warnCallback → AlarmClassifier.classify()
  L0(信息)   → 仅记录 alarm_logs
  L1(警告)   → 注入 warn_l1 → warn_pause（60s 自动恢复 / 升级）
  L2(严重)   → 注入 callback_exception → manual_intervention
  L3(紧急)   → 同上 + 发布 rcs.critical_alarm（Web 弹窗）

manual_intervention：
  - Web /task_control：user_retry → 重新 calling_rcs；user_cancel → failed
  - task_status_monitor 每 30s 查询：RCS 9 → auto_resolved；7/8 → auto_failed（自动闭环）
  - 超过 600s 未处置 → rcs.alarm_escalated（当前无消费方，见 11.1）
```

### 8.6 流程 5：Web 运维与配置热加载

```text
WebServer 独立线程（:9183）
  ├─ 页面：/、/monitor、/control、/test、/calibration
  ├─ REST：/api/status*、/api/control*、/api/config*、/api/business/*、/api/task/*、/api/alarms、/api/calibration/*
  └─ WebSocket：/ws（status_update / status_periodic / business_update / slot_update / alarm_update / config_updated）
监控线程（plugin）：周期 get_system_status → AlarmManager.check_system_status → 广播
```

## 10. 现存问题与风险（代码级审查）

### 10.1 架构/设计层面

| 级别 | 问题 | 位置 | 说明 |
|---|---|---|---|
| 高 | 工作流全局 `on_error` 未被引擎执行 | `workflow/instance.py`、YAML | 定义支持 `on_error`，但实例执行中从不消费，异常仅靠回调兜底 |
| 高 | 终态 `on_exit` 永远不执行 | `workflow/instance.py` | `run()` 循环条件 `not is_final_state`，进入 completed/failed 即退出，其 on_exit（publish_completed_event / release_resources / publish_failed_event）为死配置；任务事件依赖引擎回调，资源释放依赖 smart_trigger 事件兜底——smart_trigger 未加载时失败任务会资源泄漏 |
| 中 | `rcs.alarm_escalated` 无消费方 | `task_monitor_plugin.py` | 人工介入超时 600s 升级告警仅发布事件，无人订阅、无页面呈现 |
| 中 | 双通道资源释放（重复释放）| `workflow_engine_plugin` + `smart_trigger` | 正常完成路径：releasing 已释放，task_completed 事件又触发 `_release_via_coordinator` 二次释放（幂等但语义混乱）|
| 中 | 插件间大量私有成员访问 | `smart_trigger`（`_trigger_engine._schedule_checker`）、`web`（`pm._params`、`trigger._task_queue`、`bay_fusion.cache` 等）| 已部分整改（公开属性/接口），仍有残留，破坏封装、阻碍重构 |
| 中 | 内部不一致的 RCS 查询键 | `workflow_engine_plugin`（补偿/恢复用 `rcs_task_no`）vs `task_monitor`（用 `task_id`）| queryTaskStatus 入参语义需与 RCS 确认，二者必须统一 |
| 低 | 全局 `max_concurrent` 双份配置 | workflow YAML 与 plugin_configs 均声明 | YAML 中 max_concurrent 未生效，易误导 |

### 10.2 并发与数据一致性

| 级别 | 问题 | 位置 |
|---|---|---|
| 高 | 同话题双消息类型冲突隐患 | `/dev01_object_status`：bay_status_fusion（BayStatus）vs object_status（AllObject，未启用）|
| 中 | 稳定无货仅本地解绑，未调用 RCS unbind | `bay_status_fusion._on_stable_empty`；依赖 bindNotify 补偿，现场无回调时缓存与 RCS 不一致 |
| 中 | 恢复逻辑直接操作引擎私有字段 | `workflow_engine_plugin._validate_and_recover` 访问 `_definitions/_instances/_create_instance_obj`；已提供公开接口但恢复路径未迁移 |
| 中 | 资源释放两套路径行为不一致 | `StateCoordinator.release_task` 不执行 `set_unbound`，旧路径执行；起点仓位解绑依赖后续 AI 无货/回调 |
| 低 | `WorkflowEngine._instances` 多线程遍历/增删 | 事件线程与定时器线程并发访问 dict |
| 低 | `TimerManager.oneshot` 双定时器 bug | oneshot 模式创建两个 timer，第一个泄漏未取消，回调执行两次 |
| 低 | force_trigger 不经过资源锁定 | 手动任务可能与自动任务抢占同一 AGV/仓位 |

### 10.3 健壮性/运维

- Web 控制接口默认无鉴权（`auth_required: false`），`execute_command` 可执行任意命令，生产环境风险高；
- `web_monitor.yaml` 明文存储标定登录口令（`admin@123`）；
- 日志文件路径 `/var/log/app_mgr` 硬编码；
- `_get_pkg_share_dir` 兜底 `os.getcwd()`，非 colcon 安装运行时配置路径易错；
- `bay_status_fusion` 模块级 `print("[DEBUG] ...")` 残留；
- `BusinessCollector.get_task_queue_data` 读取 `queue_size/items`，但 `TaskQueue.get_stats` 返回 `queue_size/queued_src/queued_dst` → 队列前端恒显示空；
- `BusinessCollector.get_agv_status` 统计 `status == 'IDLE'`，而内部状态为 `AVAILABLE` → available_count 恒为 0；
- `BusinessCollector.get_task_statistics` 对 `get_active_instances()`（dict 快照）做对象属性访问 → 状态恒 unknown；
- `RCSResponseParser.parse_agv_status` 映射可疑（3→ERROR、4→AVAILABLE），且当前轮询路径未使用该解析器，双套映射易漂移；
- `request_handler` 组件引用不存在的 `rcs_client.models/constants`，属未完成代码（未被插件引用，属死代码）。

### 10.4 代码质量

- `web_server.py` 存在大量注释掉的旧告警路由（L854~L947）与双套广播/告警循环（组件内线程 + 插件监控线程），职责重叠；
- 基类模板方法非强制（默认实现返回 True），新插件漏实现不报错；
- 部分文件注释/中文标点混用、调试打印残留；
- `setup.py` 版本号固定 `0.0.0`，与包版本（0.1.4）不一致。

## 11. 优化与扩展建议

### 11.1 P0（高优先，建议近期修复）

1. **统一资源释放语义**：明确"资源释放唯一入口"（建议 `StateCoordinator`），工作流 `release_resources` 与 `workflow.task_completed/task_failed` 事件释放互斥（如事件携带 `released: true` 标记）；failed 终态补一次确定性释放，避免 smart_trigger 缺失时泄漏。
2. **执行终态 on_exit / 全局 on_error**：在 `run()` 循环退出前执行终态 `on_exit`；实现 `on_error` 处理（Action 抛异常 → log_error + release + publish_failed）。
3. **统一 RCS 查询键**：确认 queryTaskStatus 入参为 taskCode 还是 taskNo，补偿/恢复/轮询三处统一；建议在 context 中保存双键并实现兼容双查询。
4. **Web 控制接口鉴权**：至少加 token/签名校验；敏感口令移出 YAML（环境变量/密钥文件）。
5. **修复 BusinessCollector 三处字段不匹配**（queue、agv IDLE、task stats），保证仪表盘数据真实。

### 11.2 P1（中优先）

1. 插件间私有访问收敛：`smart_trigger`/`web` 全面改为公开接口（engine/queue/schedule_checker/config_cache 已部分提供属性，补齐并迁移）；
2. `_validate_and_recover` 迁移到公开接口，移除对 `_definitions/_instances/_create_instance_obj` 的直接访问；
3. 稳定无货时增加可选 RCS 解绑（`bindCtnrAndBin(ind_bind=0)`），或至少记录缓存漂移告警；
4. `rcs.alarm_escalated` 接入 Web 告警/广播链路；
5. 同话题双消息类型：将 object_status 的订阅话题与 bay_status_fusion 的 ai_topic 彻底分离（如 `/object_status_v1`），或删除遗留插件；
6. 修复 `TimerManager.oneshot` 双定时器；
7. `force_trigger` 增加资源锁定与冲突检查；
8. `RCSResponseParser` 状态映射修正（IDLE/BUSY/OFFLINE/ERROR 一一对应），并让 status_poller 复用解析器，消除双套映射。

### 11.3 P2（低优先/重构）

1. `LifecycleManager._state_change_callbacks` 接入真实状态迁移（当前未触发）；
2. 清理死代码：`web_server` 注释路由、`request_handler`（补齐 rcs_client.models/constants 或移除）、`token` 组件（或启用 OAuth2 鉴权）；
3. `setup.py` 版本号与包版本统一（读取 `package.xml` 或硬编码对齐）；
4. 删除 `print()` 调试残留，规范中文注释与文档字符串；
5. `ParamManager.update_plugin_config_nested` 成功后若 handler 应用失败，回滚文件或补偿内存，保证文件/内存一致；
6. 配置校验外置为 schema（jsonschema），供 ConfigManager 与 API 层复用。

### 11.4 扩展方向

| 方向 | 建议 |
|---|---|
| 多场景工作流 | 新增搬运类型（如空车回库、多 AGV 协同、跨楼层）时仅新增 YAML + Action，不改引擎；建议补充"工作流版本迁移"（schema_version + 迁移脚本）|
| 调度算法升级 | 从"类型优先级 + 贪婪"升级为带路径代价/AGV 电量/楼层约束的评分函数；`TaskBatchMatcher` 已抽象，可替换匹配器实现 |

## 12. 二次开发指引

### 12.1 新增一个插件

1. 在 `plugins/` 下新建 `xxx_plugin.py`，继承 `BasePlugin`，声明 `PLUGIN_NAME`；
2. 实现 `_configure_impl / _activate_impl / _deactivate_impl / _cleanup_impl`（返回 bool）；
3. 在 `config/plugin_configs/xxx.yaml` 提供配置（含 `auto_start`）；
4. 在 `params.yaml` 的 `plugin_load_order` 中按依赖顺序插入；
5. 在 `plugins/__init__.py` 导出（便于 IDE/静态分析，非必须）；
6. 若需与其他插件协作：通过 `node.<plugin_name>` 或 `node.plugin_manager.get_plugin(name)` 获取实例，通过 `EventBus` 发布/订阅事件。

### 12.2 新增一个工作流

1. 在 `config/workflows/xxx.yaml` 编写状态机（见 6.1 规范）；
2. 在 `workflow_engine_plugin._register_actions()` 注册所需 Action；
3. 在调用方（触发器/Web/服务）指定 `workflow_name` 创建实例；
4. 通过 `WorkflowEngine.get_active_instances / get_instance_snapshot / get_task_from_db` 查询，`inject_event / cancel_instance` 控制。

### 12.3 新增一个组件

1. 在 `components/` 下新建子包，保持无 ROS2 强耦合（依赖通过构造注入）；
2. 提供线程安全接口与 `get_status()`；
3. 由插件在 `configure()` 阶段组装，`activate()` 阶段启动线程/定时器。

### 12.4 本地调试

- 模拟仓位：`scripts/bay_status_simulator.py`（按仓位/通道/货物类型模拟 AI 检测消息）；
- 强制任务：调用 `/task_control` 服务 `force_trigger` 或 Web `/api/task/control`；
- 查看状态：Web `/api/business/summary`、`/api/task/instances`、`/api/task/history`；
- 数据库：`~/.app_mgr_object/task_instances.db`（task_instances / state_change_log / exception_log 可直接 SQL 排查）。
